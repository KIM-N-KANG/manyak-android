# 권한 흐름

## 목적

런타임 권한을 요청하고 거부 이후를 다루는 작업 스킬입니다. 권한이 필요한 기능마다 반복되는 흐름을 맡습니다.

**무엇을 수집하고 왜 필요한지는 여기서 정하지 않습니다.** 수집 항목의 최소화, 보관 기간, 삭제 경로, 스토어 공시는 고려 사항 4번 항목 스킬에서 정합니다. 알림 권한은 채널이라는 별도 축이 있어 고려 사항 5번 항목 스킬이 맡되, 아래 일반 원칙은 거기서도 그대로 적용됩니다.

이 스킬은 **요청하고 거부당한 뒤에 무엇을 하는가**를 다룹니다.

## 선행 전제: 요청 기회는 사실상 한 번입니다

영구 거부 상태가 되면 시스템 대화상자가 더 이상 뜨지 않습니다. 코드는 요청을 보내지만 아무 일도 일어나지 않고, 콜백은 즉시 거부로 돌아옵니다. 여기서 두 규칙이 나옵니다.

- **그 한 번을 언제 쓸지가 이 흐름의 핵심입니다.** 아무 맥락 없이 일찍 쓰면 거부되고, 거부되면 되돌릴 방법이 앱 안에 없습니다.
- **거부 이후 경로가 없으면 기능이 죽은 채로 남습니다.** 사용자는 버튼을 눌러도 아무 반응이 없는 화면을 보게 됩니다. 가장 흔한 권한 관련 버그입니다.

## 적용 범위 판단

| 요청 | 검토할 것 |
| --- | --- |
| 권한이 필요한 기능 구현 | 전부 |
| 권한 흐름 감사 | 전부 |
| 눌러도 아무 일이 없는 문제 | 거부 상태 구분, 설정 안내 |
| 앱 설정 토글과 실제 권한이 어긋남 | 상태 동기화 |
| 특정 기기·버전에서만 다르게 동작 | 버전별 차이 |
| 권한을 새로 추가 | 요청 시점, 사전 설명, 축소 경로 |

## 요청 시점과 사전 설명

- **그 권한이 필요한 동작 직전에 요청합니다.** 앱 시작 시 한꺼번에 요청하면 거부율이 오르고 사용자는 무엇에 쓰이는지 모릅니다.
- **요청 전에 앱 화면으로 이유를 설명합니다.** 시스템 대화상자는 이유를 말해 주지 않습니다. 설명 화면에서 사용자가 그만두기를 선택하면 시스템 요청을 띄우지 않아 기회를 남겨 둡니다.
- **사용자가 명시적으로 시작한 동작에 붙입니다.** 사진을 고르려고 버튼을 누른 직후의 요청은 이해되지만, 화면에 들어서자마자 뜨는 요청은 이해되지 않습니다.

## 거부 상태 구분

| 상태 | 무엇이 다른가 | 해야 할 일 |
| --- | --- | --- |
| 아직 묻지 않음 | 요청하면 대화상자가 뜸 | 사전 설명 후 요청 |
| 거부됨 | 다시 요청할 수 있음 | 왜 필요한지 다시 설명하고, 사용자가 원할 때 재요청 |
| 영구 거부 | **요청해도 대화상자가 뜨지 않음** | 앱 요청을 보내지 말고 시스템 설정으로 안내 |

- **세 상태를 구분하지 않으면 세 번째에서 조용히 실패합니다.** 요청을 보냈는데 아무 일도 없는 것이 이 경우입니다.
- **설정으로 보낼 때 무엇을 켜야 하는지 알려 줍니다.** 설정 화면을 열어 주는 것만으로는 사용자가 어느 항목을 찾아야 하는지 모릅니다.
- **설정에서 돌아왔을 때 상태를 다시 읽습니다.** 사용자가 켜고 돌아왔는데 화면이 그대로면 다시 껐다고 생각합니다.

## 상태 동기화

- **앱 안의 설정 토글을 앱이 따로 기억하지 않습니다.** 시스템 권한 상태를 읽어 표시합니다. 따로 저장하면 사용자가 시스템 설정에서 끈 뒤에도 앱은 켜져 있다고 표시합니다.
- **화면에 돌아올 때마다 다시 읽습니다.** 권한은 앱 밖에서 언제든 바뀔 수 있고, 바뀌면 앱 프로세스가 종료되기도 합니다.
- **권한이 필요한 기능의 진입점에서 상태를 보여 줍니다.** 기능을 눌러야 꺼져 있다는 것을 알게 되면 이미 늦습니다.

## 축소 경로

- **권한 거부가 기능 전체를 막는 설계는 다시 봅니다.** 위치 권한이 없으면 직접 입력하게 하고, 사진 권한이 없으면 그때만 고르는 방식을 쓰는 식으로 대안을 만듭니다.
- **막아야 한다면 왜 막는지 화면에서 설명합니다.** 빈 화면이나 비활성 버튼만 두지 않습니다.
- 축소 경로를 만들 수 없으면 그 사실을 결정으로 적습니다. 적지 않으면 다음 사람이 다시 고민합니다.

## 버전별 차이

- **권한은 안드로이드 버전마다 갈립니다.** 어떤 버전에서 런타임 권한이 되었는지, 하위 버전에서는 어떤 상태로 시작하는지, 세분화된 권한으로 나뉘었는지 확인합니다.
- **요청 코드만 두고 하위 버전 동작을 확인하지 않으면 기기별로 갈립니다.** 최소 지원 버전과 최신 버전 양쪽에서 흐름을 확인합니다.
- **부분 허용을 처리합니다.** 일부 권한은 전부 대신 일부만 허용될 수 있고, 그 상태를 거부로 처리하면 사용자가 허용한 것을 쓰지 못합니다.

## 작업 흐름

1. **필요한 권한과 그것이 없으면 못 하는 동작을 나열합니다.** 최소 지원 버전에서의 동작도 함께 적습니다.
2. **요청 시점을 정합니다.** 어떤 사용자 동작 직후인지 구체적으로 적습니다.
3. **사전 설명 화면을 정합니다.** 그만두기를 골랐을 때의 경로도 함께 정합니다.
4. **세 가지 거부 상태의 분기를 만듭니다.** 영구 거부에서 설정으로 안내하는 경로를 반드시 포함합니다.
5. **상태를 읽어 표시하는 지점을 정합니다.** 별도로 저장하지 않습니다.
6. **축소 경로를 정하거나, 없다는 것을 적습니다.**
7. **버전별로 확인합니다.** 최소 지원 버전과 최신 버전에서 각각 실행합니다. 실행 확인은 `android-change-verification` 스킬을 씁니다.

### 검증 시나리오

| 시나리오 | 확인 방법 |
| --- | --- |
| 최초 거부 | 요청 대화상자에서 거부한 뒤 같은 기능에 다시 진입 |
| 영구 거부 | 거부를 반복해 영구 거부로 만든 뒤 기능 진입 |
| 설정에서 켜고 복귀 | 시스템 설정에서 권한을 켜고 앱으로 돌아옴 |
| 실행 중 시스템에서 끔 | 앱이 떠 있는 동안 시스템 설정에서 권한을 끔 |
| 사전 설명에서 그만두기 | 설명 화면에서 취소를 고름 |
| 권한 없이 사용 | 거부 상태로 기능 전체를 사용 |
| 최소 지원 버전 | 최소 지원 버전 기기에서 같은 흐름 실행 |
| 부분 허용 | 일부만 허용된 상태로 기능 진입 |

영구 거부와 실행 중 권한 해제는 개발 중에 거의 재현되지 않습니다. 개발자는 대개 한 번에 허용하고 넘어가기 때문입니다.
