# 간편 제작 퍼널 이탈 개편 — 시트형 전환·전 단계 이탈·키워드 임시 저장

- 공통 계약 정본: `../../../knk-harness/docs/product-specs/3-1-client.md` §3-1-4(이탈 가드·제작 임시 저장)
- 앱 결정 정본: `../../../knk-harness/docs/product-specs/3-3-android-app.md` §3-3-3(퍼널 구조)·§3-3-5(라이프사이클)
- 선행 계획: `create-funnel-recovery.md` — 이 계획이 그 문서의 D1·D3·D6을 대체한다

## 목표

- 퍼널 전 화면의 앱 바를 왼쪽 뒤로가기에서 **오른쪽 끝 arrow-down**으로 바꾸고, 퍼널 진입·이탈에 아래에서 올라오고 위로 내려가는 전환을 준다.
- arrow-down과 디바이스 뒤로가기를 같은 동작(퍼널 이탈 → 홈 복귀)으로 통일한다. 지금은 추가 정보 단계에서 둘 다 스토리라인 복귀다.
- 추가 정보 단계에서 이탈해도 선택 스토리라인·추천 선택·입력값을 그대로 재개할 수 있게 한다.
- "다시 선택하기"가 입력을 말없이 버리지 않도록 초기화 경고를 붙이고, 그 경로로 돌아오면 재개 지점도 스토리라인으로 되돌린다.
- 키워드 단계 입력을 임시 저장해 재개할 수 있게 한다(앱 전용 확장).
- 진행 레코드 저장 수단을 Preferences DataStore에서 Room으로 옮긴다.

## 새로 내린 결정

| # | 결정 | 근거 |
| --- | --- | --- |
| E1 | 퍼널 앱 바의 이탈 버튼은 오른쪽 끝 arrow-down(`ic_angle_down` 재사용) | 시트가 아래로 닫히는 전환과 짝이 맞는 어포던스다. 위치는 사용자 지정(오른쪽 끝). 새 자산을 만들지 않고 기존 셀렉트용 단색 자산을 그대로 쓴다 |
| E2 | 이탈 지점은 퍼널 3개 목적지 전부 — 키워드·스토리라인·추가 정보 | 추가 정보 단계에서도 arrow-down·디바이스 뒤로가기가 홈 복귀여야 한다는 사용자 결정. §3-3-5의 "가드는 스토리라인 화면 한 곳"을 대체한다 |
| E3 | 추가 정보 단계의 스토리라인 복귀 수단은 하단 "다시 선택하기" 하나만 남긴다 | 이탈과 인퍼널 복귀가 같은 제스처를 쓰면 어느 쪽인지 알 수 없다. 뒤로가기 계열은 전부 이탈, 단계 복귀는 명시적 버튼으로 가른다 |
| E4 | "다시 선택하기"는 추천 선택 또는 입력값이 있을 때 초기화 경고 다이얼로그를 거친다. 확정 시 추가 정보를 초기화하고 `selectedStorylineIndex`를 null로 되돌린 뒤 pop | 스토리라인을 다시 고르면 추천 목록이 달라져 기존 선택이 의미를 잃는다. 순번을 되돌려야 그 뒤의 이탈이 스토리라인 단계로 재개된다(E5) |
| E5 | 재개 지점은 `progress.selectedStorylineIndex` 유무로 가른다 — 있으면 추가 정보, 없으면 스토리라인 | 이미 있는 미러 값이 "추가 정보 단계에 도달했는가"를 그대로 표현한다. 별도 단계 필드를 두면 두 값이 갈라진다 |
| E6 | 퍼널 진입·이탈만 수직 슬라이드, 퍼널 단계 간 이동은 기존 크로스페이드 | 퍼널 한 덩어리가 올라왔다 내려가는 느낌이 목적이다. 단계 이동까지 수직이면 "다음 단계"와 "퍼널 진입"이 구분되지 않는다 |
| E7 | 전환 판정은 `NavEntry.metadata`의 퍼널 표식을 전역 `transitionSpec`이 읽어 수행한다 | `Scene.metadata`가 마지막 엔트리의 metadata를 그대로 노출하므로, 출발지·목적지 양쪽의 퍼널 여부를 한 곳에서 비교할 수 있다. 엔트리별 spec만으로는 퍼널→퍼널과 퍼널→바깥을 구분하지 못한다 |
| E8 | 키워드 단계 임시 저장은 **앱 전용 확장**으로 두고 3-1은 고치지 않는다 | 레코드 슬롯은 플랫폼별로 분리돼 있어 웹과 충돌하지 않는다. 공용 계약 개정은 웹 구현 일정에 묶인다 |
| E9 | 키워드 임시 저장은 새 stage `KEYWORD_DRAFT` + `PendingStoryCreation.KeywordDraft`로 표현한다 | 기존 세 stage의 "생성 결과가 반드시 있다"는 불변식을 유지한다. 기존 `Draft`의 `generation`을 nullable로 만들면 스토리라인·추가 정보 전 경로가 null 분기를 떠안는다 |
| E10 | 키워드 스냅숏은 `StoryCharacterInput`을 재사용하지 않고 전용 타입을 둔다 | 커스텀 키워드는 선택을 해제해도 목록에 남는 `CustomTag(name, selected)` 상태다. 요청 페이로드용 `List<String>`으로는 편집 상태가 복원되지 않는다 |
| E11 | 키워드 이탈은 입력이 하나라도 있을 때만 저장하고 기존 토스트 문구를 재사용한다. 없으면 조용히 이탈하며 소실 경고는 띄우지 않는다. **판정 기준은 선택 장르 태그·커스텀 장르 태그·주인공과 주변 인물의 이름·성별·특징 중 하나라도 비어 있지 않은 것**이며, 진입 시 놓인 빈 주변 인물 섹션 1개는 입력으로 세지 않는다 | 빈 화면을 열었다 닫은 것까지 배너로 남기면 배너가 신호를 잃는다. 키워드 단계에 소실 경고를 두지 않는 것은 3-1 제외 규칙 그대로다 |
| E12b | 키워드 스냅숏에 활성 카테고리 탭은 담지 않고 복원은 항상 첫 탭에서 시작한다 | 완료된 카테고리는 잠금이 풀려 있어 사용자가 바로 이동할 수 있다. 탭 위치까지 복원하면 저장할 상태만 늘고 복원 실패 시 잠긴 탭이 열린 것처럼 보일 수 있다 |
| E12c | 키워드 화면 ViewModel은 `PendingStoryCreationStore`를 직접 주입받아 저장·복원한다. 생성 스토어를 거치지 않는다 | 키워드 입력은 뒤 단계가 읽지 않아 단계 간 공유 상태가 아니다. 이미 함수 수 상한을 넘긴 생성 스토어에 무관한 책임을 더하지 않는다. 공유되는 규칙은 "진행 중 레코드 우선"(E12) 하나뿐이라 레코드 한 번 읽기로 충족된다 |
| E12 | 키워드 이탈 시 진행 중 레코드(`STORYLINE_GENERATION`·`STORY_COMPLETION`)가 있으면 덮어쓰지 않는다 | 3-1의 "진행 중 요청 우선" 규칙. 서버에서 실제로 돌고 있는 복구 대상이 편집 스냅숏보다 우선한다 |
| E13 | 키워드 화면은 진입 시 `KEYWORD_DRAFT`가 있으면 복원하고 레코드를 소비한다. 복원 대기 중에는 입력 미러링을 막는다 | "레코드가 남아 있는 진입은 곧 재개"라는 기존 규칙을 그대로 따른다. 미러링을 막지 않으면 복원 전 빈 입력이 저장분을 덮어쓴다 |
| E14 | 저장 수단은 Room 단일 행 테이블 `pending_story_creation`(`id` 고정 0) | 사용자 결정. 단일 슬롯 계약은 그대로 두고 수단만 바꾼다. 앞으로 Room이 필요한 저장소가 늘 것을 보고 기반을 먼저 깐다 |
| E15 | 컬럼은 `id`·`stage`만 정규화하고 페이로드는 `generationCommand`·`completionCommand`·`generation`·`progress`·`keywordSnapshot` 다섯 개의 nullable JSON 컬럼에 담는다. 타임스탬프 컬럼은 두지 않는다 | 슬롯이 1개라 조인할 대상이 없어 중첩 리스트까지 테이블로 쪼갤 이유가 없다. 기존 `PendingRecordDto`의 최상위 필드와 1:1로 대응시켜 직렬화 코드를 재사용한다. TTL은 3-1에서 범위 밖이고 정렬할 행도 없어 타임스탬프를 읽을 곳이 없다 |
| E16 | 스키마를 export하고 마이그레이션은 파괴적 폴백을 쓴다 | 진행 레코드는 재생성 가능한 스냅숏이고, 현행 스토어도 "해석 불가 = 없음"으로 폐기한다. 같은 규칙을 DB 수준에서 유지한다 |
| E17 | 기존 DataStore 레코드는 옮기지 않고 폐기하며, `pending_creation` DataStore 파일 삭제를 정리 코드에 넣는다 | 미출시 단계의 진행 스냅숏이라 이관 가치가 없다. 파일을 남기면 쓰는 곳 없는 사용자 귀속 데이터가 기기에 남는다 |

## 외부 합의 필요

없음 — 서버 계약과 웹 동작은 건드리지 않는다. 키워드 임시 저장은 클라이언트 로컬 저장소 안에서 끝난다.

## 이탈·복귀 동작표

| 화면 | arrow-down · 디바이스 뒤로가기 | "다시 선택하기" |
| --- | --- | --- |
| 키워드 | 입력 있으면 `KEYWORD_DRAFT` 저장 + 토스트 → 홈. 없으면 조용히 홈 | — |
| 스토리라인 (생성 중·선택) | 진행 중 레코드 유지 또는 `STORY_DRAFT` 저장 + 토스트 → 홈. 보존할 게 없으면 소실 경고 다이얼로그 | — |
| 추가 정보 (입력·완성 중) | 스토리라인과 같은 규칙 → 홈 | 추가 정보 있으면 초기화 경고 → 확정 시 초기화 후 스토리라인 복귀 |

재개 지점:

| 레코드 | 재개 지점 | 백스택 |
| --- | --- | --- |
| `KEYWORD_DRAFT` | 키워드 | `[탭, 키워드]` |
| `STORYLINE_GENERATION` | 스토리라인 | `[탭, 스토리라인]` |
| `STORY_COMPLETION` | 추가 정보 | `[탭, 스토리라인, 추가 정보]` |
| `STORY_DRAFT` · 선택 순번 있음 | 추가 정보 | `[탭, 스토리라인, 추가 정보]` |
| `STORY_DRAFT` · 선택 순번 없음 | 스토리라인 | `[탭, 스토리라인]` |

## 구현 단계

0. 하네스 §3-3-3·§3-3-5 결정 갱신(구현 전 선행)과 `create-funnel-recovery.md` 대체 표기.
1. `core:domain` — `PendingStoryCreation.KeywordDraft`와 키워드 스냅숏 타입, `CreationResumePoint.KeywordStep`, `resumePoint()` 분기.
2. `core:data` — Room 도입(버전 카탈로그·의존성·스키마 export), `ManyakDatabase`·엔티티·DAO·TypeConverter, `PendingStoryCreationRoomStore`(+`UserScopedStore` 바인딩), 기존 DataStore 스토어 제거와 파일 정리. (1 이후)
3. `core:ui` — `create_close_funnel` 문자열.
4. `feature:create` — `CreateFunnelHeader` 앱 바 교체, 키워드 VM 저장·복원, 추가 정보 VM 이탈·초기화 경로, 생성 스토어의 추가 정보 진행 초기화, 초기화 경고 다이얼로그. (1·3 이후, 5와 병렬 가능)
5. `app` — 퍼널 엔트리 메타데이터와 수직 전환 판정, 추가 정보 이탈 배선, `KeywordStep` 재개 체인.
6. 단위 테스트와 정적 검사.

## 검증

- 태그: `state-restore`(키워드·추가 정보 재개 복원), `session-cleanup`(Room 테이블이 사용자 귀속 정리에 참여), `idempotent-write`(레코드 우선순위 — 진행 중 레코드를 키워드 스냅숏이 덮지 않음)
- 단위 테스트: `resumePoint()` 분기, 키워드 VM 저장 조건·복원·미러링 차단, 추가 정보 VM 이탈 저장·초기화 후 순번 null, Room 스토어 읽기·쓰기·삭제·`clearUserData`, 전환 판정 순수 함수.
- 수동 검증: 퍼널 진입·이탈 전환의 z-order와 잔상, 각 단계 이탈 후 배너 재개 지점, 프로세스 재시작 후 재개, 로그아웃 후 레코드 삭제.
