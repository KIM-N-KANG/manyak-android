# 데이터·네트워크·동기화

## 목적

안드로이드 앱 개발 고려 사항 8개 항목 중 3번 **데이터·네트워크·동기화**를 담당합니다. 아래 7개 결정 항목을 각각 명시적으로 결정하거나, 기존 코드가 이미 내린 결정을 확인하고 위반을 지적합니다.

| 결정 항목 | 결정할 내용 |
| --- | --- |
| 1. 오류·타임아웃·재시도 | 네트워크 실패를 어떻게 분류하고 무엇을 재시도할지 |
| 2. 중복 방지 | 중복 요청과 중복 데이터 생성을 어떻게 막을지 |
| 3. 저장소 역할 분리 | 로컬 DB·키-값 저장소·파일 저장소의 역할을 어떻게 나눌지 |
| 4. 저장·캐시 대상 | 어떤 데이터를 로컬에 저장하거나 캐시할지 |
| 5. 오프라인 동작 | 오프라인에서 데이터를 어떻게 보여주고 수정할지 |
| 6. 동기화 | 앱·웹·여러 기기 간 데이터를 어떻게 맞출지 |
| 7. 충돌 처리 | 동시에 수정된 데이터의 충돌을 어떻게 처리할지 |

이 항목의 결정은 상당수가 클라이언트 혼자 정할 수 없습니다. 멱등성 키, 변경분 조회, 삭제 표시, 버전 필드는 서버와의 계약입니다. 합의되지 않은 것을 정해진 것처럼 설계하면 구현 단계에서 전부 뒤집힙니다.

## 적용 범위 판단

요청 규모에 맞는 항목만 검토합니다.

| 요청 | 검토할 항목 |
| --- | --- |
| 데이터 계층 설계, 연동 리뷰·감사 | 1~7 전부 |
| 화면 하나에 API 연동 추가 | 1, 2, 4 |
| 오프라인 지원 추가 | 3, 4, 5, 6, 7 |
| 저장소 도입, 저장 대상 판단 | 3, 4 |
| 중복 생성·데이터 어긋남 문제 진단 | 2, 6, 7 |

## 두 가지 선행 결정

나머지 결정이 전부 이 둘에서 갈라집니다.

### 화면이 보는 데이터의 출처를 하나로 정합니다

| 출처 | 화면이 관찰하는 것 | 적합한 경우 |
| --- | --- | --- |
| 네트워크 직접 | 요청 결과 | 오프라인 지원이 필요 없고 항상 최신이어야 하는 화면 |
| 로컬 저장소 경유 | 저장소 쿼리 결과, 네트워크는 저장소만 갱신 | 오프라인 표시, 재진입 즉시 표시, 여러 화면이 같은 데이터를 봄 |

한 데이터에 두 출처를 섞지 않습니다. 목록은 저장소에서, 상세는 네트워크에서 가져오면 같은 항목이 화면마다 다르게 보이고 어느 쪽이 맞는지 판단할 근거가 없어집니다.

### 읽기와 쓰기를 따로 결정합니다

| 구분 | 실패 비용 | 기본 전략 |
| --- | --- | --- |
| 읽기 | 다시 요청하면 복구됨 | 자동 재시도, 캐시로 대체 표시 |
| 쓰기 | 중복 생성, 데이터 손실, 되돌리기 어려움 | 멱등성 보장, 재시도 조건 제한, 충돌 규칙 |

읽기에 맞춘 재시도 정책을 쓰기에 그대로 적용하면 중복 생성이 납니다.

- **결정이 있으면 다시 결정하지 않습니다.** 결정을 읽고, 이 요청의 코드가 그것을 지키는지만 봅니다. 어긋나면 위반으로 보고합니다. 결정 자체를 바꿔야 하면 이유와 함께 `_project.md`를 갱신합니다.
- **결정이 없으면 여기서 정하고 그 결과를 `_project.md`에 남깁니다.** 남기지 않으면 다음 기능이 같은 결정을 처음부터 다시 하고, 기능마다 구조가 갈립니다.

## 결정 항목별 판단 기준

### 1. 오류·타임아웃·재시도

- **오류 분류를 먼저 정합니다**: 연결 실패, 타임아웃, 요청 오류(4xx), 인증 오류(401·403), 서버 오류(5xx), 응답 파싱 실패. 분류가 없으면 모든 실패가 같은 문구로 표시되어 사용자가 무엇을 해야 할지 알 수 없습니다. 화면 표시와 복구 안내는 고려 사항 7번 항목 스킬에서 함께 정합니다.
- **오류를 데이터 계층 경계에서 앱이 정의한 타입으로 변환합니다.** HTTP 예외나 직렬화 예외를 그대로 화면까지 올리면 화면이 네트워크 라이브러리에 묶이고, 화면마다 같은 분류 코드를 다시 씁니다.
- **자동 재시도 대상은 연결 실패, 타임아웃, 5xx, 429로 제한합니다.** 4xx는 몇 번을 보내도 같은 결과입니다. 401은 재시도가 아니라 토큰 갱신 경로이며 고려 사항 4번 항목 스킬에서 결정합니다.
- **재시도 방식**: 지수 백오프에 지터를 더하고, 최대 횟수와 전체 소요 시간 상한을 함께 정합니다. 지터가 없으면 장애 복구 시점에 모든 클라이언트가 같은 순간에 몰립니다. 서버가 응답에 재시도 가능 시점을 내려주면 계산한 백오프보다 그 값을 우선합니다.
- **타임아웃을 계층별로 정합니다**: 연결, 읽기, 쓰기, 그리고 재시도까지 포함한 전체 상한. 전체 상한이 없으면 느린 응답에서 화면이 무한 대기합니다.
- **쓰기 자동 재시도는 멱등성이 보장될 때만 합니다.** 보장되지 않으면 사용자에게 재시도를 맡기고, 앞선 요청이 처리됐는지 확인할 경로를 둡니다.
- **취소와 실패를 구분합니다.** 화면 이탈로 취소된 요청을 오류로 처리하면 사용자에게 의미 없는 오류가 뜹니다. 취소 범위는 고려 사항 2번 항목 스킬에서 정합니다.

### 2. 중복 방지

- **중복 요청 처리 방식을 정합니다**: 같은 요청이 진행 중일 때 무시할지, 취소하고 새로 보낼지, 진행 중인 결과를 공유할지. 버튼 연타, 화면 재진입, 자동 재시도가 겹치는 지점입니다.
- **UI 차단만으로 막지 않습니다.** 버튼 비활성화는 구성 변경이나 프로세스 복원에서 풀립니다. 요청 계층에서 막습니다.
- **중복 생성 방지는 서버와의 계약입니다.** 생성 요청마다 클라이언트가 고유 키를 만들어 보내고 서버가 같은 키의 재요청에 같은 결과를 돌려주는 방식을 쓸지 결정합니다. 이 계약이 없으면 응답을 못 받고 재시도한 순간 데이터가 두 번 생깁니다.
- **키 생성 시점이 중요합니다.** 사용자가 작성을 시작할 때 만들어 두고 모든 재시도에서 같은 키를 재사용합니다. 요청 직전에 만들면 재시도마다 새 키가 되어 아무것도 막지 못합니다.
- **식별자 발급 주체를 정합니다.** 서버 발급 식별자만 쓸지, 클라이언트가 만든 식별자도 쓸지 결정합니다. 오프라인 생성을 지원하려면 클라이언트 식별자가 필요합니다.

### 3. 저장소 역할 분리

| 저장소 | 담당 | 넣지 않을 것 |
| --- | --- | --- |
| 로컬 DB | 조회·정렬·관찰이 필요한 구조화 데이터, 전송 대기 항목 | 설정 값 하나, 큰 바이너리 |
| 키-값 저장소 | 사용자 설정, 온보딩 완료 여부, 마지막 동기화 시점 | 목록 데이터, 자주 바뀌는 대량 데이터 |
| 파일·캐시 디렉터리 | 이미지, 첨부, 다운로드 원본 | 검색·정렬이 필요한 데이터 |
| 보안 저장소 | 토큰, 자격 증명 | 일반 데이터 |

- 판단 기준은 셋 중 하나입니다: **쿼리하거나 관찰해야 하는가**(DB), **키 하나로 읽고 쓰는가**(키-값), **바이트 덩어리인가**(파일).
- 파일은 경로만 DB에 저장하고 실제 바이트는 파일 시스템에 둡니다. 큰 바이너리를 DB에 넣으면 쿼리와 스키마 변경이 함께 느려집니다.
- **시스템이 지울 수 있는 캐시 위치와 영구 저장 위치를 구분합니다.** 잃으면 안 되는 데이터를 캐시 디렉터리에 두지 않습니다.
- **스키마 변경 방식을 미리 정합니다.** 마이그레이션을 작성할지, 캐시성 데이터라 지우고 다시 받아도 되는지 결정해 두지 않으면 첫 스키마 변경에서 사용자 데이터가 날아갑니다. 실제 변경 작업과 마이그레이션 테스트는 `room-migration` 스킬이 맡습니다.
- 토큰과 민감 정보의 저장 위치는 고려 사항 4번 항목 스킬에서 결정합니다.

### 4. 저장·캐시 대상

- 판단 기준 세 가지입니다: **다시 열었을 때 즉시 보여야 하는가**, **오프라인에서 필요한가**, **재요청 비용이 큰가.** 셋 다 아니면 저장하지 않습니다.
- **저장하지 않을 것**: 한 번만 쓰는 응답, 매 요청마다 달라지는 결과, 민감 정보.
- **데이터마다 신선도 정책을 정합니다**: 유효 기간, 화면 진입마다 갱신할지, 당겨서 새로고침에서만 갱신할지.
- **캐시 표시와 갱신의 관계를 정합니다.** 캐시를 먼저 보여주고 뒤에서 갱신하면 화면이 두 번 바뀝니다. 갱신 중임을 표시할지 조용히 교체할지 결정합니다.
- **무효화 규칙을 정합니다**: 로그아웃, 계정 전환, 강제 업데이트 시 무엇을 지울지. 계정 전환 후 이전 사용자 데이터가 남으면 사고입니다.
- 페이지네이션 결과를 저장할 때는 서버가 페이지 기반인지 커서 기반인지 확인합니다. 페이지 기반은 목록이 바뀌면 경계가 어긋나므로 저장 단위와 갱신 방식을 함께 정합니다.

### 5. 오프라인 동작

- **읽기만 지원할지 쓰기까지 지원할지 먼저 정합니다.** 쓰기까지 지원하면 6번, 7번 결정 항목이 반드시 따라옵니다. 필요 없는데 쓰기를 지원하면 동기화와 충돌 비용을 그대로 떠안습니다.
- **읽기만 지원하는 경우**: 마지막으로 받은 데이터를 보여주고 언제 받은 것인지 표시합니다. 수정 동작은 막고 이유를 알립니다.
- **쓰기까지 지원하는 경우** 다음을 모두 정합니다.
  - 전송 대기 항목을 어디에 어떤 순서로 쌓을지
  - 아직 전송되지 않은 항목을 화면에서 어떻게 구분해 보여줄지
  - 전송 실패가 반복될 때 언제 포기하고 사용자에게 알릴지
  - 대기 중인 항목을 사용자가 다시 수정하거나 취소할 수 있는지
- **화면에 먼저 반영한 변경을 되돌리는 경로를 미리 정합니다.** 서버가 거절했을 때 화면을 되돌릴지 실패 표시를 남길지 정하지 않으면 사용자는 저장된 것으로 압니다.
- **연결 상태만으로 판단하지 않습니다.** 연결되어 있어도 요청은 실패합니다. 시스템의 연결 여부는 참고값이고 기준은 실제 요청 결과입니다.
- 전송 대기 항목을 앱이 꺼진 뒤에도 보내야 한다면 고려 사항 2번 항목 스킬의 지속 작업 결정과 같은 자리입니다.

### 6. 동기화

- **동기화를 일으키는 주체를 정합니다**: 클라이언트 주기 실행, 서버 알림으로 트리거(고려 사항 5번 항목 스킬), 사용자의 명시적 새로고침.
- **동기화 단위를 정합니다.** 전체를 다시 받을지, 마지막 시점 이후 변경분만 받을지. 변경분 방식은 서버가 변경 시각이나 커서를 제공해야 하므로 API 계약에 포함되어야 합니다.
- **삭제 전파를 반드시 확인합니다.** 변경분만 받으면 서버에서 삭제된 항목은 응답에 없으므로 클라이언트에 영원히 남습니다. 서버가 삭제 표시를 내려주는지 확인하고, 없으면 전체 재동기화 시점을 정합니다.
- **부분 실패를 정의합니다.** 여러 항목을 한 번에 맞출 때 일부만 성공하면 마지막 동기화 시점을 어디까지 올릴지 정해야 합니다. 실패한 항목을 건너뛰고 시점을 올리면 그 항목은 영원히 누락됩니다.
- **기준 시각은 서버 값을 씁니다.** 클라이언트 시계는 틀릴 수 있으므로 로컬 시간으로 변경분 경계를 계산하지 않습니다.
- **동기화 빈도와 트리거를 정합니다**: 앱 진입, 화면 진입, 주기 실행 중 무엇을 쓸지. 주기 실행은 배터리와 데이터 사용에 직접 영향을 줍니다.
- 여러 기기에서 같은 계정을 쓸 때 로그아웃과 탈퇴가 다른 기기에 어떻게 반영되는지는 고려 사항 4번 항목 스킬에서 결정합니다.

### 7. 충돌 처리

- **충돌 감지 방법을 서버와 합의합니다.** 버전 번호나 갱신 시각을 함께 보내고 서버가 어긋나면 거절하는 방식이 기본입니다. 감지 수단이 없으면 나중 요청이 앞선 변경을 조용히 덮고, 사용자는 자기 수정이 사라진 것만 봅니다.
- **해결 규칙은 데이터 종류마다 다르게 정합니다.**

| 규칙 | 적합한 데이터 |
| --- | --- |
| 마지막 쓰기 우선 | 설정 값, 단일 필드 토글 |
| 서버 우선 | 서버가 계산하는 값, 집계 결과 |
| 사용자에게 선택 요청 | 본문처럼 잃으면 안 되는 사용자 작성 데이터 |
| 필드 단위 병합 | 서로 다른 필드를 각각 수정하는 일이 흔한 데이터 |

- **사용자에게 선택을 요청하려면 두 버전을 모두 보관해야 합니다.** 로컬 변경을 서버 응답으로 즉시 덮어쓰는 구조에서는 선택 화면을 만들 수 없습니다. 규칙을 먼저 정하고 저장 구조를 맞춥니다.
- **삭제와 수정의 충돌을 따로 정합니다.** 한쪽에서 지운 항목을 다른 쪽에서 수정했을 때 되살릴지 버릴지 규칙이 필요합니다.
- 충돌이 실제로 일어나는 데이터인지 먼저 확인합니다. 한 사용자가 한 기기에서만 수정하는 데이터는 감지 수단만 두고 해결 규칙은 단순하게 유지해도 됩니다.

## 작업 흐름

1. **다루는 데이터와 요청을 나열합니다.** 추측하지 않고 실제 API 계약, 저장소 스키마, 요청 시작 지점을 읽습니다.
2. **데이터마다 출처를 하나로 정합니다.** 화면이 네트워크를 직접 보는지 로컬 저장소를 관찰하는지 명시합니다.
3. **요청을 읽기와 쓰기로 나눕니다.** 읽기에는 재시도와 캐시 정책을, 쓰기에는 중복 방지와 충돌 규칙을 배정합니다.
4. **저장할 데이터를 고르고 저장소를 배정합니다.** 저장하지 않기로 한 데이터도 이유와 함께 남깁니다.
5. **오프라인 지원 범위를 정합니다.** 읽기까지인지 쓰기까지인지에 따라 6번, 7번 항목을 검토할지가 결정됩니다.
6. **서버와 합의가 필요한 항목을 따로 모읍니다.** 멱등성 키, 변경분 조회, 삭제 표시, 버전 필드는 클라이언트 혼자 정할 수 없습니다. 합의 전이면 미결정으로 두고 무엇이 필요한지 적습니다.
7. **검증 시나리오를 씁니다.** 아래 표에서 이 데이터와 요청에 필요한 항목을 고릅니다.
8. **결정할 수 없는 항목은 미결정으로 남깁니다.** 무엇을 알면 결정할 수 있는지 함께 적습니다.
9. **코드 변경은 사용자 승인 후에 합니다.** 이 스킬의 산출물은 결정과 감사 결과입니다.

### 검증 시나리오

이 항목의 결정은 정상 경로에서 전부 통과합니다. 아래 조건을 만들어야 드러납니다.

| 시나리오 | 확인 방법 |
| --- | --- |
| 네트워크 없음 | 비행기 모드로 진입하고 조작 |
| 느린 응답 | 지연·대역 제한을 걸고 진입 |
| 서버 오류 | 5xx와 429 응답을 받게 하고 재시도 동작 관찰 |
| 연타와 재진입 | 전송 버튼 연타, 요청 중 화면 재진입 |
| 응답 유실 후 재시도 | 요청 전송 직후 연결을 끊고 다시 시도 |
| 오프라인 수정 후 복귀 | 비행기 모드에서 수정하고 연결을 되살림 |
| 동시 수정 | 다른 기기나 웹에서 같은 데이터를 수정 |
| 계정 전환 | 로그아웃 후 다른 계정으로 로그인 |

응답 유실 후 재시도는 중복 생성을 드러내는 유일한 시나리오입니다. 정상 응답만 받아 보면 멱등성 계약이 없어도 문제가 보이지 않습니다.
