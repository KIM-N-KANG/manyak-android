# 간편 제작 퍼널 이탈 개편 — 닫기·전 단계 이탈·키워드 임시 저장

> **KNK-1197 구조 이전 안내 (2026-09-05)** — 아래 모듈 경로·코드 예시·검증 명령은 작성 당시 기록입니다. 현재 소유 위치와 검증 결과는 [모듈 재구성 기록](./module-reorganization.md), 현재 계층·의존 규칙은 [하네스 모듈 아키텍처](../../../knk-harness/docs/planning/android-module-architecture.md)를 따릅니다.

- 공통 계약 정본: `../../../knk-harness/docs/product-specs/3-1-client.md` §3-1-4(이탈 가드·제작 임시 저장)
- 앱 결정 정본: `../../../knk-harness/docs/product-specs/3-3-android-app.md` §3-3-3(퍼널 구조)·§3-3-5(라이프사이클)
- 선행 계획: `create-funnel-recovery.md` — 이 계획이 그 문서의 D1·D3·D6을 대체한다

## 목표

- 퍼널 전 화면의 앱 바를 왼쪽 뒤로가기에서 **오른쪽 끝 닫기(X)**로 바꾼다.
- 닫기와 디바이스 뒤로가기를 같은 동작(퍼널 이탈 → 홈 복귀)으로 통일한다. 지금은 추가 정보 단계에서 둘 다 스토리라인 복귀다.
- 추가 정보 단계에서 이탈해도 선택 스토리라인·추천 선택·입력값을 그대로 재개할 수 있게 한다.
- "다시 선택하기"가 입력을 말없이 버리지 않도록 초기화 경고를 붙이고, 그 경로로 돌아오면 재개 지점도 스토리라인으로 되돌린다.
- 키워드 단계 입력을 임시 저장해 재개할 수 있게 한다(앱 전용 확장).
- 작성 중 변경을 300ms 디바운스로 계속 저장하고, 실제 저장 성공 여부를 퍼널 헤더에서 확인할 수 있게 한다.
- 진행 레코드 저장 수단을 Preferences DataStore에서 Room으로 옮긴다.

| --- | --- | --- |
| E1 | 퍼널 앱 바의 이탈 버튼은 오른쪽 끝 닫기(X, `ic_close` 재사용) | 어느 단계에서든 퍼널 전체를 종료하는 동작임을 익숙한 X로 명확히 드러낸다. 기존 단색 자산이 있어 새 자산은 만들지 않는다 |
| E2 | 이탈 지점은 퍼널 3개 목적지 전부 — 키워드·스토리라인·추가 정보 | 추가 정보 단계에서도 닫기·디바이스 뒤로가기가 홈 복귀여야 한다는 사용자 결정. §3-3-5의 "가드는 스토리라인 화면 한 곳"을 대체한다 |

| E4 | "다시 선택하기"는 추천 선택 또는 입력값이 있을 때 초기화 경고 다이얼로그를 거친다. 확정 시 추가 정보를 초기화하고 `selectedStorylineIndex`를 null로 되돌린 뒤 pop | 스토리라인을 다시 고르면 추천 목록이 달라져 기존 선택이 의미를 잃는다. 순번을 되돌려야 그 뒤의 이탈이 스토리라인 단계로 재개된다(E5) |
| E5 | 재개 지점은 `progress.selectedStorylineIndex` 유무로 가른다 — 있으면 추가 정보, 없으면 스토리라인 | 이미 있는 미러 값이 "추가 정보 단계에 도달했는가"를 그대로 표현한다. 별도 단계 필드를 두면 두 값이 갈라진다 |
| E6 | 퍼널 진입·이탈·단계 이동 모두 앱의 기존 공통 교차 페이드를 쓴다 | 퍼널만 위아래로 움직이는 별도 모션을 두지 않고 다른 전체 화면 이동과 같은 전환 문법을 유지한다 |
| E7 | 퍼널 전환용 `NavEntry.metadata`·방향 판정·전용 테스트를 제거한다 | 모든 화면이 같은 `rememberScreenTransition()`을 쓰므로 퍼널 여부를 구분할 상태와 분기가 더 이상 필요 없다 |
| E8 | 키워드 단계 임시 저장은 **앱 전용 확장**으로 두고 3-1은 고치지 않는다 | 레코드 슬롯은 플랫폼별로 분리돼 있어 웹과 충돌하지 않는다. 공용 계약 개정은 웹 구현 일정에 묶인다 |
| E9 | 키워드 임시 저장은 새 stage `KEYWORD_DRAFT` + `PendingStoryCreation.KeywordDraft`로 표현한다 | 기존 세 stage의 "생성 결과가 반드시 있다"는 불변식을 유지한다. 기존 `Draft`의 `generation`을 nullable로 만들면 스토리라인·추가 정보 전 경로가 null 분기를 떠안는다 |
| E10 | 키워드 스냅숏은 `StoryCharacterInput`을 재사용하지 않고 전용 타입을 둔다 | 커스텀 키워드는 선택을 해제해도 목록에 남는 `CustomTag(name, selected)` 상태다. 요청 페이로드용 `List<String>`으로는 편집 상태가 복원되지 않는다 |
| E11 | 키워드 입력은 마지막 변경 300ms 뒤 저장하고, 명시적 이탈은 대기 중 변경을 즉시 저장한다. 입력이 하나도 없으면 `KEYWORD_DRAFT`를 남기지 않고 소실 경고 없이 이탈한다. **입력 판정 기준은 선택 장르 태그·커스텀 장르 태그·주인공과 주변 인물의 이름·성별·특징 중 하나라도 비어 있지 않은 것**이며, 진입 시 놓인 빈 주변 인물 섹션 1개는 입력으로 세지 않는다 | 재실행 전 이탈 동작을 거쳐야만 저장하는 방식은 작성 도중 프로세스가 끝나면 입력을 잃는다. 300ms는 연속 입력마다 Room을 쓰지 않으면서 사용자가 다시 해야 할 작업을 작게 제한한다 |
| E12b | 키워드 스냅숏에 활성 카테고리 탭은 담지 않고 복원은 항상 첫 탭에서 시작한다 | 완료된 카테고리는 잠금이 풀려 있어 사용자가 바로 이동할 수 있다. 탭 위치까지 복원하면 저장할 상태만 늘고 복원 실패 시 잠긴 탭이 열린 것처럼 보일 수 있다 |
| E12c | 키워드 화면 ViewModel은 `PendingStoryCreationStore`를 직접 주입받아 저장·복원한다. 생성 스토어를 거치지 않는다 | 키워드 입력은 뒤 단계가 읽지 않아 단계 간 공유 상태가 아니다. 이미 함수 수 상한을 넘긴 생성 스토어에 무관한 책임을 더하지 않는다. 공유되는 규칙은 "진행 중 레코드 우선"(E12) 하나뿐이라 레코드 한 번 읽기로 충족된다 |
| E12 | 키워드 자동 저장은 진행 중 레코드(`STORYLINE_GENERATION`·`STORY_COMPLETION`)와 생성 결과(`STORY_DRAFT`)를 덮어쓰지 않는다 | 서버에서 실제로 돌고 있는 복구 대상과 이미 만든 결과가 키워드 편집 스냅숏보다 우선한다. 요청 단계 쓰기와 지연된 Draft 쓰기도 직렬화해 이전 단계가 늦게 덮지 않게 한다 |
| E13 | `KEYWORD_DRAFT`와 `STORY_DRAFT`는 복원해도 소비하지 않는다. 복원 대기 중에는 입력 미러링을 막고, 복원 뒤 변경분만 다시 저장한다 | 복원 직후 프로세스가 다시 끝나도 같은 저장본으로 재개할 수 있어야 한다. 화면에 한 번 읽었다는 사실은 사용자가 폐기를 확정했다는 뜻이 아니다 |
| E14 | 저장 수단은 Room 단일 행 테이블 `pending_story_creation`(`id` 고정 0) | 사용자 결정. 단일 슬롯 계약은 그대로 두고 수단만 바꾼다. 앞으로 Room이 필요한 저장소가 늘 것을 보고 기반을 먼저 깐다 |
| E15 | 컬럼은 `id`·`stage`만 정규화하고 페이로드는 `generationCommand`·`completionCommand`·`generation`·`progress`·`keywordSnapshot` 다섯 개의 nullable JSON 컬럼에 담는다. 타임스탬프 컬럼은 두지 않는다 | 슬롯이 1개라 조인할 대상이 없어 중첩 리스트까지 테이블로 쪼갤 이유가 없다. 기존 `PendingRecordDto`의 최상위 필드와 1:1로 대응시켜 직렬화 코드를 재사용한다. TTL은 3-1에서 범위 밖이고 정렬할 행도 없어 타임스탬프를 읽을 곳이 없다 |
| E16 | 스키마를 export하고 마이그레이션은 파괴적 폴백을 쓴다 | 진행 레코드는 재생성 가능한 스냅숏이고, 현행 스토어도 "해석 불가 = 없음"으로 폐기한다. 같은 규칙을 DB 수준에서 유지한다 |
| E17 | 기존 DataStore 레코드는 옮기지 않고 폐기하며, `pending_creation` DataStore 파일 삭제를 정리 코드에 넣는다 | 미출시 단계의 진행 스냅숏이라 이관 가치가 없다. 파일을 남기면 쓰는 곳 없는 사용자 귀속 데이터가 기기에 남는다 |
| E18 | 홈 배너의 닫기(X)를 두지 않는다. 사용 가능한 임시 저장본은 FAB 진입 다이얼로그의 "새로 만들기"·완성 후 채팅 진입 성공·로그아웃에서만 폐기한다. 새 요청 단계는 같은 단일 슬롯을 덮어쓴다 | 화면 복원은 폐기 의사가 아니다. 배너의 X도 확인 없이 만들던 스토리를 버리므로 두지 않고, 사용자가 확정한 종료 경로에 폐기를 모은다. 생성 결과가 전혀 없는 확정적 요청 실패 레코드는 재개할 내용이 없어 예외적으로 정리한다 |
| E19 | 생성·완성 요청 단계는 API 호출 전에 즉시 저장하고, 스토리라인 생성 성공은 곧바로 `STORY_DRAFT`로 저장한다. 활성·선택 스토리라인과 추가 정보 변경은 마지막 변경 300ms 뒤 저장하며 이탈 시 즉시 플러시한다 | 생성 결과가 메모리에만 있는 시간을 없앤다. 자동 저장과 요청 단계 저장을 한 순서로 직렬화해야 지연된 `STORY_DRAFT`가 `STORYLINE_GENERATION`·`STORY_COMPLETION`을 덮지 않는다 |
| E20 | 퍼널 헤더의 닫기 버튼 왼쪽에 임시 저장 pill 뱃지를 둔다. 편집 직후부터 Room 쓰기가 끝날 때까지는 `{colors.background-neutral}` 배경과 `{colors.text-subtle}` 글자의 `임시 저장중`, 현재 스냅숏 쓰기 성공 뒤에는 브랜드 subtle 배경과 브랜드 글자의 `임시 저장됨`을 표시한다. 저장할 내용이 없거나 쓰기가 실패하면 숨긴다 | 입력 때마다 뱃지가 사라지면 자동 저장이 동작하는지 알 수 없다. 저장 중과 완료를 색·문구로 구분하고 같은 위치를 유지하되, 메모리 반영을 저장 완료처럼 표시하지는 않는다 |
| E21 | 퍼널 이탈 시 `스토리가 임시 저장되었어요` 토스트를 표시하지 않는다. 저장 여부는 헤더 뱃지로만 알린다 | 이탈과 동시에 사라지는 화면의 저장 상태를 토스트로 다시 반복할 필요가 없고, 자동 저장이 이미 완료된 경우에도 이탈 시점의 새 저장처럼 보일 수 있다 |

## 구현 단계

0. 하네스 §3-3-3·§3-3-5 결정 갱신(구현 전 선행)과 `create-funnel-recovery.md` 대체 표기.
1. `core:domain` — `PendingStoryCreation.KeywordDraft`와 키워드 스냅숏 타입, `CreationResumePoint.KeywordStep`, `resumePoint()` 분기.
2. `core:data` — Room 도입(버전 카탈로그·의존성·스키마 export), `ManyakDatabase`·엔티티·DAO·TypeConverter, `PendingStoryCreationRoomStore`(+`UserScopedStore` 바인딩), 기존 DataStore 스토어 제거와 파일 정리. (1 이후)
3. `core:ui` — `create_close_funnel` 문자열.
4. `feature:create` — `CreateFunnelHeader` 앱 바 교체, 키워드 VM 저장·복원, 추가 정보 VM 이탈·초기화 경로, 생성 스토어의 추가 정보 진행 초기화, 초기화 경고 다이얼로그. (1·3 이후, 5와 병렬 가능)
5. `app` — 퍼널 전용 전환 없이 공통 교차 페이드 사용, 추가 정보 이탈 배선, `KeywordStep` 재개 체인.
6. 단위 테스트와 정적 검사.
7. 후속 저장 안정화 — 300ms 자동 저장, 비소비 복원, 생성 성공 즉시 `STORY_DRAFT`, 저장 성공 뱃지, 요청 단계와 지연 저장의 직렬화.

## 검증

- 태그: `state-restore`(키워드·추가 정보 재개 복원), `session-cleanup`(Room 테이블이 사용자 귀속 정리에 참여), `idempotent-write`·`race-condition`(요청 단계와 300ms 지연 저장의 우선순위)
- 단위 테스트: `resumePoint()` 분기, 키워드 VM 299ms/300ms 저장 경계·비소비 복원·저장 실패 표시, 생성 성공 즉시 Draft·진행 변경 디바운스, 추가 정보 VM 이탈 저장·초기화 후 순번 null, Room 스토어 읽기·쓰기 성공 결과·삭제·`clearUserData`.
- 수동 검증: 각 단계 헤더의 닫기(X)와 공통 교차 페이드, 이탈 후 배너 재개 지점, 프로세스 재시작 후 재개, 로그아웃 후 레코드 삭제.
