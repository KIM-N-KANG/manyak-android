# 안정성·품질·성능

## 범위 선택

요청과 직접 관련된 모드만 봅니다.

| 요청 | 모드 |
| --- | --- |
| 로딩·빈 상태·오류 UX | 실패와 복구 |
| 중복 실행·응답 순서 문제 | 경쟁 상태 |
| 무엇을 테스트할지 | 테스트 전략 |
| 느림·메모리·배터리 문제 | 성능 |
| 크래시·ANR·실패 추적 | 관측 |

한 모드 때문에 나머지 모드를 모두 검토하지 않습니다.

## 실패와 복구

- 오류는 기술 원인보다 사용자가 취할 수 있는 행동으로 화면에 매핑합니다.
- 재시도, 입력 수정, 로그인, 다른 경로 중 가능한 복구 수단을 제공합니다.
- 기존 콘텐츠를 유지할지 비울지와 작성 중 입력 보존을 정합니다.
- 부분 실패를 성공처럼 표시하지 않고 막다른 화면을 남기지 않습니다.

## 경쟁 상태

- 버튼 연타, 화면 이탈, 자동·수동 재시도 중첩, 응답 순서 역전 중 실제 가능한 경로만 확인합니다.
- 최신 요청만 유효한 흐름과 모든 결과를 반영해야 하는 흐름을 구분합니다.
- UI 비활성화만 중복 방지 수단으로 의존하지 않습니다.

## 테스트 전략

되돌릴 수 없는 동작, 인증·세션, 데이터 변환, 오류 분기를 우선합니다. 단순 표시와 프레임워크가 보장하는 동작은 낮은 우선순위로 둡니다. 자동화 가능한 검증을 수동 시나리오로 남기지 않습니다.

## 성능과 관측

- 성능은 실제 문제가 있거나 목표가 필요한 경로만 측정하고 측정 전 수치를 임의로 만들지 않습니다.
- 원인을 측정한 뒤 변경하고 같은 조건으로 다시 측정합니다.
- 크래시·ANR·주요 실패는 버전별로 추적 가능해야 하며 로그에 민감 정보를 넣지 않습니다.
- 의도적 크래시나 저사양 릴리스 측정은 관측·성능 작업 또는 릴리스에서만 수행합니다.

## 결과

선택한 모드의 결정과 `android-change-verification`에 넘길 위험 태그만 보고합니다. 모드에 따라 `failure-recovery`, `race-condition`, `performance`, `observability` 중 해당하는 것만 사용합니다. 이 스킬에서 검증을 직접 실행하지 않습니다.
