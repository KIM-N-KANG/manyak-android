# 상태·생명주기

## 목적

안드로이드 앱 개발 고려 사항 8개 항목 중 2번 **상태·생명주기**를 담당합니다. 아래 6개 결정 항목을 각각 명시적으로 결정하거나, 기존 코드가 이미 내린 결정을 확인하고 위반을 지적합니다.

| 결정 항목 | 결정할 내용 |
| --- | --- |
| 1. 리컴포지션 유지 상태 | 리컴포지션 사이에 어떤 상태를 유지할지, 상태를 어디에 둘지 |
| 2. Activity 재생성 복원 상태 | 구성 변경 후 어떤 상태를 복원할지 |
| 3. 프로세스 종료 복원 상태 | 프로세스가 죽은 뒤에도 복원해야 하는 상태가 무엇인지 |
| 4. 대상별 보존 방식 | 입력값·스크롤·탭·네비게이션 상태를 어떻게 보존할지 |
| 5. 비동기 작업 취소 범위 | 화면을 벗어났을 때 작업을 취소할지 유지할지 |
| 6. 앱 종료 후 완료 작업 | 앱이 종료되어도 완료되어야 하는 작업을 어떻게 처리할지 |

핵심 판단 질문은 하나입니다. **이 상태를 잃으면 사용자가 무엇을 다시 해야 하는가.** 사용자가 직접 만든 것(타이핑, 선택, 진행 중인 전송)은 살리고, 서버에서 다시 받을 수 있는 것은 살리지 않습니다. 이 질문에 답하지 않고 저장소를 먼저 고르면 과하게 저장하거나 필요한 것을 잃습니다.

## 적용 범위 판단

요청 규모에 맞는 항목만 검토합니다.

| 요청 | 검토할 항목 |
| --- | --- |
| 새 화면·플로우 설계, 상태 처리 리뷰·감사 | 1~6 전부 |
| 값이 사라지는 문제 진단 | 1, 2, 3, 4 |
| 상태를 어디에 둘지 판단 | 1, 4 |
| 비동기 작업·업로드·동기화 추가 | 5, 6 |

## 상태 수명과 저장소

모든 결정 항목이 이 표를 기준으로 판단됩니다. 상태마다 필요한 수명을 먼저 정하고, 그 수명에 맞는 저장소를 고릅니다.

| 필요한 수명 | 저장소 | 잃는 시점 |
| --- | --- | --- |
| 리컴포지션 사이 | `remember` | 컴포지션 이탈, 구성 변경 |
| 구성 변경까지 | ViewModel | 프로세스 종료 |
| 프로세스 종료까지 | `rememberSaveable`, ViewModel의 `SavedStateHandle` | 사용자가 직접 종료, 시스템이 상태를 버릴 만큼 오래 방치 |
| 앱 재실행 이후까지 | DataStore, 로컬 DB, 파일 | 앱 삭제, 명시적 삭제 |

`rememberSaveable`과 `SavedStateHandle`은 같은 저장 메커니즘을 씁니다. 프로세스가 죽어도 복원되지만 용량이 작고, 큰 데이터를 넣으면 `TransactionTooLargeException`으로 앱이 죽습니다. 식별자와 사용자 입력 원문 같은 작은 값만 넣습니다.

- **결정이 있으면 다시 결정하지 않습니다.** 결정을 읽고, 이 요청의 코드가 그것을 지키는지만 봅니다. 어긋나면 위반으로 보고합니다. 결정 자체를 바꿔야 하면 이유와 함께 `_project.md`를 갱신합니다.
- **결정이 없으면 여기서 정하고 그 결과를 `_project.md`에 남깁니다.** 남기지 않으면 다음 기능이 같은 결정을 처음부터 다시 하고, 기능마다 구조가 갈립니다.

이 문서를 이미 읽었다면 다시 열지 않고 그 내용을 씁니다.

| 구분 | 항목 |
| --- | --- |

## 결정 항목별 판단 기준

### 1. 리컴포지션 유지 상태

- **상태 위치**: 화면 전체의 상태와 데이터 요청 결과는 상태 홀더(ViewModel)에 둡니다. 그 컴포저블 안에서만 의미 있는 UI 상태(펼침 여부, 다이얼로그 표시, 애니메이션 진행)는 컴포저블 로컬에 둡니다. 로컬에 두어도 되는 상태를 전부 ViewModel로 올리면 화면 상태가 커지고 갱신 이유를 추적하기 어려워집니다.
- **상태 홀더 범위**: 상태 홀더를 화면 하나에 묶을지 여러 화면이 공유할지 정합니다. 기본은 화면 단위입니다. 여러 단계 폼처럼 화면을 넘나들며 이어지는 상태는 그 흐름을 감싸는 범위에 묶고 흐름이 끝나면 함께 사라지게 합니다. Activity 범위로 올리면 앱이 살아 있는 동안 값이 남아 다음 진입에 이전 입력이 되살아납니다.
- **`remember` 키**: 입력에 따라 달라지는 계산을 `remember`로 캐시할 때 키를 반드시 명시합니다. 키를 빼면 입력이 바뀌어도 이전 값이 남습니다.
- **상태 노출 형태**: 화면 상태를 단일 `UiState`로 노출할지, 성격이 다른 상태를 나눠 노출할지 결정합니다. 단일 상태는 여러 값이 함께 바뀌어야 할 때 어긋난 조합을 막아 줍니다. 자주 바뀌는 값(입력 중인 텍스트, 스크롤)은 나눠 두는 편이 불필요한 리컴포지션을 줄입니다.
- **파생 상태**: 다른 상태에서 계산할 수 있는 값을 별도 상태로 두지 않습니다. 두 개를 따로 두면 동기화가 어긋납니다.
- 상태 홀더에 Context, View, Activity 참조를 담지 않습니다. 생명주기가 다른 객체를 붙잡으면 재생성 시 누수가 됩니다.

### 2. Activity 재생성 복원 상태

- **구성 변경 트리거**: 화면 회전, 다크 모드 전환, 시스템 폰트 크기 변경, 언어 변경, 분할 화면 진입, 폴더블 접기·펴기. 하나만 검증하고 전부 통과했다고 보지 않습니다. 레이아웃 대응은 고려 사항 6번 항목(디바이스·다국어·접근성) 스킬에서 함께 봅니다.
- **기본 선택은 ViewModel입니다.** 화면 상태를 상태 홀더로 올리면 구성 변경은 별도 처리 없이 넘어갑니다.
- **컴포저블 로컬 상태는 `rememberSaveable`로 둡니다.** 저장 가능한 타입이 아니면 Saver를 정의하거나, 애초에 상태 홀더로 올릴 상태인지 다시 판단합니다.
- **화면 진입 요청의 재실행 방지**: 진입 시 시작하는 요청을 컴포지션에서 조건 없이 시작하면 회전할 때마다 같은 요청이 다시 나갑니다. 요청 시작 지점을 상태 홀더에 두고 한 번만 실행되게 합니다.
- **일회성 이벤트를 상태 필드로 두지 않습니다.** 스낵바 표시, 화면 이동, 토스트를 상태로 남기면 구성 변경 후 다시 실행됩니다. 소비 후 즉시 지우거나 이벤트 전달 경로를 따로 두는 방식 중 하나를 정합니다.

### 3. 프로세스 종료 복원 상태

- **ViewModel은 프로세스 종료에서 살아남지 않습니다.** 살아남는 것은 `rememberSaveable`, `SavedStateHandle`, 영속 저장소뿐입니다. 구성 변경만 통과하는 구현을 상태 복원이 끝났다고 보고하지 않습니다.
- **판단 기준**: 사용자가 앱을 다시 열었을 때 무엇을 다시 해야 하는가. 다시 스크롤만 하면 되는 상태는 잃어도 됩니다. 다시 타이핑해야 하는 상태는 살립니다.
- **화면 위치 복원**: 네비게이션 백스택은 시스템이 복원합니다. 대신 각 화면이 복원에 필요한 인자를 라우트에 가지고 있어야 합니다. 화면이 메모리에만 있던 값에 의존하면 복원 후 빈 화면이 됩니다.
- **서버에서 다시 받을 수 있는 데이터는 저장하지 않고 다시 요청합니다.** 캐시로 대신할지는 고려 사항 3번 항목(데이터·네트워크·동기화) 스킬에서 결정합니다.
- **사용자가 직접 종료한 경우와 시스템이 죽인 경우를 구분합니다.** 사용자가 앱을 스와이프로 닫은 뒤에도 진행 중이던 화면과 입력을 그대로 되살리면 사용자가 예상하지 못할 수 있습니다. 되살릴 대상을 명시적으로 정합니다.

### 4. 대상별 보존 방식

| 상태 | 기본 선택 | 판단 근거 |
| --- | --- | --- |
| 입력 중인 텍스트 | `rememberSaveable` 또는 `SavedStateHandle` | 잃으면 사용자가 다시 타이핑해야 함 |
| 여러 단계 폼의 진행 상태 | `SavedStateHandle`, 며칠 뒤 이어 쓰기를 지원하면 영속 저장소 | 재입력 비용이 큼 |
| 목록 스크롤 위치 | 기본 제공 리스트 상태 기억 함수 | 저장 동작이 이미 들어 있어 따로 감쌀 필요가 없음 |
| 선택된 탭 | 네비게이션 상태로 표현 | 탭이 라우트면 백스택 복원에 함께 실림 |
| 펼침·접힘, 다이얼로그 표시 | 컴포저블 로컬 `rememberSaveable` | 화면 밖에서 의미 없음 |
| 검색어와 필터 조건 | `SavedStateHandle` | 재요청 조건이라 복원해야 결과가 같아짐 |
| 서버에서 받은 목록·상세 | 저장하지 않고 재요청 | 다시 받을 수 있음 |
| 로그인 여부와 토큰 | 보안 저장소 | 고려 사항 4번 항목 스킬에서 결정 |

- **스크롤 위치는 저장해도 목록 데이터가 없으면 복원되지 않습니다.** 복원 직후 데이터를 다시 받아오는 화면은 데이터가 도착하기 전에 위치가 초기화됩니다. 목록을 받은 뒤 위치를 적용할지, 데이터가 준비될 때까지 목록을 그리지 않을지 정합니다.
- **탭 전환 시 각 탭 상태를 보존할지는 고려 사항 1번 항목(앱 구조) 스킬의 백스택 규칙과 같은 결정입니다.** 두 곳에 다르게 적으면 구현이 갈립니다. 한쪽에서 정하고 다른 쪽은 참조합니다.
- 화면을 벗어났다 돌아왔을 때 상태를 유지할지 초기화할지도 결정에 넣습니다. 목록 필터는 보통 유지하고, 완료된 폼은 초기화합니다.

### 5. 비동기 작업 취소 범위

- **기본은 화면 수명에 묶습니다.** 읽기 요청은 화면이 사라지면 취소되는 스코프에서 시작합니다. 취소되지 않는 스코프로 화면 작업을 시작하면 결과를 받을 상태 홀더가 이미 사라져 있습니다.
- **UI가 보이지 않을 때 수집을 멈춥니다.** 백그라운드에서 계속 수집하면 배터리와 데이터를 씁니다. 멈추면 안 되는 흐름이 있다면 그 이유를 결정에 적습니다.
- **취소하면 안 되는 작업**: 사용자가 확정한 쓰기 작업(전송, 저장, 결제, 업로드)입니다. 화면 수명이 아니라 앱 또는 시스템 수명에 묶어야 하므로 6번 결정 항목으로 넘깁니다.
- **취소는 요청 자체를 되돌리지 않습니다.** 이미 서버에 도달한 요청은 클라이언트가 취소해도 서버에서 완료됩니다. 중복 방지와 멱등성은 고려 사항 3번 항목 스킬에서 결정합니다.
- **재진입 시 중복 실행을 막을지 정합니다.** 같은 요청이 화면 재진입마다 다시 나가도 되는지, 진행 중이면 무시할지, 최신 요청만 남길지 결정합니다.

### 6. 앱 종료 후 완료 작업

- **판단 기준**: 사용자가 앱을 닫아도 끝나야 하는가, 실패하면 재시도해야 하는가, 네트워크나 충전 같은 실행 조건이 필요한가. 하나라도 해당하면 지속 작업 스케줄러(WorkManager)로 옮깁니다.
- 화면 수명 코루틴으로 처리하면 안 되는 대표 작업: 파일·이미지 업로드, 대기 중인 전송, 서버 동기화, 지연 전송 로그.
- **재시도 정책을 결정에 포함합니다**: 백오프 방식, 최대 재시도 횟수, 최종 실패 시 사용자에게 알릴지.
- **중복 실행 방지**: 고유 작업 이름을 정하고 이미 예약된 작업이 있을 때 유지할지 교체할지 결정합니다. 같은 작업이 여러 번 예약되면 서버에 중복 요청이 갑니다.
- **진행 상태를 UI에 보일지 정합니다.** 보여야 하면 작업 상태를 관찰해 화면에 반영하는 경로를 만들고, 보일 필요가 없으면 조건(네트워크 연결, 충전 중)에만 붙입니다.
- 정확한 시각 실행, 알람, 사용자가 보는 중 계속 진행해야 하는 작업은 요건이 다릅니다. 배터리 최적화 제한과 필요한 권한을 함께 확인하고, 스케줄러로 대체할 수 있는지 먼저 판단합니다.

## 작업 흐름

1. **대상 화면과 작업을 나열합니다.** 추측하지 않고 실제 상태 홀더, 컴포저블 로컬 상태, 시작되는 비동기 작업을 읽습니다.
2. **상태 목록을 만들고 각 상태에 "잃으면 사용자가 무엇을 다시 해야 하는가"를 적습니다.** 이 답이 수명을 결정합니다.
3. **수명에 맞는 저장소를 배정합니다.** 수명보다 오래 사는 저장소를 고르면 오래된 값이 되살아나고, 짧으면 사용자가 다시 입력합니다.
4. **비동기 작업마다 취소 범위를 배정합니다.** 화면 수명, 앱 수명, 시스템 수명 중 하나로 명시합니다.
5. **검증 시나리오를 씁니다.** 아래 표를 기준으로 이 화면에 필요한 항목을 고릅니다.
6. **결정할 수 없는 항목은 미결정으로 남깁니다.** 무엇을 알면 결정할 수 있는지 함께 적습니다.
7. **코드 변경은 사용자 승인 후에 합니다.** 이 스킬의 산출물은 결정과 감사 결과입니다.

### 검증 시나리오

| 시나리오 | 확인 방법 | 검증 대상 |
| --- | --- | --- |
| 구성 변경 | 화면 회전, 다크 모드·폰트 크기·언어 변경 | 2번 결정 항목 |
| Activity 파괴 | 개발자 옵션의 Activity 유지 안 함 | 컴포저블 로컬 상태 복원 |
| 프로세스 종료 | 백그라운드로 보낸 뒤 프로세스를 강제 종료하고 복귀 (`adb shell am kill <패키지>`) | 3번 결정 항목 |
| 사용자 직접 종료 | 최근 앱에서 스와이프로 닫고 재실행 | 되살릴 상태와 초기화할 상태 구분 |
| 화면 이탈 중 요청 진행 | 요청 중 뒤로 가기, 홈으로 이동 | 5번 결정 항목 |
| 작업 중 앱 종료 | 업로드·전송 중 앱 종료 후 재실행 | 6번 결정 항목 |

개발자 옵션의 Activity 유지 안 함은 Activity 파괴만 재현합니다. 프로세스 종료 복원은 따로 확인합니다.
