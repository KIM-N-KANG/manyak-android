# 세션 데이터 정리

## 목적

고려 사항 4번 항목 **인증·보안·개인정보**에서 갈라져 나온 작업 스킬입니다. 고려 사항 스킬이 정책을 결정한다면 이 스킬은 저장소를 탐색합니다.

| 하는 일 | 내용 |
| --- | --- |
| 탐색 | 사용자 귀속 데이터가 남는 지점을 저장소 전체에서 찾습니다 |
| 대조 | 찾은 지점이 현재 정리 경로에 포함되어 있는지 확인하고 누락을 지적합니다 |
| 계약 | 기능이 늘어도 정리가 새지 않는 참여 구조를 설계합니다 |
| 검증 | 정리가 멱등하고, 일부 실패에 견디고, 끝난 뒤 되살아나지 않는지 확인합니다 |

세션 정책 자체는 여기서 정하지 않습니다. 멀티 디바이스 동시 로그인 허용 여부, 탈퇴의 복구 가능 기간과 서버 삭제 시점, 원격 로그아웃 제공 여부는 고려 사항 4번 항목 스킬에서 서버와 함께 결정합니다. 이 스킬은 **무엇을 지울지와 어떻게 지울지**를 다룹니다.

## 선행 전제: 정리 대상은 기능이 늘 때마다 늘어납니다

한 번 만든 삭제 목록은 다음 기능에서 이미 낡습니다. 새 화면이 설정 값을 하나 저장하고, 새 SDK가 사용자 식별자를 하나 잡고, 새 작업이 큐에 하나 쌓이면 그때마다 목록에서 빠집니다. 여기서 두 가지 규칙이 나옵니다.

- **목록을 기억하지 않고 매번 다시 훑습니다.** 지난번에 만든 목록을 그대로 쓰면 그 이후에 생긴 저장 지점은 영원히 발견되지 않습니다. 이 스킬의 산출물은 결정이 아니라 이번 시점의 탐색 결과입니다.
- **목록을 유지하는 대신 참여를 강제합니다.** 사람이 목록을 갱신하는 방식은 반드시 실패합니다. 새 저장 지점이 정리 계약에 참여하지 않으면 눈에 띄도록 만드는 편이 낫습니다.

정리 누락은 개발 중에 드러나지 않습니다. 한 계정만 쓰면 잔여 데이터가 보이지 않기 때문입니다. 사고는 사용자가 계정을 바꾸는 순간 처음 나타납니다.

## 적용 범위 판단

| 요청 | 하는 일 |
| --- | --- |
| 로그아웃·탈퇴·계정 전환을 처음 구현 | 전체 탐색 + 정리 계약 설계 + 실행 규칙 |
| 사용자 데이터를 저장하는 기능 추가 | 그 기능의 저장 지점이 계약에 참여했는지만 확인 |
| 새 저장소·SDK 도입 | 사용자 귀속인지 판단하고 계약 참여 여부 확인 |
| 계정 전환 후 이전 데이터가 보이는 문제 | 전체 탐색 + 검증 시나리오 |
| 로그아웃 후에도 알림·동기화가 계속되는 문제 | 지속 작업 큐, 푸시 등록, 메모리 상태 |

## 이미 결정된 항목

**정리 계약의 구조**는 프로젝트에서 한 번 정하면 그대로 적용되므로 `docs/plans/_project.md`를 먼저 확인합니다. 결정이 있으면 다시 설계하지 않고 새 저장 지점이 그 계약을 따르는지만 봅니다. 없으면 여기서 정하고 문서에 남깁니다.

**정리 대상 목록은 프로젝트 결정이 아닙니다.** 문서에 적어 두고 재사용하지 않고 매번 탐색합니다. 위 선행 전제가 그 이유입니다.

## 탐색 대상

아래를 저장소 전체에서 찾습니다. **찾지 못했으면 "없음"으로 적지 말고 어디를 확인했는지 적습니다.** 확인하지 않은 것과 없는 것은 다릅니다.

| 대상 | 어디를 보는가 | 놓쳤을 때 |
| --- | --- | --- |
| 키-값 저장소의 사용자별 값 | DataStore·SharedPreferences 키 정의 전체 | 이전 계정의 설정이 새 계정에 적용됩니다 |
| 로컬 DB의 사용자 귀속 테이블 | 엔티티 목록에서 사용자에 매인 것 | 이전 계정의 목록이 그대로 보입니다 |
| 파일·이미지 캐시와 내려받은 파일 | 캐시 디렉터리, 이미지 로더 캐시, 다운로드 경로 | 이전 계정의 사진이 새 계정 화면에 뜹니다 |
| 메모리 상태 | Singleton, 인메모리 캐시, 앱 범위 상태 홀더 | 앱을 재시작하기 전까지 이전 값이 남습니다 |
| DI의 세션·계정 스코프 | 스코프 정의와 그 안에 사는 객체 | 스코프를 끊지 않으면 위 메모리 상태가 전부 살아 있습니다 |
| 지속 작업 큐 | WorkManager 등에 등록된 사용자별 작업 | 로그아웃 후에도 이전 계정 데이터를 올리거나 내려받습니다 |
| 푸시 등록 토큰과 사용자 매핑 | 등록·해제 호출 지점, 서버 매핑 | 로그아웃한 기기로 이전 사용자의 알림이 계속 갑니다 |
| WebView 쿠키와 외부 로그인 세션 | WebView 쿠키 저장소, 외부 제공자 SDK의 세션 | 다시 로그인할 때 이전 계정으로 자동 진입합니다 |
| 분석·크래시 도구의 사용자 식별자 | 각 SDK의 식별자 설정 호출 지점 | 새 계정의 행동과 오류가 이전 사용자에게 기록됩니다 |

푸시 등록 해제는 고려 사항 5번 항목 스킬의 등록 토큰 결정과 같은 자리입니다. 지속 작업 큐의 수명과 취소 범위는 고려 사항 2번 항목 스킬에서 정한 규칙을 따릅니다.

## 정리 계약

- **각 도메인이 로그아웃 코드를 직접 부르지 않게 합니다.** 로그아웃 처리 지점이 모든 저장소를 알아야 하는 구조면, 새 저장소를 추가한 사람이 그 지점을 고치는 것을 잊는 순간 새 데이터가 남습니다. 각 저장소가 자기 정리 방법을 제공하고 공통 정리기가 그것들을 호출하는 방향이 낫습니다.
- **참여하지 않은 저장 지점이 드러나게 합니다.** 계약에 등록하지 않으면 그냥 조용히 빠질 뿐이라면 계약은 목록과 다를 게 없습니다. 저장소를 만드는 자리에서 참여를 요구하거나, 참여하지 않은 것을 찾는 검사를 두는 방법을 정합니다.
- **정리 범위를 두 가지로 나눕니다.** 로그아웃은 사용자 귀속 데이터를 지우고, 탈퇴는 거기에 더해 서버 삭제 요청과 그 진행 상태를 다룹니다. 계정 전환은 로그아웃 후 로그인으로 처리하되 두 계정 사이에 아무것도 넘어가지 않는지 확인합니다.
- **지우지 않을 것도 명시합니다.** 언어 설정, 테마, 온보딩 완료 여부처럼 기기에 속하고 사용자에 속하지 않는 값은 남깁니다. 명시하지 않으면 전부 지우거나 전부 남기는 쪽으로 흐릅니다.

## 실행 규칙

- **정리는 여러 번 실행되어도 안전해야 합니다.** 로그아웃 중 앱이 죽어 다시 시도되는 경우, 서버 세션 만료와 사용자 로그아웃이 겹치는 경우가 실제로 생깁니다. 이미 지운 것을 다시 지우려 할 때 예외가 나면 나머지 정리가 중단됩니다.
- **일부 실패가 나머지를 막지 않게 합니다.** 캐시 파일 하나를 지우지 못했다고 토큰이 남으면 최악입니다. 각 정리를 독립적으로 실행하고 실패한 것만 모아 보고합니다.
- **서버 호출 실패와 무관하게 로컬은 지웁니다.** 네트워크가 없다고 로그아웃이 막히면 사용자는 기기를 넘겨줄 수 없습니다.
- **정리 중 새 데이터가 들어오지 못하게 막습니다.** 지우는 동안 살아 있던 작업이 응답을 받아 다시 저장하면 정리가 끝난 뒤 데이터가 되살아납니다. 진행 중인 작업을 먼저 취소하고, 취소가 확인된 뒤에 지웁니다.
- **토큰을 지우는 시점을 정합니다.** 서버 로그아웃 호출에 토큰이 필요하므로 호출 전에 지우면 서버 세션이 남습니다. 호출 후에 지우면 호출이 오래 걸리는 동안 인증된 요청이 나갈 수 있습니다. 어느 쪽을 택했는지 적습니다.
- **정리가 끝나기 전에는 인증이 필요한 화면으로 돌아가지 못하게 합니다.** 중간 상태에서 화면이 살아 있으면 빈 목록이나 오류가 사용자에게 보입니다.

## 작업 흐름

1. **위 탐색 대상 아홉 줄을 하나씩 훑습니다.** 추측하지 않고 실제 키 정의, 엔티티 목록, SDK 초기화 지점을 읽습니다. 확인한 위치를 함께 적습니다.
2. **찾은 저장 지점을 현재 정리 경로와 대조합니다.** 정리 경로가 없으면 이 단계가 곧 첫 목록이 됩니다.
3. **누락을 지적합니다.** 각 누락에 대해 그것이 남았을 때 사용자에게 무엇이 보이는지 함께 적습니다. 목록만 주면 우선순위를 매길 수 없습니다.
4. **정리 계약을 설계하거나 기존 계약 위반을 지적합니다.** 새 저장 지점이 참여하지 않은 채 추가되었다면 그것이 위반입니다.
5. **실행 규칙을 하나씩 확인합니다.** 멱등성, 부분 실패 격리, 취소 후 삭제 순서, 토큰 삭제 시점.
6. **지우지 않을 항목을 명시적으로 적습니다.**
7. **검증 시나리오를 씁니다.** 아래 표에서 이번 변경에 필요한 항목을 고릅니다.
8. **결정할 수 없는 항목은 미결정으로 남기고, 코드 변경은 사용자 승인 후에 합니다.**

### 검증 시나리오

| 시나리오 | 확인 방법 |
| --- | --- |
| 계정 전환 잔여 | 계정 A로 데이터를 만들고 로그아웃 후 계정 B로 로그인 |
| 두 번 정리 | 로그아웃을 연속으로 두 번 실행하거나 정리 중 앱을 죽이고 재실행 |
| 부분 실패 | 정리 대상 하나를 실패하게 만든 상태로 로그아웃 |
| 오프라인 로그아웃 | 비행기 모드에서 로그아웃 |
| 작업 되살아남 | 업로드나 동기화가 진행 중인 상태에서 로그아웃 |
| 로그아웃 후 알림 | 로그아웃한 기기로 이전 계정 알림을 보내 봄 |
| 재로그인 자동 진입 | 로그아웃 후 외부 제공자로 다시 로그인 |
| 크래시 귀속 | 계정 전환 후 크래시를 일으켜 기록된 사용자 확인 |
| 기기 설정 보존 | 로그아웃 후 언어·테마가 유지되는지 확인 |

계정 전환 잔여와 크래시 귀속은 한 계정만 쓰는 개발 중에는 드러나지 않습니다. 두 계정을 번갈아 쓰는 확인을 반드시 포함합니다.
