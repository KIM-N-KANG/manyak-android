# 변경 검증

## 원칙

- 실행하지 않은 검증을 통과로 보고하지 않습니다.
- 검증 비용은 변경 위험에 비례해야 합니다.
- 영역 스킬은 위험과 완료 조건을 전달하고, 실제 실행은 이 스킬이 담당합니다.
- 문서·스킬만 바뀐 경우 Android Gradle 작업을 돌리지 않습니다.

## 검증 단계

| 단계 | 기본 사용 시점 | 범위 |
| --- | --- | --- |
| 로컬 집중 | 구현 중·구현 직후 | 변경된 모듈의 직접 관련 테스트 또는 가장 작은 컴파일 작업 |
| CI | PR | 저장소 CI가 정의한 전체 정적 검사·테스트·패키징 |
| 수동 | 자동화할 수 없는 변경 완료 | 변경된 화면·흐름의 위험 항목만 |
| 릴리스 | 출시 준비 또는 명시적 요청 | 릴리스 빌드, 호환성, 운영 설정과 기기 매트릭스 |

PR에서 CI가 `check`와 `assembleDebug`를 실행한다면 같은 전체 작업을 로컬에서 자동으로 반복하지 않습니다. 사용자가 로컬 전체 검증을 요청했거나, CI를 사용할 수 없어 같은 게이트를 재현해야 하거나, 공통 빌드 로직 변경을 한정 작업으로 확인할 수 없을 때만 전체 작업을 실행합니다.

## 선택 기준

먼저 `git status --short`와 diff를 확인하고 실제 Gradle 구성과 CI 워크플로에서 사용 가능한 작업을 읽습니다.

| 변경 | 로컬 기본값 |
| --- | --- |
| 문서·스킬 | frontmatter, 링크, 참조와 전용 validator |
| 순수 Kotlin 로직 | 관련 테스트 클래스 또는 모듈 단위 테스트 |
| 상태·코루틴 | 바뀐 상태 전이·취소 경로 테스트 |
| Compose | 변경 모듈 컴파일, 영향받은 UI 테스트가 있으면 해당 테스트 |
| 문자열·일반 리소스 | 해당 모듈의 가장 작은 resource 처리·컴파일 작업 |
| 매니페스트·패키징 설정 | 해당 variant 조립 |
| 생성 코드·DI | 생성 작업이 포함된 해당 모듈 컴파일 |
| 새 모듈·의존 경계 | 새 모듈의 관련 검사·테스트 작업 존재 여부, 새 모듈과 직접 소비 모듈 컴파일. 루트 전체 게이트는 CI |
| DB 스키마 | 관련 마이그레이션 테스트 |
| 빌드 설정 | 바뀐 설정이 연결한 작업만. 정적 검사 배선은 `check`, 패키징·variant 설정은 해당 variant 조립 |

`--tests`나 모듈 한정 작업을 쓸 수 있으면 전체 테스트보다 우선합니다. 정확한 작업 이름은 추측하지 않고 `./gradlew :app:tasks --all`과 같은 해당 모듈 경로의 작업 목록 또는 빌드 파일에서 확인합니다.

## 위험 태그

계획이나 영역 스킬이 다음 태그를 남겼다면 해당 변경에만 추가 확인합니다.

- `db-migration` — 지원하는 이전 스키마의 마이그레이션 테스트
- `auth-session` — 만료, 동시 갱신, 무효 세션의 자동화 가능한 경로
- `permission` — 거부·설정 복귀 등 바뀐 분기
- `external-entry` — 변경된 외부 입력의 종료·실행 중 진입, 라우트와 잘못된 파라미터
- `push-registration` — 등록 토큰의 발급·갱신·실패·로그아웃 해제
- `notification-delivery` — 변경된 채널·중복·지연·표시 정책
- `session-cleanup` — 바뀐 저장 지점의 계정 전환 정리
- `state-restore` — 바뀐 상태의 구성 변경·프로세스 복원
- `durable-work` — 지속 작업의 취소·재시도·중복 실행
- `data-retry` — 바뀐 타임아웃·재시도 분기
- `idempotent-write` — 응답 유실·재시도에서 중복 쓰기 방지
- `offline-sync` — 변경된 오프라인·동기화·충돌 경로
- `coroutine-lifecycle` — 화면 이탈 시 취소와 결과 반영
- `flow-sharing` — 재구독·동시 구독에서 중복 실행과 최신 상태
- `failure-recovery` — 변경된 오류 표현과 복구 경로
- `race-condition` — 연타·응답 순서 역전 등 변경된 경쟁 경로
- `performance` — 명시된 성능 목표의 전후 측정
- `observability` — 바뀐 크래시·실패 신호의 수집과 해석
- `adaptive-ui` — 바뀐 축에 한해 창 크기·인셋·큰 글자·지역화·RTL·접근성
- `release` — `release-ops`의 릴리스 점검

전체 기기·버전 매트릭스는 로컬 기본값이 아닙니다. 자동화되지 않은 확인은 실행 가능한 범위만 수행하고 나머지는 담당자와 시점을 명시합니다.

## 작업 흐름

1. 변경 파일과 요청된 검증 수준을 확인합니다.
2. 가장 작은 관련 검증을 선택하고 이유를 한 줄로 알립니다.
3. 실행 결과를 확인합니다. 실패하면 명령과 최초의 실행 가능한 오류를 요약합니다.
4. 실패 원인 수정이 요청 범위에 있으면 수정 후 실패한 검증부터 다시 실행합니다.
5. 실행한 것, 결과, 실행하지 않은 것과 이유를 보고합니다.
