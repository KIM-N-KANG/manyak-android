# 기능 개발 계획

## 목적

새 기능을 만들기 전에, 그 기능에 해당하는 고려 사항만 골라 검토하고 구현 순서가 있는 계획을 만듭니다.

이 스킬의 핵심 기능은 **선별**입니다. 8개를 전부 훑으면 작은 기능도 몇 시간짜리 검토가 되고, 아무것도 훑지 않으면 구현 중반에 "토큰 만료는 어떻게 하죠", "오프라인에서는요" 같은 질문이 나와 되돌아갑니다. 지금 만드는 기능의 코드에 실제로 나타날 결정만 고릅니다.

## 작업 흐름

### 1. 기능을 이해하고 코드를 한 번 읽습니다

기능 설명에서 다음을 뽑습니다: 사용자가 무엇을 하게 되는지, 어떤 화면이 생기거나 바뀌는지, 서버와 무엇을 주고받는지, 로그인이 필요한지.

그다음 **기능이 닿는 코드를 한 번만 읽습니다.** 모듈 목록, 관련 화면과 상태 홀더, 관련 데이터 계층, 라우트 정의. 이 결과를 이후 모든 검토에 재사용합니다. 스킬마다 코드를 다시 읽으면 같은 파일을 여러 번 읽게 됩니다.

**이미 정해진 결정을 먼저 확인합니다.** 두 곳을 읽습니다.

- `docs/plans/_project.md` — 모듈 구조, 오류 분류 방식, 저장소 역할, 토큰 저장 위치처럼 한 번 정하면 모든 기능에 적용되는 결정
- `docs/plans/`의 관련 기능 계획 — 이 기능이 이어받거나 바꾸는 기능이 있을 때만

이미 정해진 것을 기능마다 다시 정하면 기능마다 구조가 갈립니다. 기존 결정과 다르게 가야 할 이유가 있으면 그 이유를 계획에 적고, 프로젝트 결정 자체를 바꿔야 하면 `_project.md`를 갱신합니다.

기능 설명이 모호해 신호를 뽑을 수 없으면 여기서 사용자에게 묻습니다. 잘못 선별하면 이후 전부가 어긋납니다.

### 2. 검토할 스킬을 고릅니다

기능에서 아래 신호를 찾아 해당하는 스킬을 모읍니다. 한 신호가 여러 스킬을 부르고, 여러 신호가 같은 스킬을 부르면 한 번만 셉니다.

| 기능에 이런 것이 있으면 | 검토할 스킬 |
| --- | --- |
| 새 화면이나 새 사용자 흐름 | `module-architecture`, `state-lifecycle`, `adaptive-ui` |
| 서버에서 데이터를 읽어 보여줌 | `data-layer`, `reliability` |
| 서버에 만들거나 고치거나 지움 | `data-layer`, `reliability` |
| 사용자 입력을 받는 폼 | `state-lifecycle`, `reliability`, `adaptive-ui` |
| 목록, 페이지네이션, 검색·필터 | `data-layer`, `state-lifecycle`, `reliability` |
| 인증 인프라가 아직 없는데 로그인이나 토큰이 필요함 | `auth-session` |
| 인증 방식 변경, 로그인 제공자 추가 | `auth-session` |
| 로그아웃·탈퇴·계정 전환 | `auth-session`, `session-data-cleanup` |
| 사용자 데이터를 저장하는 저장소나 SDK를 새로 도입함 | `session-data-cleanup` |
| 새 권한을 요청하거나 개인정보를 저장함 | `auth-session` |
| 알림, 딥링크, 외부에서 앱을 여는 경로 | `notification-entry`, `module-architecture` |
| 앱을 닫아도 끝나야 하는 작업(업로드·전송·동기화) | `state-lifecycle`, `data-layer` |
| 오프라인에서 보거나 수정해야 함 | `data-layer`, `state-lifecycle` |
| 새 모듈, 새 라이브러리, 환경 설정 변경 | `module-architecture`, `release-ops` |
| 새 문자열이나 새 레이아웃 | `adaptive-ui` |
| 단계적으로 열거나 급할 때 꺼야 함 | `release-ops` |

**선별 판단 기준**: 그 스킬의 결정이 이 기능의 코드나 설정에 실제로 나타나는가. 나타나지 않으면 뺍니다. 애매하다는 이유로 넣지 않습니다.

**이미 있는 것을 그대로 쓰는 것은 신호가 아닙니다.** 공통 인증 클라이언트가 이미 있는데 인증이 필요한 API를 하나 더 붙이거나, 저장소 역할이 이미 정해졌는데 테이블을 하나 더 만드는 것은 결정할 것이 없습니다. `_project.md`의 결정을 따르면 됩니다. 스킬은 그 결정이 아직 없거나, 이 기능 때문에 바뀌어야 할 때 부릅니다.

**고른 스킬이 6개를 넘으면 기능이 너무 큽니다.** 이건 계획을 크게 세우라는 뜻이 아니라 기능을 쪼개라는 신호입니다. 사용자에게 나눌 단위를 제안하고, 첫 단위부터 계획합니다.

**고른 스킬이 없거나 하나뿐이면 계획 문서를 만들지 않습니다.** 문구 수정이나 설정 토글 하나처럼 결정할 것이 거의 없는 변경에 계획 문서는 비용만 늘립니다. 해당 스킬의 결정만 대화로 답하고 구현으로 넘어갑니다.

**고른 스킬을 사용자에게 먼저 알립니다.** "이 기능은 A, B, C를 검토하겠습니다"라고 한 줄로 말하고 진행합니다. 빠진 것이 있으면 사용자가 여기서 잡아 줍니다.

### 3. 스킬을 하나씩 호출해 검토합니다

Skill 도구로 고른 스킬을 순서대로 호출합니다. **`module-architecture`를 가장 먼저 봅니다.** 코드를 어디에 둘지가 나머지 결정의 전제이기 때문입니다. 나머지는 데이터 → 상태 → 화면 → 외부 진입 → 운영 순서가 자연스럽습니다.

각 스킬에는 **적용 범위 판단** 표가 있습니다. 그 표를 써서 이 기능에 해당하는 결정 항목만 봅니다. 스킬을 불렀다고 그 안의 항목을 전부 검토하지 않습니다. 1단계에서 읽은 내용은 이미 이 대화에 있으므로, 스킬이 코드를 읽으라고 해도 같은 파일을 다시 열지 않습니다.

**각 스킬의 작업 흐름을 끝까지 실행하지 않습니다.** 고려 사항 스킬들은 단독으로 불릴 때를 전제로 쓰여 있어서, 결정을 사용자에게 보고하고 코드 변경 승인을 받는 단계로 끝납니다. 여기서는 판단 기준을 적용해 결정을 얻는 데까지만 씁니다. 스킬마다 사용자에게 보고하거나 승인을 묻지 않고, 보고와 승인은 계획이 완성된 뒤 한 번에 합니다.

각 스킬에서 세 가지를 받아옵니다.

- **결정**: 이 기능에 적용되는 항목과 선택한 값, 그리고 왜 그 값인지 한 줄
- **미결정**: 지금 정할 수 없는 것과, 무엇이 있어야 정할 수 있는지
- **검증 시나리오**: 이 기능에서 실제로 확인해야 할 항목

**한 스킬을 마치면 결과만 들고 넘어갑니다.** 위 세 가지를 받아 적었으면 그 스킬의 판단 기준 본문은 더 참조하지 않습니다. 다섯 개를 부르면 판단 기준만 수백 줄이 쌓이고, 정작 결정을 합치고 계획을 쓸 자리가 줄어듭니다. 검토가 길어지면 지금까지 모은 결정 목록을 짧게 정리하고 다음 스킬로 갑니다.

### 4. 결정을 합칩니다

**같은 결정을 두 번 정하지 않습니다.** 고려 사항 스킬들은 서로 겹치는 지점을 이미 명시하고 있습니다. 두 스킬이 같은 것을 가리키면 한 곳에서 정하고 다른 곳은 그 값을 참조합니다. 자주 겹치는 곳입니다.

| 겹치는 결정 | 어디서 정하는가 |
| --- | --- |
| 탭 전환 시 상태 보존 | `module-architecture`의 백스택 규칙에서 정하고 `state-lifecycle`이 참조 |
| 오류 분류 | `data-layer`가 기술 분류를 정하고 `reliability`가 화면 표현을 정함 |
| 중복 실행 | 요청 계층은 `data-layer`, 취소 범위는 `state-lifecycle`, 화면 상태 어긋남은 `reliability` |
| 권한 요청 | 일반 원칙은 `auth-session`, 알림 권한은 `notification-entry` |
| 세션 종료 | 정책은 `auth-session`, 지울 대상 탐색은 `session-data-cleanup` |
| 백그라운드 작업 | `state-lifecycle`이 정하고 `data-layer`·`notification-entry`가 참조 |

**충돌하면 드러냅니다.** 두 검토가 같은 것을 다르게 정했다면 둘 중 하나를 조용히 고르지 말고, 무엇이 갈렸는지 적고 하나로 합칩니다.

**미결정을 세 갈래로 나눕니다.** 이것이 계획의 위험 목록이 됩니다.

- 서버와 합의가 필요한 것 (API 계약, 멱등성 키, 토큰 수명, 페이로드 스키마)
- 제품·디자인 결정이 필요한 것 (오프라인 지원 범위, 오류 문구, 권한 요청 시점)
- 사용자가 다르게 고를 수 있는 것

서버 합의가 필요한 항목은 **가장 먼저 요청해야 하는 것**입니다. 구현을 막기 때문입니다.

**계획을 질문지로 만들지 않습니다.** 정할 수 있는 것은 기본값으로 정하고 근거를 적습니다. 사용자에게 되묻는 것은 다르게 골랐을 때 계획이 실제로 달라지는 항목으로 제한하고, 계획을 다 만든 뒤 3~5개로 모아 한 번에 확인합니다. 열 개가 넘는 질문을 늘어놓으면 답을 받지 못하고, 결국 아무것도 정해지지 않은 계획이 남습니다.

### 5. 구현 순서를 정합니다

의존 관계를 따릅니다. 아래가 기본 순서이고, 해당 없는 단계는 건너뜁니다.

1. **자리 만들기** — 모듈·패키지 위치, 라우트 추가. 이게 없으면 나머지를 놓을 곳이 없습니다.
2. **데이터 계층** — 데이터 출처 결정 적용, 저장소, 오류 타입 변환.
3. **상태와 화면 상태** — 상태 홀더, 로딩·성공·비어 있음·오류 네 상태.
4. **화면** — 레이아웃, 문자열, 접근성.
5. **외부 진입** — 알림, 딥링크, 백스택 합성.
6. **검증과 계측** — 검증 시나리오 실행, 관측 대상 연결.

각 단계에 **끝났다고 말할 수 있는 조건**을 한 줄로 답니다. "화면 구현"이 아니라 "폰트 최대 설정에서 잘림 없이 스크롤 가능"처럼 확인 가능한 문장으로 씁니다.

서버 합의 대기 항목이 막는 단계를 표시합니다. 막힌 단계를 우회할 수 있으면(가짜 데이터로 화면 먼저) 그 방법을 적습니다.

### 6. 계획 문서를 남깁니다

`docs/plans/{기능-이름}.md`에 아래 구조로 씁니다. 대화 응답에는 결정 요약과 구현 순서만 짧게 옮기고, 자세한 내용은 문서로 보냅니다.

**결정 표에는 실제로 갈릴 수 있었던 것만 적습니다.** 기본값을 그대로 따른 항목까지 전부 옮기면 표가 길어져 정작 다시 볼 결정이 묻힙니다. 나중에 이 문서를 여는 사람은 "왜 이렇게 했지"를 확인하러 오지, 무엇을 검토했는지 세는 것이 아닙니다.

**프로젝트 차원 결정은 기능 계획이 아니라 `docs/plans/_project.md`에 남깁니다.** 이 기능에서 처음 정했지만 다음 기능에도 그대로 적용될 결정이 그렇습니다. 기능 계획에만 적으면 다음 기능이 그 결정을 찾으려고 지난 계획을 전부 뒤져야 하고, 결국 다시 정하게 됩니다. 파일이 없으면 만듭니다.

```markdown
# 프로젝트 결정

| 결정 | 값 | 정한 곳 | 날짜 |
| --- | --- | --- | --- |
| 모듈 구조 | 흐름 단위 feature 모듈, core는 성격별 분리 | 목록 기능 계획 | YYYY-MM-DD |
| 오류 분류 | data 계층 경계에서 앱 오류 타입으로 변환 | 목록 기능 계획 | YYYY-MM-DD |
```

```markdown
# {기능 이름} 개발 계획

- 작성일: YYYY-MM-DD
- 검토한 고려 사항: module-architecture, data-layer, reliability

## 결정

```

### 7. 계획을 공격한 뒤 냅니다

계획을 다 쓰면 `plan-critique` 스킬을 호출해 방금 쓴 계획을 적대적으로 검토합니다. 사용자에게 내는 것은 **이미 한 번 공격당한 계획**이어야 합니다. 계획은 만든 직후가 가장 그럴듯해 보이고, 만든 사람 눈에는 빠진 부분이 보이지 않습니다.

- **재설계 등급 발견은 계획을 고친 뒤 냅니다.** 그대로 구현하면 나중에 버릴 것이 생기는 발견입니다.
- **보완·확인 등급은 계획에 반영하거나 검토 결과로 함께 냅니다.** 구현 중에 정해도 되는 것까지 계획을 붙잡고 다듬지 않습니다.
- **반영은 한 번만 합니다.** 고친 계획을 다시 공격해 또 나오면 사용자 판단으로 넘깁니다. 계획 단계에서 무한히 다듬는 것보다 구현하며 확인하는 편이 빠른 지점이 있습니다.
- `plan-critique`를 쓸 수 없는 상황이면 그 사실을 알리고 넘어갑니다. 검토를 못 했다는 것 자체가 사용자가 알아야 할 정보입니다.

사용자에게 낼 때 세 가지를 함께 냅니다: 계획 문서 경로, 검토에서 고친 것, 남겨 둔 발견.

그다음 구현을 시작할지 확인합니다. 이 스킬의 산출물은 계획이며, 코드 작성은 승인 후에 시작합니다.
