# 프로젝트 결정

- 최종 확인일: 2026-08-21
- 상태: 초기 구성 단계

구조·데이터·인증·배포와 상태·비동기 처리처럼 여러 기능이 공통으로 따라야 하는 기술 결정을 기록합니다. 실제 코드나 하네스 제품 스펙에 근거가 없는 값은 `미정`으로 둡니다.

## 현재 결정

| 영역 | 결정 | 근거 |
| --- | --- | --- |
| 모듈 구조 | 멀티 모듈을 채택합니다. 전환 완료 후 `:app`은 애플리케이션 조립과 진입을 담당하고, 기능과 공통 코드는 책임과 의존 경계에 따라 별도 모듈에 둡니다. | 사용자 결정 |
| 모듈 전환 | 현재 `settings.gradle.kts`에는 `:app`만 있습니다. 첫 구조 계획에서 초기 모듈과 전환 순서를 정하고, 각 변경에서는 계획에 포함된 기능만 이동합니다. 관련 없는 기존 코드는 해당 전환 단계까지 `:app`에 남길 수 있으며 기존 기능 이동과 동작 변경을 불필요하게 섞지 않습니다. | 빅뱅 전환과 원인 분리가 어려운 대규모 변경을 피하기 위함 |
| 계층 구조 | UDF(Unidirectional Data Flow)를 사용합니다. 불변 UI 상태는 상태 소유자에서 UI로 내려가고, 사용자·시스템 이벤트는 UI에서 상태 소유자로 올라갑니다. 상태 전이는 상태 소유자 한 곳에서 일어나며 지속 상태는 재구독자에게 최신값을 제공합니다. | 사용자 결정. 상태 변경 경로와 책임을 일관되게 유지하기 위함 |
| 일회성 효과 | 내비게이션·스낵바·권한 요청 같은 일회성 효과는 지속 UI 상태와 구분합니다. 처리된 효과는 재구독 때 반복되지 않고, 반드시 완료해야 하거나 앱 재시작 뒤 복원할 작업·목적지는 유실 가능한 신호에만 의존하지 않게 합니다. 구체 타입 이름은 강제하지 않지만 전달·소비 의미는 명시합니다. | 효과의 중복 실행과 유실을 피하기 위함 |
| 모듈 의존성 | 구체적인 모듈 의존 방향과 Domain·UseCase 계층의 도입 범위는 멀티 모듈 구조 계획에서 확정합니다. UDF만으로 별도 계층을 자동 도입하지 않습니다. | 모듈 목록과 기능 경계가 아직 확정되지 않음 |
| 모듈 품질 게이트 | 새 모듈은 역할에 필요한 정적 검사·lint·테스트 작업이 루트 CI 게이트에 연결되고 리포트를 모듈 경로와 무관하게 수집할 수 있어야 합니다. 로컬에서는 새 모듈과 직접 소비 모듈만 확인하고 전체 게이트는 CI에 맡깁니다. | 새 모듈이 기존 품질 정책에서 조용히 빠지는 것을 막기 위함 |
| 로컬 검증 | 변경된 모듈의 관련 테스트 또는 가장 작은 컴파일 작업을 우선합니다. | 빠른 피드백 유지 |
| PR 검증 | CI의 `./gradlew check`와 `./gradlew assembleDebug`가 전체 기본 게이트입니다. 로컬에서 자동으로 중복 실행하지 않습니다. | `.github/workflows/android-ci.yml` |
| 수동 검증 | 변경된 동작 중 자동화할 수 없는 고위험 경로만 기능 완료 시 확인합니다. 전체 기기·언어·버전 매트릭스는 릴리스 또는 명시적 QA에서 수행합니다. | 검증 비용을 변경 위험에 맞추기 위함 |
| 빌드 버전 | JDK, SDK, 플러그인 버전은 실제 Gradle·CI 파일을 정본으로 사용합니다. | 문서 사본의 노후화 방지 |
| 데이터·네트워크 | 미정 — 기능별 계약이 확정될 때 프로젝트 공통값만 이 문서에 추가합니다. | 구현 근거 없음 |
| 인증·세션 | 미정 — 서버 토큰·세션 계약 확정 전에는 클라이언트 값을 추측하지 않습니다. | 구현 근거 없음 |
| 배포 | PR CI 외 환경 분리·서명·단계적 배포 정책은 미정입니다. | 운영 구성 근거 없음 |

## 갱신 규칙

- 한 기능에만 해당하는 선택은 기능 계획 또는 코드에 남기고 이 문서에 복사하지 않습니다.
- 다음 기능도 따라야 하는 결정이 실제로 바뀔 때만 이유와 날짜를 함께 갱신합니다.
- 구현을 요청받은 작업은 이미 변경 권한이 있는 것으로 보고, 스킬이 같은 범위의 승인을 다시 요구하지 않습니다.
- 설계·감사·리뷰만 요청받은 작업은 코드나 외부 시스템을 변경하지 않습니다.
