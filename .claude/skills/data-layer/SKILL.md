# 데이터 계층

## 목적

데이터의 권위 있는 출처, 실패 처리, 저장 범위를 명확히 하고 클라이언트가 혼자 정할 수 없는 서버 계약을 분리합니다.

## 먼저 정할 것

데이터마다 다음을 명시합니다.

- 권위 있는 출처와 화면이 관찰하는 경로
- 읽기인지 쓰기인지
- 저장이 필요한 이유와 신선도
- 오프라인에서 허용할 동작

네트워크와 로컬 캐시를 함께 쓸 수 있지만, 충돌했을 때 무엇이 최종값인지와 갱신 흐름이 하나여야 합니다.

## 실패와 재시도

- 네트워크·HTTP·파싱 오류를 데이터 경계에서 앱 오류로 변환합니다.
- 연결·읽기·쓰기와 전체 요청의 시간 상한을 구분합니다.
- 자동 재시도는 요청의 멱등성과 서버 부하를 확인한 뒤 제한합니다.
- 서버의 `Retry-After` 등 명시적 지시가 있으면 임의 백오프보다 우선합니다.
- 취소를 오류로 바꾸지 않으며 재시도는 한 계층에서만 담당합니다.

## 쓰기와 중복

응답 유실 후 재요청될 수 있는 쓰기는 서버와 멱등성 계약을 확인합니다. 키의 발급 주체, 생성 시점, 재사용 범위가 계약에 포함되어야 합니다. 계약이 없으면 자동 재시도를 넣지 않습니다.

## 저장과 동기화

- 다시 열 때 즉시 필요하거나 오프라인 요구가 있거나 재요청 비용이 큰 데이터만 저장합니다.
- DB, 키-값, 파일은 조회 형태와 데이터 수명에 맞춰 고릅니다.
- 오프라인 쓰기는 명시적 제품 요구가 있을 때만 도입합니다.
- 변경분 동기화에는 커서·삭제 표시·부분 실패·서버 기준 시각이 필요합니다.
- 동시 수정이 실제로 가능한 데이터에만 충돌 해결 정책을 만듭니다.

## 결과

결정, 저장하지 않을 데이터, 서버 합의 항목, 미결정을 간결하게 보고합니다. 프로젝트 공통 정책이 바뀔 때만 `docs/plans/_project.md`를 갱신합니다.

실제 검증은 `android-change-verification`에 맡기고 변경에 해당하는 태그만 전달합니다.

- `data-retry` — 재시도·타임아웃 변경
- `idempotent-write` — 쓰기 중복 방지 변경
- `offline-sync` — 오프라인 쓰기·동기화·충돌 변경
- `db-migration` — 스키마 변경
