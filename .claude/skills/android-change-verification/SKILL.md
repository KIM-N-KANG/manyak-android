# 변경 검증

## 목적

변경에 맞는 검증만 골라 실제로 실행하는 작업 스킬입니다. 결정을 내리지 않고 명령을 돌립니다.

| 하는 일 | 내용 |
| --- | --- |
| 선택 | 변경된 영역을 보고 필요한 검증만 고릅니다 |
| 수집 | 이 변경에 관련된 스킬이 남긴 검증 시나리오를 모읍니다 |
| 실행 | 고른 명령을 돌리고 출력을 확인합니다 |
| 판정 | 통과·실패를 근거와 함께 보고합니다 |

## 선행 전제: 전부 돌리는 것과 맞게 돌리는 것은 다릅니다

모든 변경에 전체 빌드를 돌리면 느려서 아무도 로컬에서 돌리지 않게 되고, 결국 CI만 믿게 됩니다. 반대로 적게 돌리면 놓칩니다. 두 가지 규칙이 나옵니다.

- **변경 위험에 맞춰 고릅니다.** 문자열 하나를 고친 변경과 데이터베이스 스키마를 바꾼 변경에 같은 검증을 요구하지 않습니다.
- **최소 검증과 병합 전 필수 검증을 나눕니다.** 작업 중에는 빠른 쪽을 돌리고, 병합 전에는 느려도 전부 돌립니다. 이 경계를 정하지 않으면 둘 중 하나로 쏠립니다.

**실행하지 않은 검증을 통과로 적지 않습니다.** 돌리지 못했으면 그 이유를 함께 남깁니다.

## 적용 범위 판단

| 요청 | 하는 일 |
| --- | --- |
| 구현을 마치고 확인 | 변경 영역 분석 + 최소 검증 실행 |
| 커밋·PR 전 확인 | 병합 전 필수 검증 전부 실행 |
| 특정 영역만 확인 | 그 영역의 검증만 실행 |
| 무엇을 돌려야 하는지 판단 | 영역 분석과 명령 목록까지, 실행은 승인 후 |
| 실패 원인 확인 | 실패한 검증을 좁혀 다시 실행 |

## 이 저장소의 명령

**추측하지 않고 실제 구성을 읽습니다.** `app/build.gradle.kts`, `gradle/libs.versions.toml`, `.github/workflows/`를 확인해 아래 목록이 지금도 맞는지 봅니다. 구성이 바뀌었으면 읽은 내용을 따릅니다.

| 명령 | 포함하는 것 |
| --- | --- |
| `./gradlew check` | ktlint, detekt, Android lint, 단위 테스트 |
| `./gradlew testDebugUnitTest` | 단위 테스트만 |
| `./gradlew assembleDebug` | 패키징까지. `check`는 여기까지 하지 않아 리소스·매니페스트 문제를 놓칩니다 |
| `./gradlew connectedDebugAndroidTest` | 계측 테스트. 기기나 에뮬레이터가 필요합니다 |

CI는 `check` 다음 `assembleDebug`를 돌립니다. 로컬에서 다른 명령을 쓰면 CI에서만 깨지는 상황이 생기므로 같은 명령을 씁니다.

## 변경 영역별 검증

| 변경한 것 | 최소 검증 | 병합 전에 추가로 |
| --- | --- | --- |
| 순수 Kotlin 로직 | 해당 단위 테스트 | `check` |
| 상태 홀더, 비동기 흐름 | 상태 전이 테스트, 취소·재시도 경로 | `check` |
| Compose 화면 | 컴파일, Preview 확인 | UI 테스트, 폰트 확대·다크 모드 |
| 문자열, 리소스, 매니페스트 | `assembleDebug` | 영향받는 다른 variant도 패키징 |
| 의존성 주입, 생성 코드 | 생성이 포함된 컴파일 | `check` |
| 데이터베이스 스키마 | 스키마 변경 확인, 마이그레이션 테스트 | 이전 버전에서 올라오는 경로 |
| 축소·난독화 설정 | 축소를 켠 빌드 생성 | 그 빌드로 주요 흐름 실행 |
| 외부 진입 경로 | 링크 실행으로 도착 화면 확인 | 앱이 없는 상태와 실행 중 상태 각각 |
| 빌드 설정, 버전 카탈로그 | `check`, `assembleDebug` | 모든 variant 컴파일 |

**컴파일만으로 끝나는 변경은 거의 없습니다.** 컴파일은 통과했는데 실행에서 죽는 자리가 생성 코드, 리소스, 축소 설정입니다.

## 검증 시나리오 수집

**시나리오 목록을 여기에 적어 두지 않습니다.** `.claude/skills/`를 훑어 이 변경에 관련된 스킬을 찾고, 각 스킬의 **검증 시나리오** 표에서 해당하는 행을 가져옵니다. 스킬들이 이미 자기 영역에서 무엇을 확인해야 하는지 적어 두었으므로 옮겨 적으면 낡습니다.

가져온 시나리오 중 명령으로 자동화되는 것과 사람이 직접 해야 하는 것을 나눕니다. 기기 설정을 바꾸거나 두 계정을 번갈아 쓰는 확인은 자동화되지 않으므로 사용자에게 목록으로 넘깁니다.

## 작업 흐름

1. **변경된 파일을 확인합니다.** `git status`와 `git diff --name-status`로 보고, 추측하지 않습니다.
2. **파일을 위 표의 영역으로 분류합니다.** 한 변경이 여러 영역에 걸치면 전부 셉니다.
3. **관련 스킬의 검증 시나리오를 모읍니다.** 디렉터리를 훑어 찾습니다.
4. **최소 검증과 병합 전 필수 검증으로 나눠 명령 목록을 만듭니다.** 사용자에게 무엇을 왜 돌리는지 한 줄로 알립니다.
5. **명령을 실행하고 출력을 확인합니다.** 실패하면 출력을 그대로 인용합니다. 요약으로 대체하지 않습니다.
6. **자동화되지 않는 시나리오를 목록으로 넘깁니다.** 사람이 확인할 항목입니다.
7. **판정을 보고합니다.** 실행한 명령, 결과, 실행하지 못한 것과 그 이유를 함께 적습니다.

**실패를 숨기지 않습니다.** 관련 없어 보이는 실패도 보고합니다. 그 판단은 사용자가 합니다.
