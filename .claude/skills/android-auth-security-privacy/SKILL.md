# 인증·보안·개인정보

## 목적

안드로이드 앱 개발 고려 사항 8개 항목 중 4번 **인증·보안·개인정보**를 담당합니다. 아래 7개 결정 항목을 각각 명시적으로 결정하거나, 기존 코드가 이미 내린 결정을 확인하고 위반을 지적합니다.

| 결정 항목 | 결정할 내용 |
| --- | --- |
| 1. 토큰 관리 | Access·Refresh 토큰의 수명, 보관 형태, 요청 첨부 방식 |
| 2. 만료·갱신 실패 | 토큰 만료와 갱신 실패를 어떻게 처리할지 |
| 3. 동시 갱신 방지 | 여러 요청이 동시에 토큰을 갱신하지 않게 할 방법 |
| 4. 저장 위치 | 토큰과 민감한 데이터를 어디에 저장할지 |
| 5. 세션 종료·전환 | 로그아웃·탈퇴·계정 전환·멀티 디바이스 세션을 어떻게 처리할지 |
| 6. 수집 범위 | 권한과 개인정보를 어느 범위까지 수집하고 보관할지 |
| 7. 노출 경로 | 로그·백업·외부 입력에서 민감 정보가 새지 않는지 |

## 선행 전제: 클라이언트는 신뢰 경계 밖입니다

앱은 사용자 기기에서 실행되고 분해될 수 있습니다. 앱에 포함되거나 앱이 저장한 어떤 값도 비밀로 유지된다고 가정할 수 없습니다. 클라이언트가 할 수 있는 일은 셋뿐입니다.

- 탈취 난이도를 올린다
- 탈취됐을 때 피해 범위와 유효 기간을 줄인다
- 서버가 검증하고 무효화할 수 있게 한다

이 전제가 없으면 "클라이언트에서 암호화하니 안전하다", "난독화했으니 키를 넣어도 된다" 같은 결정이 나옵니다. 접근 제어의 최종 판단은 항상 서버가 합니다. 클라이언트의 화면 숨김은 편의이지 보안이 아닙니다.

요청 규모에 맞는 항목만 검토합니다.

| 요청 | 검토할 항목 |

## 결정 항목별 판단 기준

### 1. 토큰 관리

- **Access와 Refresh의 수명을 서버와 합의합니다.** 짧은 Access와 긴 Refresh가 기본입니다. Access 수명이 길면 탈취 시 무효화할 방법이 없고, 지나치게 짧으면 갱신이 잦아 3번 항목의 동시 갱신 문제가 커집니다.
- **Refresh 토큰 회전 여부를 확인합니다.** 갱신할 때마다 새 Refresh를 발급하고 이전 것을 무효화하면 재사용을 감지할 수 있습니다. 회전하지 않으면 탈취된 Refresh가 만료까지 유효합니다. 회전을 쓰면 3번 항목의 동시 갱신 방지가 필수가 됩니다.
- **로그인이 확정되는 지점을 하나로 정합니다.** 외부 제공자 인증 성공, 서버와 토큰 교환, 토큰 저장은 각각 실패할 수 있습니다. 서버 토큰을 저장한 순간만 로그인으로 보고 그 앞 단계는 전부 미로그인으로 취급합니다. 중간 단계를 로그인으로 처리하면 제공자는 인증된 상태인데 앱은 토큰이 없는 상태가 남아, 다시 시도할 때 제공자가 화면을 띄우지 않아 사용자가 진행할 수 없습니다.
- **토큰 첨부 지점을 한 곳으로 모읍니다.** 요청마다 헤더를 붙이는 코드를 화면이나 저장소 계층에 흩어 두면 새 API에서 빠뜨리고 갱신 로직도 여러 벌이 됩니다.
- **화면과 상태 홀더에 토큰을 노출하지 않습니다.** 화면이 아는 것은 로그인 여부와 사용자 표시 정보까지입니다.
- **메모리와 저장소의 관계를 정합니다.** 매 요청마다 디스크를 읽지 않도록 메모리에 두되, 프로세스가 죽은 뒤 다시 읽어 올리는 경로를 명시합니다.

### 2. 만료·갱신 실패

- **앱 시작 시 인증 상태 판단 경로를 정합니다.** 저장된 토큰이 있다는 사실만으로 로그인 상태로 보고 바로 진입할지, 시작 화면에서 갱신을 한 번 시도해 확인한 뒤 진입할지 결정합니다. 확인 후 진입은 시작이 느려지고, 바로 진입은 첫 요청이 실패하며 화면이 한 번 흔들립니다. Access 토큰을 메모리에만 두기로 했다면 앱을 켤 때마다 갱신이 한 번 나가므로 이 결정과 함께 봅니다.
- **만료 판단 경로를 정합니다.** 만료 시각을 미리 계산해 갱신할지, 401을 받고 갱신할지. 클라이언트 시계는 틀릴 수 있으므로 사전 계산만 믿지 않고 401 경로는 항상 있어야 합니다.
- **갱신 실패를 두 가지로 구분합니다.** 네트워크 실패는 재시도 대상이고, Refresh 무효는 로그아웃 대상입니다. 이 둘을 합치면 사용자가 지하철에서 세션을 잃습니다.
- **403은 갱신 대상이 아닙니다.** 토큰은 유효하지만 권한이 없는 상태이므로 갱신하거나 로그아웃시키지 않고 접근 불가로 처리합니다. 401과 403을 한 분기로 묶으면 권한 없는 화면에 들어갈 때마다 로그아웃됩니다.
- **강제 로그아웃 시 사용자 경험을 정합니다**: 작성 중이던 입력을 어떻게 할지, 어느 화면으로 보낼지, 이유를 알릴지, 다시 로그인한 뒤 원래 화면으로 돌려보낼지.
- **인증 상태를 한 곳에서 관찰하게 합니다.** 강제 로그아웃은 네트워크 계층에서 감지되지만 화면 전환은 화면 계층에서 일어납니다. 상태를 전파하는 경로가 없으면 세션이 끊긴 뒤에도 화면이 그대로 남아 사용자는 빈 목록만 보게 됩니다.
- **인증이 필요한 화면과 가드 지점을 정합니다.** 화면마다 각자 로그인 여부를 검사하면 새 화면에서 빠집니다. 인증이 필요한 라우트를 그래프에서 구분하고 한 곳에서 막습니다. 미로그인 상태로 진입했을 때 로그인 화면으로 보낸 뒤 원래 화면으로 돌려보낼지도 함께 정합니다. 그래프 구성은 고려 사항 1번 항목 스킬과 같은 자리입니다.
- **401을 받은 원래 요청은 갱신 성공 후 한 번만 재시도합니다.** 재시도 후에도 401이면 갱신을 다시 부르지 않습니다. 이 상한이 없으면 갱신 루프가 됩니다.
- **쓰기 요청의 재시도는 중복 생성을 확인하고 합니다.** 서버가 요청을 처리한 뒤 401을 반환한 경우 재시도가 데이터를 두 번 만들 수 있습니다. 멱등성은 고려 사항 3번 항목 스킬에서 결정합니다.

### 3. 동시 갱신 방지

- **문제 상황을 먼저 이해합니다.** 화면 진입 시 여러 요청이 동시에 나가고 토큰이 만료되어 있으면 401이 동시에 돌아옵니다. 각 요청이 각자 갱신을 시작하면, 회전 방식에서는 뒤늦은 갱신이 이미 무효가 된 Refresh를 보내 전부 실패하고 사용자가 로그아웃됩니다.
- **갱신을 단일 진입점으로 만듭니다.** 첫 요청만 갱신을 수행하고 나머지는 그 결과를 기다립니다. 갱신 성공 시 대기하던 요청은 새 토큰으로 재시도하고, 실패 시 모두 같은 실패로 끝냅니다.
- **갱신 요청 자체는 갱신 경로를 타지 않게 합니다.** 갱신 요청이 401을 받아 다시 갱신을 부르면 무한 루프입니다.
- **갱신과 저장의 원자성을 확인합니다.** 새 토큰을 저장하는 도중 프로세스가 죽으면 이전 토큰도 새 토큰도 못 쓰는 상태가 될 수 있습니다.
- **앱 프로세스 밖의 접근을 확인합니다.** 지속 작업이나 위젯처럼 화면과 별개로 실행되는 코드도 같은 갱신 경로를 쓰는지 봅니다.

### 4. 저장 위치

| 데이터 | 위치 | 근거 |
| --- | --- | --- |
| Refresh 토큰 | 시스템 보안 저장소, 하드웨어 지원 키로 보호 | 탈취 시 피해가 가장 큼 |
| Access 토큰 | 메모리 우선, 필요한 경우에만 보안 저장소 | 수명이 짧고 재발급 가능 |
| 사용자 표시 정보 | 일반 저장소 | 민감도 낮음 |
| 결제 수단, 신원 확인 정보 | 저장하지 않음 | 서버가 보관하고 클라이언트는 참조만 |

- **어떤 저장소도 루팅·디버깅 환경에서는 안전하지 않습니다.** 저장 위치 결정은 피해를 늦추는 수단이지 차단이 아닙니다.
- **앱에 포함되는 값은 비밀이 아닙니다.** 소스 상수, 빌드 설정, 리소스에 서버 비밀 키를 넣지 않습니다. 환경별 설정과 서명 키 보호는 고려 사항 8번 항목 스킬에서 결정합니다.
- **보안 저장소 읽기·쓰기 실패의 복구 경로를 정합니다.** 사용자가 화면 잠금을 바꾸거나 해제하면 하드웨어 키가 무효화되어 저장된 토큰을 영영 복호화하지 못할 수 있습니다. 이때 저장 값을 지우고 재로그인으로 보내는 경로가 없으면 앱이 시작 화면에서 멈추거나 죽습니다. 저장 실패도 조용히 넘기지 않습니다.
- **기기 인증을 요구할지 정합니다.** 보안 저장소 접근에 생체·화면잠금 인증을 요구하면 잠금 해제 전에는 백그라운드 작업이 토큰을 읽지 못합니다. 자동 동기화와 충돌하므로 함께 결정합니다.
- 로컬 DB에 저장하는 사용자 데이터 중 암호화가 필요한 항목이 있는지 판단하고, 없다면 없다고 명시합니다.

### 5. 세션 종료·전환

- **로그아웃 시 지울 대상 목록을 명시적으로 만듭니다.** 목록이 없으면 항상 무언가 남습니다. 후보: 토큰, 로컬 DB의 사용자 데이터, 이미지·파일 캐시, 사용자별 설정 값, 전송 대기 항목, 알림 등록 정보, 메모리 캐시.
- **서버 세션 종료와 로컬 삭제를 모두 수행하되, 서버 호출이 실패해도 로컬은 지웁니다.** 네트워크가 없다고 로그아웃이 막히면 사용자는 기기를 넘겨줄 수 없습니다.
- **계정 전환은 로그아웃 후 로그인으로 처리하고, 이전 계정 데이터가 남지 않는지 확인합니다.** 이 항목의 사고는 대부분 여기서 납니다.
- **로그인 없이 쓸 수 있는 앱이라면 전환 시 데이터 처리를 정합니다.** 미로그인 상태에서 만든 데이터를 로그인 계정으로 넘길지, 버릴지, 사용자에게 물을지 결정합니다. 정하지 않으면 로그인하는 순간 사용자가 만든 것이 사라집니다.
- **탈퇴는 로그아웃과 다릅니다.** 복구 가능 기간, 서버 데이터 삭제 시점, 같은 계정으로 재가입했을 때의 동작을 서버와 합의합니다. 클라이언트는 진행 상태와 취소 가능 여부를 사용자에게 정확히 보여줘야 합니다.
- **멀티 디바이스 세션 정책을 정합니다**: 동시 로그인을 허용할지, 한 기기의 로그아웃이 다른 기기에 영향을 주는지, 기기 목록과 원격 로그아웃을 제공할지.
- **다른 곳에서 세션이 끊긴 사실은 다음 요청이 실패할 때 알게 됩니다.** 즉시 감지가 필요하면 서버 알림이 필요하며 고려 사항 5번 항목 스킬과 함께 봅니다.

### 6. 수집 범위

- **권한은 그 권한이 필요한 동작 직전에 요청합니다.** 앱 시작 시 한꺼번에 요청하면 거부율이 오르고 사용자는 이유를 알 수 없습니다. 요청 전에 왜 필요한지 앱 화면에서 먼저 설명합니다.
- **거부와 영구 거부를 구분해 처리합니다.** 영구 거부 상태에서는 시스템 대화상자가 뜨지 않으므로 설정 화면으로 안내하는 경로가 필요합니다. 이 분기가 없으면 버튼을 눌러도 아무 일이 없습니다.
- **알림 권한은 여기서 정하지 않습니다.** 요청 시점과 사전 설명 화면은 고려 사항 5번 항목(알림·외부 진입) 스킬에서 정하고, 이 스킬에서는 권한 일반 원칙만 적용합니다.
- **권한 없이 동작하는 축소 경로를 만듭니다.** 권한 거부가 기능 전체를 막는 설계는 다시 봅니다.
- **수집은 기능에 필요한 최소 항목으로 제한합니다.** 나중에 쓸지 몰라서 모으지 않습니다. 수집한 순간부터 보관·삭제·공시 책임이 생깁니다.
- **항목마다 보관 기간과 삭제 경로를 정합니다.** 사용자가 삭제를 요청했을 때 무엇이 지워지는지 답할 수 있어야 합니다.
- **기기 식별자와 광고 식별자의 사용 목적을 정합니다.** 재설치 후에도 동일 사용자를 추적하기 위한 영구 식별자는 스토어 정책에 걸립니다.
- 스토어에 공시하는 수집 항목과 실제 수집 항목을 일치시킵니다. 배포 시 점검은 고려 사항 8번 항목 스킬과 함께 봅니다.

### 7. 노출 경로

점검 대상은 코드가 아니라 경로입니다. 아래를 하나씩 확인합니다.

- **로그**: 토큰, 인증 헤더, 요청·응답 본문, 사용자 입력 원문을 로그에 남기지 않습니다. 네트워크 로깅이 릴리스 빌드에서 꺼지는지 빌드 설정으로 확인합니다.
- **전송 구간**: 모든 요청이 암호화된 연결을 쓰는지 확인합니다. 로컬 서버 연동을 위해 열어 둔 평문 허용 설정이 릴리스 빌드에 남아 있지 않은지 빌드 설정으로 확인합니다.
- **크래시·분석 리포트**: 예외 메시지, 사용자 속성, 이벤트 파라미터에 민감 값이 실리지 않는지 확인합니다.
- **자동 백업**: 기본 설정에서 앱 데이터가 클라우드로 올라갈 수 있습니다. 토큰과 사용자 데이터를 백업 대상에서 제외할지 명시적으로 정합니다.
- **작업 전환기 미리보기**: 민감한 화면이 최근 앱 목록에 캡처되는지 확인하고 필요하면 가립니다.
- **외부 입력**: 딥링크 파라미터, 공유 인텐트, 알림 데이터, 웹뷰 URL은 신뢰하지 않습니다. 검증 없이 화면 이동이나 요청에 그대로 넣으면 외부에서 앱 동작을 유도할 수 있습니다. 외부 진입 흐름은 고려 사항 5번 항목 스킬에서 함께 정합니다.
- **다른 앱에 노출되는 진입점**: 외부에서 열 수 있는 컴포넌트가 인증이 필요한 화면을 바로 열 수 있는지 확인합니다.
- **웹뷰를 쓴다면** 자바스크립트 인터페이스로 노출하는 범위와 로드 허용 도메인을 제한합니다.
- **클립보드와 스크린샷**: 민감 값의 복사와 캡처를 허용할지 정합니다.

## 작업 흐름

1. **인증 흐름과 저장 대상을 나열합니다.** 추측하지 않고 토큰 발급·첨부·갱신 지점, 저장소 접근 지점, 로그아웃 처리 지점을 읽습니다.
2. **토큰 수명과 저장 위치를 결정합니다.** 서버와 합의된 값인지, 클라이언트 가정인지 구분해 적습니다.
3. **갱신 경로를 단일 진입점으로 확정하고 실패 분기를 정의합니다.** 네트워크 실패와 Refresh 무효를 반드시 나눕니다.
4. **세션 종료 시 삭제 목록을 작성합니다.** 로그아웃, 계정 전환, 탈퇴 각각에 대해 무엇을 지우는지 항목으로 남깁니다.
5. **수집하는 권한과 개인정보 항목을 나열하고 최소화합니다.** 각 항목에 사용 목적, 보관 기간, 삭제 경로를 붙입니다.
6. **노출 경로 점검 목록을 하나씩 확인합니다.** 확인하지 않은 항목은 통과로 적지 않습니다.
7. **서버와 합의가 필요한 항목을 따로 모읍니다.** 토큰 수명, 회전 여부, 세션 무효화, 탈퇴 정책, 기기 목록은 클라이언트 혼자 정할 수 없습니다.
8. **검증 시나리오를 씁니다.** 아래 표에서 이 변경에 필요한 항목을 고릅니다.
9. **결정할 수 없는 항목은 미결정으로 남깁니다.** 무엇을 알면 결정할 수 있는지 함께 적습니다.
10. **코드 변경은 사용자 승인 후에 합니다.** 이 스킬의 산출물은 결정과 감사 결과입니다.

### 검증 시나리오

| 시나리오 | 확인 방법 | 검증 대상 |
| --- | --- | --- |
| 토큰 만료 | 만료된 Access 토큰 상태로 요청 | 2번 결정 항목 |
| 동시 만료 | 여러 요청이 동시에 나가는 화면에서 만료 상태로 진입 | 3번 결정 항목 |
| 갱신 네트워크 실패 | 비행기 모드에서 갱신 시도 | 2번 결정 항목(로그아웃 오작동) |
| Refresh 무효 | 서버에서 세션을 끊고 요청 | 2번, 5번 결정 항목 |
| 계정 전환 잔여 | 로그아웃 후 다른 계정 로그인해 이전 데이터 노출 확인 | 5번 결정 항목 |
| 릴리스 빌드 로그 | 릴리스 빌드에서 로그 출력 확인 | 7번 결정 항목 |
| 백업·복원 | 백업 후 다른 기기에 복원해 인증 상태 확인 | 7번 결정 항목 |
| 권한 거부 | 거부와 영구 거부 상태로 해당 기능 진입 | 6번 결정 항목 |
| 조작된 외부 진입 | 임의 파라미터를 넣은 딥링크로 실행 | 7번 결정 항목 |
| 화면 잠금 변경 | 기기 화면 잠금을 바꾸거나 해제한 뒤 앱 실행 | 4번 결정 항목(저장소 키 무효화) |
| 로그인 중단 | 외부 제공자 인증 후 서버 교환 단계에서 앱을 종료하고 재실행 | 1번 결정 항목(로그인 확정 지점) |

계정 전환 잔여와 릴리스 빌드 로그는 개발 중에 드러나지 않습니다. 개발 빌드는 로그가 켜져 있고, 한 계정만 쓰면 잔여 데이터가 보이지 않기 때문입니다.
