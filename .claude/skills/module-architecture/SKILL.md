# 앱 구조

## 목적

안드로이드 앱 개발 고려 사항 8개 항목 중 1번 **앱 구조**를 담당합니다. 아래 5개 결정 항목을 각각 명시적으로 결정하거나, 기존 코드가 이미 내린 결정을 확인하고 위반을 지적합니다.

| 결정 항목 | 결정할 내용 |
| --- | --- |
| 1. 모듈 경계 | 어떤 모듈을 두고 각 모듈의 책임을 어디까지 볼지 |
| 2. 코드 분리 축 | 기능별·계층별로 코드를 어떻게 나눌지 |
| 3. 계층 분리 범위 | UI·Domain·Data를 어디까지 분리할지 |
| 4. 의존성 방향 | 모듈과 계층 간 의존 방향을 어떻게 제한할지 |
| 5. 네비게이션 | 화면 구조, 네비게이션 그래프, 백스택을 어떻게 구성할지 |

**전제: 멀티 모듈 구조를 사용합니다.** 따라서 1번은 단일 모듈과 멀티 모듈 중 하나를 고르는 결정이 아니라, 모듈을 어떤 축으로 몇 개까지 쪼갤지에 대한 결정입니다.

핵심 원칙은 필요한 만큼만 쪼개기입니다. 모듈은 컴파일 단위로 경계를 강제하는 대가로 Gradle 구성 시간, IDE 인덱싱, 빌드 스크립트 유지 비용을 요구합니다. 지금 없는 요구를 위해 모듈을 미리 만들지 않되, 나중에 승격할 경계는 패키지로 미리 드러냅니다.

## 적용 범위 판단

요청 규모에 맞는 항목만 검토합니다. 화면 하나 추가하는 요청에 5개 항목을 전부 훑으면 작업이 막힙니다.

| 요청 | 검토할 항목 |
| --- | --- |
| 초기 구조 설계, 구조 리뷰·감사 | 1~5 전부 |
| 새 기능 추가, 모듈을 쪼갤지 판단 | 1, 2, 4 |
| 새 화면 추가, 라우트·백스택 변경 | 5, 필요하면 2 |
| 코드를 어느 모듈·패키지에 둘지 판단 | 2, 필요하면 3 |

## 이미 결정된 항목

아래 판단 기준 중 일부는 프로젝트에서 한 번 정하면 모든 기능에 그대로 적용됩니다. 그런 항목은 `docs/plans/_project.md`를 먼저 확인합니다.

- **결정이 있으면 다시 결정하지 않습니다.** 결정을 읽고, 이 요청의 코드가 그것을 지키는지만 봅니다. 어긋나면 위반으로 보고합니다. 결정 자체를 바꿔야 하면 이유와 함께 `_project.md`를 갱신합니다.
- **결정이 없으면 여기서 정하고 그 결과를 `_project.md`에 남깁니다.** 남기지 않으면 다음 기능이 같은 결정을 처음부터 다시 하고, 기능마다 구조가 갈립니다.

이 문서를 이미 읽었다면 다시 열지 않고 그 내용을 씁니다.

| 구분 | 항목 |
| --- | --- |
| 프로젝트에서 한 번 결정 | 1 모듈 경계, 2 코드 분리 축, 3 계층 분리 범위, 4 의존성 방향, 5의 그래프 구조 |
| 기능마다 판단 | 5의 새 라우트와 백스택 |

## 결정 항목별 판단 기준

### 1. 모듈 경계

기본 모듈 유형은 다음 세 가지입니다.

| 모듈 | 책임 | 판단 기준 |
| --- | --- | --- |
| `:app` | 조립만 담당. Application 클래스, DI 그래프 루트, `NavHost`, 매니페스트 병합 | 여기에 화면이나 비즈니스 로직이 들어가면 경계가 무너진 신호입니다 |
| `:feature:*` | 화면, 상태 홀더, 비즈니스 규칙, 그 기능 전용 Data | 사용자 흐름 또는 도메인 단위로 묶습니다 |
| `:core:*` | 둘 이상의 feature가 공유하는 코드 | 두 번째 사용처가 생겼을 때 올립니다 |

**Domain 전용 모듈은 만들지 않습니다.** 비즈니스 규칙은 해당 feature 모듈 안의 `domain` 패키지에 둡니다. 계층 경계는 패키지와 가시성으로 지키고, 모듈 경계는 기능 단위로만 씁니다.

- **시작 모듈 세트**: 새 프로젝트는 `:app` + 흐름별 `:feature:*` + `:core:designsystem` + `:core:model`로 시작하고, 원격 데이터가 있으면 `:core:network`, 로컬 저장이 있으면 `:core:database` 또는 `:core:datastore`를 더합니다. 아직 쓰지 않는 core 모듈은 만들지 않습니다.
- **feature 모듈 단위**: 화면 하나당 모듈은 과합니다. 독립적으로 진입해서 완료되는 사용자 흐름(예: 인증, 온보딩, 목록·상세, 설정) 단위로 묶습니다. 다른 담당자가 병행 작업하는 경계인지도 판단에 넣습니다.
- **core 모듈 쪼개는 정도**: `:core:common` 하나에 모든 공통 코드를 넣으면 모든 모듈이 무관한 변경에 재컴파일됩니다. 성격이 다른 것부터 쪼갭니다: 디자인 시스템, 공통 모델, 네트워크, 로컬 저장소. 반대로 파일 두세 개짜리 core 모듈을 여러 개 만들지 않습니다.
- **빌드 스크립트 공유**: convention plugin(`build-logic` 포함 빌드 또는 `buildSrc`)을 처음부터 둡니다. Android·Kotlin·Compose·DI 설정을 여기에 모으고, 각 모듈 `build.gradle.kts`에는 플러그인 적용과 자기 의존성만 남깁니다. 같은 설정 블록을 모듈마다 복사하면 모듈 추가 비용이 모듈 수에 비례해 늘어납니다.
- **가시성**: 모듈 밖에서 쓸 타입만 public으로 두고 나머지는 `internal`로 둡니다. 모듈 경계가 있을 때 `internal`이 실제로 강제되므로, 이 규칙이 멀티 모듈의 실질적 이득입니다.
- **모듈 추가 판단**: 새 코드를 넣을 곳이 없다고 느껴지면 먼저 기존 모듈의 패키지로 시작하고, 사용처가 둘 이상이 되거나 담당이 갈릴 때 모듈로 승격합니다.

### 2. 코드 분리 축

- 모듈 최상위는 기능으로 나누고, 모듈 안에서 계층으로 나눕니다: `:feature:catalog`(목록·상세 흐름) 안에 `ui`, `domain`, `data` 패키지. 계층을 모듈 최상위 축으로 쓰면(`:ui`, `:data`에 전 기능) 기능 하나를 볼 때 파일이 흩어지고 모든 기능이 같은 모듈을 함께 재컴파일합니다.
- 배치 판단 기준: **이 코드를 지우면 어느 기능이 깨지는가.** 한 기능만 깨지면 그 feature 모듈, 둘 이상이면 `core`로 올립니다.
- `core`에 올릴 후보: 디자인 시스템과 공통 Composable, 여러 기능이 공유하는 모델, 네트워크 클라이언트 설정, DB·설정 저장소 설정, 날짜·포맷 유틸.
- **리소스 배치**: 문자열과 드로어블은 그것을 쓰는 모듈에 둡니다. 여러 모듈이 쓰는 것만 `core`로 올리고, 모듈별 `resourcePrefix`로 이름 충돌을 막습니다.
- 한 기능에서만 쓰는 코드를 미리 `core`에 넣지 않습니다. `core`는 모든 모듈이 의존하는 자리이므로 여기에 넣은 코드는 되돌리기 가장 비쌉니다.

### 3. 계층 분리 범위

- 최소 형태는 UI + Data 2계층입니다. Domain 계층(UseCase)은 다음 신호가 있을 때만 추가합니다: 여러 Repository를 조합해야 함, 둘 이상의 화면이 같은 비즈니스 규칙을 씀, 비즈니스 규칙 자체를 단위 테스트로 고정해야 함.
- Repository 메서드를 1:1로 감싸는 pass-through UseCase만 나온다면 Domain 계층을 만들지 않습니다.
- **Domain 위치**: feature 모듈 안 `domain` 패키지에 둡니다. Domain 전용 모듈로 빼지 않습니다.
- **여러 feature가 같은 규칙을 쓰는 경우**: 먼저 feature 경계를 잘못 나눴는지 확인합니다. 같은 흐름이면 한 feature로 합칩니다. 경계가 맞는데도 공유가 필요하면 규칙이 다루는 모델과 규칙 함수만 `core` 모듈로 최소 단위로 올리고, 규칙을 쓰는 쪽 로직은 각 feature에 남깁니다.
- **모델 분리 최소 규칙**: 네트워크 DTO와 로컬 저장소 Entity를 Composable까지 노출하지 않습니다. 계층 경계에서 매퍼로 변환합니다.
- 도메인 모델과 UI 상태를 항상 나눌 필요는 없지만, 표시 포맷(문자열 포맷, 리소스 ID, 색상)은 UI 계층에서 만듭니다.
- **Repository 인터페이스 위치**: Domain 계층이 있으면 Domain에 인터페이스를 두고 구현을 Data에 둡니다. Domain 계층이 없으면 Data 안에 인터페이스와 구현을 두고 구현만 `internal`로 숨깁니다.

### 4. 의존성 방향

모듈 간 방향과 모듈 내 계층 방향은 강제 수단이 다르므로 따로 결정합니다.

**모듈 간 방향**

- 허용 방향은 `:app` → `:feature:*` → `:core:*` 한 방향입니다. `core`는 feature를 모르고, feature는 `:app`을 모릅니다.
- **feature 간 직접 의존을 금지합니다.** 공유가 필요하면 `core`로 올리고, 화면 이동은 이 스킬 5번 결정 항목의 라우트 계약으로 처리합니다. feature가 서로를 참조하기 시작하면 모듈을 쪼갠 이득이 사라집니다.
- `:app`만 모든 feature를 알고 DI 그래프와 `NavHost`를 조립합니다. 각 모듈은 자기 바인딩을 자기 DI 모듈로 선언하고 `:app`은 그것을 모으기만 합니다. `:app`에 특정 기능의 바인딩을 직접 쓰면 조립 지점이 기능 구현을 알게 됩니다.
- **`api`와 `implementation`**: 기본은 `implementation`입니다. 해당 타입이 모듈의 public API 시그니처에 드러날 때만 `api`를 씁니다. `api`를 남용하면 의존이 전이되어 Gradle 그래프가 경계를 강제하지 못합니다.

**모듈 내 계층 방향**

- 허용 방향은 ui → domain → data 한 방향입니다. data는 domain의 모델과 인터페이스만 알고, domain은 Android 프레임워크·Compose·HTTP 클라이언트·DB 라이브러리에 의존하지 않습니다.
- 계층 방향은 Gradle이 막아주지 않습니다. 패키지 규칙과 `internal`로 지키고 검증 수단을 따로 정합니다.

**공통**

- **강제 수단을 결정에 포함합니다.** 모듈 간 방향은 Gradle 의존 그래프와 `api`/`implementation` 구분이 1차 강제 수단입니다. 그래프로 막을 수 없는 규칙(모듈 내 계층 방향, 패키지 규칙)은 detekt 규칙, Android Lint, 구조 테스트 중 무엇으로 검증할지 정하고, 검증하지 않기로 했다면 그 사실을 명시합니다.
- 순환 의존을 발견하면 인터페이스를 아래 계층으로 내리거나 공통 타입을 `core`로 추출해 끊습니다. 우회 호출이나 리플렉션으로 덮지 않습니다.

### 5. 네비게이션

- 기본은 Single Activity + Compose 네비게이션입니다. Activity를 추가하는 결정은 외부 진입이나 시스템 연동 같은 명확한 이유가 있을 때만 내립니다.
- 라이브러리와 API 형태는 프로젝트의 버전 카탈로그와 실제 의존성을 읽어 확인합니다. Navigation Compose의 타입 안전 라우트와 Navigation 3의 백스택 상태 모델은 구성 방식이 다르므로 버전을 추측하지 않습니다.

**멀티 모듈에서 핵심 결정은 feature가 서로를 모르면서 화면을 이동하는 방법입니다.** 세 가지 선택지가 있습니다.

| 선택지 | 방식 | 트레이드오프 |
| --- | --- | --- |
| 콜백 위임(기본 권고) | 각 feature가 자기 그래프를 `NavGraphBuilder` 확장 함수로 노출하고, 다른 화면으로 가는 이동은 람다 파라미터로 밖에 넘김. `:app`이 그래프와 람다를 연결 | feature 간 의존이 0. feature가 늘면 `:app` 조립 코드가 길어짐 |
| 공용 라우트 모듈 | 라우트 타입만 `:core:navigation`에 모으고 모든 feature가 참조 | `:app` 조립이 단순해짐. 공용 모듈이 모든 화면을 알게 되고 라우트 변경이 전 모듈 재컴파일을 유발 |
| api·impl 분리 | feature를 `:feature:x:api`와 `:feature:x:impl`로 쪼개고 api만 참조 | 격리가 가장 강함. 모듈 수가 두 배가 되고 DI 배선이 복잡해짐 |

- feature 수가 적을 때는 콜백 위임으로 시작합니다. `:app` 조립 코드가 관리하기 어려워질 때 공용 라우트 모듈로 옮깁니다.
- 화면 간에는 식별자만 넘깁니다. 객체 전체나 직렬화한 응답을 라우트 인자로 넘기지 않습니다.
- 그래프는 인증, 온보딩, 메인 탭처럼 진입 조건이 다른 단위로 중첩 그래프를 나눕니다. 이 경계가 feature 모듈 경계와 어긋나면 둘 중 하나를 다시 봅니다.
- **백스택 규칙을 화면 단위로 정합니다**: 로그인·온보딩 완료 후 진입 화면을 백스택에서 제거할지, 탭 전환에서 각 탭 상태를 보존할지, 같은 화면 중복 push를 막을지, 폼 이탈 시 확인이 필요한지. 탭 상태 보존은 고려 사항 2번 항목 스킬의 상태 보존 결정과 같은 것이므로 한쪽에서만 정하고 다른 쪽은 참조합니다.
- **창 크기에 따라 화면이 합쳐지는 경우를 라우트 설계에 포함합니다.** 좁은 창에서 목록과 상세가 두 라우트인데 넓은 창에서 한 화면이 되면, 크기가 바뀔 때 백스택을 어떻게 옮길지 정해야 합니다. 어느 크기에서 합칠지는 고려 사항 6번 항목 스킬에서 정합니다.
- **네비게이션 호출 위치**: 화면 Composable은 이벤트를 위로 올리고(`onItemClick: (String) -> Unit`), `NavController`는 그래프 조립 지점에서만 다룹니다. 화면 Composable이 `NavController`를 직접 받으면 프리뷰와 단위 테스트가 어려워지고 feature가 네비게이션 구현에 묶입니다.
- 딥링크·알림 진입의 백스택 합성은 고려 사항 5번 항목(알림·외부 진입) 스킬에서 결정합니다. 여기서는 해당 라우트가 그래프에 존재하고 딥링크를 붙일 자리가 있는지만 확인합니다.

## 작업 흐름

1. **현재 구조를 읽습니다.** 추측하지 않습니다. 최소한 다음을 확인합니다.
   - `settings.gradle.kts`의 모듈 목록과 포함 빌드
   - 모듈별 `build.gradle.kts`의 프로젝트 의존성, `api`와 `implementation` 사용, convention plugin 적용 여부
   - 각 모듈의 패키지 트리와 public 타입
   - `NavHost`, 라우트 정의, 그래프 조립 지점, Activity 개수
   - 버전 카탈로그의 네비게이션·DI·직렬화 도입 여부
2. **5개 항목을 순서대로 검토합니다.** 이미 결정된 항목은 근거를 확인하고 넘어갑니다. 결정과 코드가 어긋나면 위반으로 보고합니다.
3. **각 항목마다 선택지 → 판단 기준 적용 → 권고 하나 → 트레이드오프 1~2줄** 순서로 답합니다. 선택지를 나열만 하고 끝내지 않습니다.
4. **감사 대상 코드가 있으면 위반을 `파일:라인`으로 지적합니다.** 각 위반에 수정 규모(파일 이동, 모듈 추가, 인터페이스 추출, 라우트 변경 등)를 함께 적습니다.
5. **결정할 수 없는 항목은 미결정으로 남깁니다.** 무엇을 알면 결정할 수 있는지 함께 적습니다.
6. **코드 변경은 사용자 승인 후에 합니다.** 이 스킬의 산출물은 결정과 감사 결과입니다.
