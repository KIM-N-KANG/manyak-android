# 빌드 정책

## 목적

빌드가 조용히 어긋나는 것을 막는 작업 스킬입니다. 구성을 읽어 정책과 어긋난 곳을 찾고 고칩니다.

고려 사항 8번 항목 스킬과 경계가 있습니다. **무엇을 언제 실행하고 무엇으로 배포를 막을지는 그쪽에서 정합니다.** 이 스킬은 **빌드 자체가 일관되게 성공하거나 시끄럽게 실패하는지**를 봅니다. 환경 분리, 서명, 배포 절차는 여기서 다루지 않습니다.

## 선행 전제: 버전 조합을 이 문서에 적지 않습니다

**버전과 toolchain 값은 실제 파일에서 읽습니다.** `gradle/libs.versions.toml`, `app/build.gradle.kts`, `gradle/wrapper/gradle-wrapper.properties`, Gradle 데몬 toolchain 설정, CI 워크플로가 출처입니다. 하네스 저장소의 안드로이드 플랫폼 문서에도 확인된 값이 정리되어 있습니다.

여기에 표로 옮겨 적으면 사본이 하나 더 늘고, 버전을 올릴 때 이 문서만 낡습니다. **낡은 버전 표는 없는 것보다 나쁩니다.** 읽는 사람이 그것을 믿기 때문입니다.

읽은 값이 서로 어긋나면 그것이 곧 이 스킬이 찾는 문제입니다.

## 적용 범위 판단

| 요청 | 하는 일 |
| --- | --- |
| 빌드 구성 감사 | 아래 정책 항목 전부 점검 |
| 버전 올리기, 플러그인 추가 | 조합 정렬, 생성 코드 실패 검출, 전체 variant 컴파일 |
| CI에서만 깨지는 문제 | 명령 일치, 환경 차이, 캐시 |
| 빌드가 느림 | 구성 캐시, 빌드 캐시, 병렬 설정 |
| 정적 검사 정책 조정 | 경고 처리 범위, 억제 목록 |
| 출시 빌드 준비 | 축소를 켠 빌드, 전체 variant 컴파일 |

## 이미 결정된 항목

빌드 정책은 대부분 프로젝트에서 한 번 정하면 그대로 갑니다. `docs/plans/_project.md`를 먼저 확인해 결정이 있으면 다시 정하지 않고 구성이 그것을 지키는지만 봅니다. 없으면 정하고 문서에 남깁니다.

## 정책 항목

### 1. 버전 조합과 toolchain 정렬

- **빌드에 쓰는 JDK와 산출물의 바이트코드 타깃은 다른 값입니다.** 둘을 같은 것으로 보고 맞추려 들면 최소 지원 기기에서 깨지거나 빌드가 안 됩니다.
- **Gradle 데몬 toolchain과 CI의 JDK를 일치시킵니다.** 어긋나면 Gradle이 데몬용 JDK를 따로 내려받아 빌드가 느려집니다. 느려지는 것으로 끝나므로 아무도 알아채지 못한 채 계속 갑니다.
- **Kotlin과 Compose 컴파일러 플러그인은 함께 움직입니다.** 한쪽만 올리면 컴파일이 실패하거나 런타임에 어긋납니다.

### 2. 경고 처리 범위

- **경고를 오류로 볼 범위를 정합니다.** 전부 오류로 하면 라이브러리 업데이트마다 빌드가 멈추고, 아무것도 오류로 하지 않으면 경고가 수백 개 쌓여 새 경고가 묻힙니다.
- **더 이상 지원하지 않는 API 사용은 최소한 눈에 띄게 합니다.** 경고 목록에 묻히면 다음 SDK 상향에서 한꺼번에 터집니다.

### 3. 억제 목록

- **정적 검사의 억제 목록이 늘어나지 않게 막습니다.** 목록에 추가하는 것이 고치는 것보다 쉬우면 반드시 목록이 자랍니다.
- **억제할 때는 이유를 남깁니다.** 이유 없는 억제는 나중에 지워도 되는지 판단할 수 없어 영원히 남습니다.
- 기존 코드를 한 번에 고칠 수 없어 목록을 만들었다면, **줄여 나갈 계획과 함께** 둡니다.

### 4. 의존성 고정

- **버전 카탈로그 한 곳에서 관리합니다.** 모듈마다 버전을 적으면 같은 라이브러리가 두 버전으로 들어옵니다.
- **범위 지정 버전을 쓰지 않습니다.** 어제 되던 빌드가 오늘 깨지고, 무엇이 바뀌었는지 저장소에 기록이 없습니다.
- **고정과 검증을 켤지 정합니다.** 켜면 재현성이 올라가고 공급망 위험이 줄지만, 의존성을 바꿀 때마다 갱신 절차가 붙습니다.

### 5. variant 컴파일

- **디버그만 컴파일하고 끝내지 않습니다.** 축소와 리소스 축소를 켠 빌드에서만 드러나는 문제가 있습니다. 반사로 접근하는 코드, 직렬화 대상, 생성 코드가 그렇습니다.
- **축소를 켠 빌드를 실제로 만들어 봅니다.** 설정만 켜 두고 만들어 보지 않으면 출시 직전에 처음 실패합니다.
- 출시 전에는 **그 빌드로 주요 흐름을 실행**합니다. 컴파일 성공은 실행 성공이 아닙니다.

### 6. 생성 코드

- **코드 생성 실패가 빌드 실패로 이어지는지 확인합니다.** 생성이 조용히 건너뛰어지면 컴파일은 통과하고 실행에서 죽습니다.
- 생성 도구를 추가하면 **캐시가 비워진 상태에서 한 번 빌드**해 봅니다. 증분 빌드에서만 되는 구성이 있습니다.

### 7. 캐시와 속도

- **구성 캐시와 빌드 캐시를 켤지 정합니다.** 켜면 빠르지만 호환되지 않는 설정 방식이 있어서, 빌드 스크립트를 쓸 때 그 제약을 알고 써야 합니다.
- **호환되지 않는 구성을 발견하면 캐시를 끄지 말고 구성을 고칩니다.** 한 번 끄면 다시 켜지지 않습니다.

### 8. CI와 로컬의 일치

- **같은 명령을 씁니다.** CI에서만 도는 명령이 있으면 그 검사는 로컬에서 통과할 수 없고, 개발자는 결과를 기다렸다가 고치게 됩니다.
- **패키징까지 확인합니다.** 검사 명령이 패키징을 포함하지 않으면 리소스와 매니페스트 문제를 놓칩니다.
- **CI가 실패했을 때 볼 수 있는 것을 남깁니다.** 리포트가 남지 않으면 로그만 보고 원인을 짐작하게 됩니다.

## 작업 흐름

1. **실제 구성을 읽습니다.** 버전 카탈로그, 모듈 빌드 스크립트, Gradle 래퍼와 데몬 설정, CI 워크플로. 추측하지 않습니다.
2. **`_project.md`에 빌드 결정이 있는지 확인합니다.**
3. **위 8개 항목을 점검합니다.** 어긋난 것을 찾아 근거와 함께 적습니다.
4. **읽은 값끼리 어긋나는 곳을 먼저 보고합니다.** toolchain과 CI JDK, Kotlin과 컴파일러 플러그인이 대표적입니다.
5. **고칠 것과 결정이 필요한 것을 나눕니다.** 켤지 말지는 사용자가 정합니다.
6. **바꾼 뒤에는 실제로 빌드해 확인합니다.** 명령 선택은 `android-change-verification` 스킬을 씁니다.
7. **새로 내린 결정을 `_project.md`에 남깁니다.**
