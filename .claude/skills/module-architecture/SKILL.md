# 앱 구조

## 목적

프로젝트가 선택한 모듈 전략과 상태 흐름을 실제 책임·의존 경계로 구체화합니다. 필요한 경계만 만들되 확정된 멀티 모듈 결정을 다시 보류하지 않습니다.

## 프로젝트 결정 우선

`docs/plans/_project.md`와 실제 `settings.gradle.kts`를 먼저 읽습니다. 현재 결정과 다른 구조가 필요할 때만 선택지와 전환 비용을 제시하고 프로젝트 결정을 갱신합니다.

## 모듈 경계

프로젝트가 멀티 모듈을 채택했다면 첫 구조 계획에서 초기 모듈과 전환 순서를 정합니다. 각 모듈에는 책임, 공개 계약, 허용 의존 방향이 있어야 합니다.

- `:app`은 조립과 앱 진입을 담당하고 기능 구현을 직접 소유하지 않게 합니다.
- 기능 모듈은 제품 기능과 진입 경계를 기준으로 나누며 화면 하나마다 만들지 않습니다.
- 둘 이상의 기능이 사용하는 안정된 계약만 공통 모듈 후보로 둡니다.
- 의존성 격리, 독립 소유·테스트, 빌드 경계 중 무엇을 얻는지 설명할 수 있어야 합니다.

공통 사용처가 하나뿐인 코드를 미리 `core`로 올리지 않습니다. 전환 중에는 모듈 수를 맞추기 위해 무관한 코드를 함께 옮기지 않습니다. convention plugin은 반복되는 모듈 설정이 실제로 생겼을 때 도입합니다.

## UDF와 의존성

- 상태 소유자는 불변 UI 상태를 내리고 UI는 사용자·시스템 이벤트를 올리는 UDF를 적용합니다.
- 상태 전이는 상태 소유자 한 곳에서 수행하고 부수 효과의 결과도 같은 상태 흐름에 반영합니다. UI는 저장소 호출이나 상태 변경을 직접 수행하지 않습니다.
- UDF는 Domain·UseCase 계층을 요구하지 않습니다. 여러 저장소를 조합하거나 재사용되는 비즈니스 규칙이 있을 때만 별도 계층을 둡니다.
- Repository를 그대로 호출하는 pass-through UseCase는 만들지 않습니다.
- 모듈 간 허용 의존 방향을 구조 계획에 명시하고 순환을 허용하지 않습니다. 기능 간 협력은 편의를 위한 직접 구현 의존 대신 조립 지점이나 공개 계약을 사용합니다.

## 네비게이션

- 화면에는 이동 객체 대신 값과 콜백을 전달합니다.
- 라우트에는 복원 가능한 식별자만 넘기고 화면 데이터는 목적지에서 다시 얻습니다.
- 인증·온보딩 완료 후 제거할 화면, 외부 진입의 부모 화면, 중복 진입 처리를 실제 흐름에 맞게 정합니다.
- 창 크기에 따라 화면 구성이 달라질 때만 adaptive layout과 백스택의 관계를 함께 결정합니다.

## 결과

선택한 경계, 근거, 의존 방향, UDF의 상태·이벤트 소유자, 이동 계약과 전환 비용만 보고합니다. 감사에서는 위반을 파일과 줄로 지적합니다. 구조 변경이 이미 요청 범위에 포함되어 있으면 추가 승인을 묻지 않습니다.
