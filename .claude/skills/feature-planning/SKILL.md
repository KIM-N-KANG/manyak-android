# 기능 개발 계획

## 목적

구현 전에 확정해야 하는 결정만 골라 의존 순서가 있는 계획으로 만듭니다. 계획의 크기는 호출된 스킬 수가 아니라 변경을 되돌리는 비용으로 판단합니다.

## 계획이 필요한 경우

다음 중 하나면 계획을 만듭니다.

- 사용자가 계획이나 설계를 요청했습니다.
- 새 API 계약, 사용자 데이터 저장소·마이그레이션, 인증·개인정보·권한 정책이 생깁니다.
- 새 모듈 경계, 백그라운드 작업, 알림·딥링크, 배포 정책을 정해야 합니다.
- 여러 영역의 순서가 얽혀 뒤 단계가 앞 단계를 뒤집을 수 있습니다.

기존 프로젝트 결정을 그대로 따르는 국소 변경과 재생성 가능한 캐시의 채움 규칙이 확정된 단순 additive 스키마 변경은 짧은 구현 순서만 제시하고 계획 문서를 만들지 않습니다. 스킬 개수로 기능 분할 여부를 판단하지 않습니다.

## 작업 흐름

1. 하네스의 관련 제품 문서, `docs/plans/_project.md`, 변경이 닿는 코드를 읽습니다.
2. 이미 확정된 결정과 이번에 새로 정해야 할 결정을 나눕니다.
3. 현재 환경이 제공하는 스킬 목록의 설명으로 필요한 스킬만 고릅니다. 모든 `SKILL.md`를 훑지 않습니다.
4. 선택한 스킬에서는 이번 결정에 필요한 항목만 적용합니다. 기존 결정 준수 여부만 확인하면 되는 스킬은 호출하지 않습니다.
5. 결정, 외부 합의가 필요한 항목, 구현 순서를 합칩니다. 막히지 않는 단계는 병렬로 표시합니다.
6. 검증은 실행하지 않고 `android-change-verification`에 넘길 위험 태그와 확인 시점만 적습니다.
7. 여러 기능이 따라야 하는 프로젝트 공통 기술 결정이 실제로 바뀌면 이유와 함께 `_project.md`를 갱신합니다.

## 계획 문서

되돌리기 비싼 결정이 있거나 사용자가 문서화를 요청했을 때만 `docs/plans/{기능}.md`를 만듭니다.

문서에는 다음만 남깁니다.

- 기능 목표와 제외 범위
- 이번 기능에서 새로 내린 결정과 근거
- 서버·제품·디자인 합의가 필요한 항목과 막는 단계
- 의존 순서가 있는 구현 단계와 확인 가능한 완료 조건
- 검증 위험 태그와 실행 시점

일반론, 기존 프로젝트 결정의 복사본, 전체 스킬 체크리스트는 넣지 않습니다.

## 검토와 실행 경계

- `plan-critique`는 사용자가 요청했거나 계획에 새 계약, 사용자 소유 데이터의 비가역적 변경, 인증·권한·배포 결정이 있을 때만 사용합니다.
- 계획만 요청받았다면 코드를 바꾸지 않습니다.
- 구현까지 요청받았다면 계획 완료 후 다시 승인을 묻지 않고 구현을 계속합니다.
- 계획을 바꾸는 데 꼭 필요한 정보만 질문하고, 나머지는 근거가 있는 기본값으로 진행합니다.
