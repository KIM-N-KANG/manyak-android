# 알림·외부 진입

## 목적

안드로이드 앱 개발 고려 사항 8개 항목 중 5번 **알림·외부 진입**을 담당합니다. 아래 7개 결정 항목을 각각 명시적으로 결정하거나, 기존 코드가 이미 내린 결정을 확인하고 위반을 지적합니다.

| 결정 항목 | 결정할 내용 |
| --- | --- |
| 1. 권한 요청 시점 | 알림 권한을 언제 요청하고 거부 상태를 어떻게 다룰지 |
| 2. 종류와 채널 | 알림 종류를 어떻게 나누고 채널을 어떻게 구성할지 |
| 3. 등록 토큰 | 발급·갱신·등록 실패를 어떻게 처리할지 |
| 4. 멀티 디바이스 | 한 사용자의 여러 기기에 알림을 어떻게 다룰지 |
| 5. 중복·지연·순서 | 중복되거나 늦게 오거나 순서가 바뀐 알림을 어떻게 처리할지 |
| 6. 진입 경로와 도착 화면 | 딥링크·앱링크·알림 클릭을 어떤 화면으로 연결할지 |
| 7. 앱 상태별 진입 흐름 | 앱 종료 상태와 실행 중 상태의 진입을 어떻게 구분할지 |

## 선행 전제: 앱 밖에서 들어오는 입력입니다

알림과 외부 링크는 앱이 통제하지 못하는 입력입니다. 도착 여부, 도착 시각, 순서, 내용의 신선도를 앱이 보장할 수 없습니다. 여기서 두 가지 규칙이 나옵니다.

- **페이로드를 표시 데이터로 믿지 않습니다.** 페이로드는 "무엇을 열지"만 알려주는 것으로 보고, 화면에 그릴 내용은 진입 후 다시 조회합니다. 늦게 도착한 알림의 내용은 이미 낡았습니다.
- **진입 경로가 여러 개여도 도착 화면 상태는 하나로 수렴해야 합니다.** 완전 종료 상태 진입, 실행 중 진입, 앱 안에서의 이동이 서로 다른 화면 상태를 만들면 경로마다 다른 버그가 생깁니다.

## 적용 범위 판단

요청 규모에 맞는 항목만 검토합니다.

| 요청 | 검토할 항목 |
| --- | --- |
| 푸시 도입, 알림·진입 리뷰·감사 | 1~7 전부 |
| 새 알림 종류 추가 | 2, 5, 6 |
| 알림이 안 오는 문제 진단 | 1, 2, 3 |
| 알림이 두 번 오거나 순서가 이상한 문제 | 5 |
| 딥링크·앱링크 추가 | 6, 7 |
| 알림 클릭 후 화면·뒤로 가기 문제 | 6, 7 |

## 결정 항목별 판단 기준

### 1. 권한 요청 시점

- **두 경로를 모두 처리합니다.** 안드로이드 13부터 알림은 런타임 권한이고, 그 이전 버전 기기는 기본 허용 상태입니다. 권한 요청 코드만 두고 하위 버전 동작을 확인하지 않으면 기기별로 갈립니다.
- **첫 실행에 바로 요청하지 않습니다.** 알림의 쓸모를 모르는 시점의 요청은 거부되기 쉽고, 거부되면 시스템 대화상자를 다시 띄울 수 없습니다. 한 번의 요청을 어디에 쓸지 정하는 것이 이 항목의 핵심입니다.
- 요청 시점 후보: 알림이 실제로 의미를 갖는 동작을 사용자가 한 직후, 설정 화면에서 사용자가 직접 켤 때, 온보딩 마지막 단계.
- **요청 전에 앱 화면으로 이유를 설명합니다.** 시스템 대화상자는 이유를 말해 주지 않습니다.
- **거부와 영구 거부 이후 경로를 만듭니다.** 시스템 설정으로 안내하고, 앱 안에서 알림이 꺼져 있다는 사실을 보여줍니다.
- **권한이 있어도 채널이 꺼져 있으면 표시되지 않습니다.** 앱 설정 화면에서 실제 시스템 상태를 읽어 보여줄지 정합니다. 앱 안의 알림 설정 토글이 시스템 상태와 어긋나면 사용자는 켰다고 믿습니다.

### 2. 종류와 채널

- **채널은 사용자가 끄는 단위입니다.** 이것이 유일한 분류 기준입니다. 성격이 다른 알림을 한 채널에 담으면 사용자는 하나가 싫어서 전부 끕니다. 반대로 채널이 지나치게 많으면 설정 화면을 이해할 수 없습니다.
- **채널마다 정할 것**: 중요도(소리와 헤드업 표시 여부), 진동, 잠금화면 표시 수준.
- **채널 설정은 만든 뒤 앱이 바꿀 수 없습니다.** 사용자가 조정한 값이 항상 우선하고, 앱이 중요도를 바꾸려면 새 채널을 만들어야 합니다. 초기 구성을 신중하게 정합니다.
- **채널을 지웠다가 같은 ID로 다시 만들면 이전 설정이 되살아납니다.** 삭제와 이름 변경은 사용자에게 그대로 보입니다.
- **누적 표시 방식을 정합니다.** 같은 종류가 여러 개 쌓일 때 개별로 남길지 하나로 묶을지. 대화형은 묶고, 각각 조치가 필요한 것은 따로 둡니다.
- **알림 액션과 스와이프 제거 처리를 정합니다.** 액션 버튼을 두면 앱을 열지 않고 처리되므로 처리 후 알림을 지우고 결과를 서버에 반영하는 경로가 필요합니다. 사용자가 스와이프로 지운 것을 서버에 알릴지도 함께 정합니다.
- **잠금화면과 미리보기에 민감한 내용이 나오지 않게 합니다.** 무엇을 가릴지는 고려 사항 4번 항목 스킬과 함께 정합니다.

### 3. 등록 토큰

- **토큰은 언제든 바뀝니다**: 재설치, 앱 데이터 삭제, 기기 복원, 서버 무효화. 갱신 콜백을 받아 서버에 다시 등록하는 경로가 없으면 어느 날부터 알림이 조용히 끊깁니다.
- **서버 등록 실패를 조용히 넘기지 않습니다.** 등록 실패는 알림이 영영 오지 않는다는 뜻입니다. 재시도를 지속 작업으로 처리할지 고려 사항 2번 항목 스킬의 결정과 함께 정합니다.
- **등록 시점을 정합니다.** 사용자와 연결해야 하므로 보통 로그인 이후입니다. 로그인 전 알림이 필요하면 기기 단위 등록을 별도로 설계합니다.
- **로그아웃 시 등록 해제를 함께 정합니다.** 해제하지 않으면 로그아웃한 기기로 이전 사용자의 알림이 계속 갑니다. 이 항목은 고려 사항 4번 항목 스킬의 로그아웃 삭제 목록에 포함되어야 합니다.
- **토큰과 사용자의 매핑은 서버가 관리합니다.** 클라이언트는 현재 토큰과 현재 사용자를 알리는 역할만 합니다.
- **앱이 꺼져 있는 동안 갱신될 수 있습니다.** 다음 실행 시 현재 토큰이 서버에 등록된 것과 같은지 확인하는 경로를 둡니다.

### 4. 멀티 디바이스

- 전송 대상 결정은 서버가 하지만, 클라이언트가 동작을 설명하려면 정책을 알아야 합니다: 모든 기기에 보낼지, 최근 사용 기기에만 보낼지.
- **읽음·처리의 전파를 정합니다.** 한 기기에서 확인한 알림이 다른 기기에서도 사라져야 하는지. 필요하면 서버가 취소 신호를 보내고 클라이언트가 표시된 알림을 지우는 경로가 있어야 합니다.
- **죽은 토큰 정리를 확인합니다.** 재설치와 기기 교체로 무효 토큰이 쌓입니다. 서버가 전송 실패 응답으로 정리하는지 확인합니다.
- **알림 대상 사용자와 현재 로그인 사용자가 다를 수 있습니다.** 로그아웃 후 다른 계정으로 로그인한 기기에 이전 알림이 남아 있는 경우의 동작을 정합니다. 그대로 열면 남의 데이터를 요청하게 됩니다.

### 5. 중복·지연·순서

**전달 방식을 먼저 정합니다.** 이 선택이 아래 규칙을 적용할 수 있는지 자체를 결정합니다.

| 방식 | 백그라운드 동작 | 제어 범위 |
| --- | --- | --- |
| 시스템이 바로 표시 | 앱 코드가 실행되지 않고 시스템이 표시 | 중복 제거, 순서 검사, 알림 ID 제어를 할 수 없음 |
| 앱이 받아서 표시 | 앱 코드가 실행된 뒤 앱이 표시 | 아래 규칙을 모두 적용할 수 있음. 절전 상태에서 지연·유실 가능 |

중복 제거와 순서 검사를 하려면 앱이 메시지를 받아 처리하는 방식이어야 합니다. 시스템이 바로 표시하는 방식을 쓰면서 아래 규칙을 설계하면 구현 단계에서 전부 불가능해집니다. 방식 선택은 서버 전송 형식과 묶여 있으므로 합의 항목에 넣습니다.

- **전달도 순서도 보장되지 않습니다.** 지연, 중복, 유실, 순서 역전을 예외가 아니라 정상 상황으로 두고 설계합니다.
- **지연과 유실의 원인을 알고 설계합니다.** 절전 상태와 배터리 최적화로 전달이 미뤄집니다. 즉시성이 필요한 알림만 높은 우선순위로 보내고, 전부를 높은 우선순위로 보내면 시스템이 앱 전체를 제한할 수 있습니다. 우선순위는 서버 전송 설정이므로 합의 항목에 넣습니다.
- **중복 제거**: 메시지에 고유 식별자를 넣고 최근 처리한 식별자를 기억해 같은 것을 두 번 표시하지 않습니다. 식별자는 서버가 발급해야 하므로 페이로드 계약에 포함합니다.
- **순서 역전**: 페이로드에 발생 시각이나 버전을 넣고, 이미 더 최신 상태를 반영했다면 오래된 알림은 무시합니다.
- **지연 도착**: 이미 처리되거나 취소된 일에 대한 알림이 뒤늦게 올 수 있습니다. 표시 전에 아직 유효한지 판단할 근거를 페이로드에 넣습니다.
- **알림 ID 설계**: 같은 대상의 갱신은 같은 ID로 덮어쓰고, 다른 대상은 다른 ID로 쌓습니다. 전부 같은 ID면 알림이 하나만 남고, 전부 다르면 무한히 쌓입니다.
- **표시 내용을 페이로드에만 의존하지 않습니다.** 알림 문구는 페이로드로 그리더라도, 진입 후 화면 내용은 다시 조회합니다.

### 6. 진입 경로와 도착 화면

- **진입 경로를 먼저 나열합니다**: 알림 클릭, 검증된 도메인 링크, 커스텀 스킴 링크, 다른 앱의 공유·인텐트, 바로가기·위젯.
- **모든 진입 경로는 그래프의 기존 라우트로 연결합니다.** 진입 전용 화면을 따로 만들면 앱 안에서의 이동과 외부 진입이 서로 다른 화면을 갖게 됩니다. 라우트 구성은 고려 사항 1번 항목 스킬에서 정합니다.
- **파라미터를 검증합니다.** 외부에서 온 값은 신뢰하지 않습니다. 형식이 어긋나거나 대상이 없으면 안전한 기본 화면으로 보내고, 아무 화면도 없이 종료되지 않게 합니다. 검증 원칙은 고려 사항 4번 항목 스킬과 같습니다.
- **인증이 필요한 대상이면 로그인 후 원래 대상으로 이어지게 합니다.** 로그인 화면으로 보내고 끝나면 사용자는 링크를 다시 눌러야 합니다.
- **삭제되었거나 접근 권한이 없는 대상**을 열었을 때 보여줄 화면을 정합니다. 빈 화면이나 무한 로딩으로 두지 않습니다.
- **도메인 링크는 검증이 필요합니다.** 검증에 실패하면 앱이 아니라 브라우저로 열리거나 선택 대화상자가 뜹니다. 검증 상태 확인을 배포 점검에 포함하는 것은 고려 사항 8번 항목 스킬에서 정합니다.

### 7. 앱 상태별 진입 흐름

- **세 가지 상태를 구분합니다**: 프로세스가 없는 완전 종료, 백그라운드에 있음, 화면을 보고 있는 실행 중.
- **완전 종료 상태 진입**: 앱이 처음부터 시작하므로 인증 상태 판단과 초기화가 끝난 뒤 대상 화면으로 가야 합니다. 초기화 전에 이동하면 빈 화면이 뜨거나 로그인 화면으로 튕깁니다. 시작 경로는 고려 사항 4번 항목 스킬의 앱 시작 인증 판단과 같은 자리입니다.
- **백스택 합성을 정합니다.** 알림으로 상세 화면에 바로 들어갔을 때 뒤로 가기가 앱을 닫을지, 목록 화면으로 갈지. 사용자가 앱 안에 남을 수 있는 경로를 만드는 편이 보통 낫습니다.
- **실행 중 진입**: 이미 그 화면을 보고 있으면 같은 화면을 다시 쌓지 않고 내용만 갱신합니다. 다른 화면이면 현재 백스택 위에 쌓을지, 특정 지점까지 정리하고 이동할지 정합니다.
- **진입 정보를 한 번만 처리합니다.** 처리 후 지우지 않으면 구성 변경이나 화면 복귀 때 같은 이동이 다시 일어납니다. 프로세스 종료 복원 대상에 포함할지도 함께 정하며, 이는 고려 사항 2번 항목 스킬의 결정과 이어집니다.
- **알림 정리 시점을 정합니다.** 클릭으로 진입했을 때 그 알림을 지울지, 같은 대상의 다른 알림도 함께 지울지 정합니다. 앱 안에서 이미 처리한 항목의 알림이 떠 있으면 지울지도 함께 정합니다. 정리하지 않으면 이미 읽은 것이 알림 목록에 계속 남습니다.
- **앱을 보고 있는 중에 도착한 알림의 표시 방식을 정합니다**: 시스템 알림으로 띄울지, 앱 안 배너로 보여줄지, 무시하고 화면만 갱신할지.

## 작업 흐름

1. **알림 종류와 진입 경로를 나열합니다.** 추측하지 않고 실제 메시지 수신 지점, 인텐트 필터, 라우트 정의를 읽습니다.
2. **채널 구성을 먼저 정합니다.** 사용자가 끄고 싶어 할 단위가 기준이며, 나중에 바꾸기 어렵습니다.
3. **권한 요청 시점과 거부 이후 경로를 정합니다.**
4. **등록·갱신·해제 경로를 정합니다.** 로그아웃 시 해제를 고려 사항 4번 항목의 삭제 목록과 맞춥니다.
5. **중복·순서 처리 규칙을 정합니다.** 필요한 페이로드 필드를 함께 적습니다.
6. **진입 경로를 라우트에 매핑하고 실패 대상의 도착 화면을 정합니다.**
7. **앱 상태별 진입 흐름과 백스택을 정의합니다.** 세 상태 각각에 대해 적습니다.
8. **서버와 합의가 필요한 항목을 따로 모읍니다.** 페이로드 스키마, 메시지 식별자, 발생 시각, 취소 신호, 멀티 디바이스 전송 정책은 클라이언트 혼자 정할 수 없습니다.
9. **검증 시나리오를 씁니다.** 아래 표에서 이 변경에 필요한 항목을 고릅니다.
10. **결정할 수 없는 항목은 미결정으로 남기고, 코드 변경은 사용자 승인 후에 합니다.**

### 검증 시나리오

| 시나리오 | 확인 방법 | 검증 대상 |
| --- | --- | --- |
| 완전 종료 상태 진입 | 최근 앱에서 앱을 닫은 뒤 알림 클릭 | 7번 결정 항목 |
| 실행 중 같은 화면 진입 | 대상 화면을 보는 중에 같은 알림 클릭 | 7번 결정 항목 |
| 진입 후 뒤로 가기 | 알림으로 들어간 뒤 뒤로 가기 | 7번 결정 항목(백스택) |
| 중복·지연 | 같은 알림을 두 번 보내고, 이미 처리된 대상의 알림을 늦게 보냄 | 5번 결정 항목 |
| 권한 거부 상태 | 거부·영구 거부 상태에서 알림 발송 | 1번 결정 항목 |
| 채널만 끔 | 권한은 허용한 채 특정 채널만 끄고 발송 | 2번 결정 항목 |
| 토큰 갱신 | 앱 데이터를 지우고 재실행한 뒤 알림 발송 | 3번 결정 항목 |
| 다른 사용자 상태 | 로그아웃 후 다른 계정으로 로그인한 상태에서 이전 알림 클릭 | 4번, 6번 결정 항목 |
| 잘못된 링크 | 없는 식별자나 형식이 깨진 파라미터로 링크 실행 | 6번 결정 항목 |
| 절전 상태 | 기기를 절전 상태로 두고 한참 뒤 발송 | 5번 결정 항목(지연·유실) |

완전 종료 상태 진입과 채널만 끈 상태는 개발 중에 거의 재현되지 않습니다. 개발 기기는 앱이 대개 실행 중이고 채널 설정은 기본값 그대로이기 때문입니다.
