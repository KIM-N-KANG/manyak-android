# 빌드·배포·운영

## 목적

안드로이드 앱 개발 고려 사항 8개 항목 중 8번 **빌드·배포·운영**을 담당합니다. 아래 7개 결정 항목을 각각 명시적으로 결정하거나, 기존 구성이 이미 내린 결정을 확인하고 위반을 지적합니다.

| 결정 항목 | 결정할 내용 |
| --- | --- |
| 1. 환경 분리 | 개발·스테이징·운영 환경을 어떻게 나눌지 |
| 2. 환경별 설정 | 환경마다 다른 API·인증·푸시 설정을 어떻게 관리할지 |
| 3. 비밀 정보 | 서명키와 비밀 값을 어떻게 보호할지 |
| 4. CI 검사 | CI에서 어떤 검사와 테스트를 실행할지 |
| 5. 구버전 호환성 | 구버전 앱과 최신 서버의 호환성을 어떻게 유지할지 |
| 6. 배포·롤백·강제 업데이트 | 단계적 배포, 문제 발생 시 대응, 업데이트 강제를 어떻게 할지 |
| 7. 긴급 차단 | 배포 없이 기능을 중단하거나 제한할 수단이 있는지 |

## 선행 전제: 배포한 앱은 회수할 수 없습니다

서버는 배포를 되돌리면 모든 사용자가 즉시 이전 버전으로 돌아갑니다. 앱은 그렇지 않습니다. 이미 설치된 버전은 회수되지 않고, 롤백은 "수정 버전을 다시 만들어 심사받아 올리고 사용자가 업데이트하기를 기다리는 것"입니다. 그동안 사용자는 문제 버전을 계속 씁니다.

여기서 두 가지가 따라옵니다.

- **배포 전 검증과 단계적 노출이 사실상 유일한 방어선입니다.** 배포 후 대응은 항상 느립니다.
- **앱을 고치지 않고 끌 수 있는 수단이 필요합니다.** 이 수단은 사고가 난 뒤에는 만들 수 없습니다. 지금 배포하는 버전에 들어 있어야 다음 사고에서 씁니다.

두 번째가 이 항목에서 가장 자주 빠지는 결정입니다.

## 적용 범위 판단

요청 규모에 맞는 항목만 검토합니다.

| 요청 | 검토할 항목 |
| --- | --- |
| 프로젝트 초기 구성, 배포 구성 리뷰·감사 | 1~7 전부 |
| 새 환경 추가, 환경 설정 변경 | 1, 2, 3 |
| CI 파이프라인 구성·변경 | 4 |
| 출시 준비 | 4, 5, 6, 7 |
| 배포 후 문제 대응 | 6, 7 |
| API 변경·최소 지원 버전 조정 | 5, 6 |

## 결정 항목별 판단 기준

### 1. 환경 분리

- **환경 목록과 각 환경이 보는 서버를 확정합니다.** 개발, 운영과 같은 구성의 스테이징, 운영이 기본입니다.
- **빌드 방식과 환경을 분리해서 다룹니다.** 디버그·릴리스는 빌드 방식이고 환경은 대상 서버입니다. 축소와 난독화를 켠 릴리스 빌드로 스테이징을 확인해야 하는 상황이 반드시 생기므로, 두 축을 조합할 수 있어야 합니다.
- **한 기기에 여러 환경을 동시에 설치할 수 있게 합니다.** 앱 식별자를 환경마다 다르게 하고 앱 이름과 아이콘으로도 구분되게 합니다. 구분되지 않으면 테스터가 어느 환경을 보고 있는지 모른 채 보고합니다.
- **운영 빌드에서 개발용 기능이 꺼지는지 확인합니다**: 상세 로깅, 디버그 메뉴, 테스트 계정, 평문 통신 허용. 확인 방법은 고려 사항 4번 항목 스킬의 노출 경로 점검과 같습니다.
- **앱 안에서 환경을 전환하게 할지 정합니다.** 편리하지만 운영 빌드에 남으면 사용자가 개발 서버에 접속할 수 있습니다.

### 2. 환경별 설정

- **환경마다 달라지는 항목을 나열합니다**: API 주소, 인증 제공자 설정, 푸시 서비스 설정, 크래시·분석 도구의 프로젝트, 기능 플래그 기본값.
- **주입 지점을 한 곳으로 모읍니다.** 설정이 여러 파일에 흩어지면 환경을 추가할 때 반드시 일부를 빠뜨리고, 그 빠뜨림은 운영에서 드러납니다.
- **푸시와 인증은 환경별로 프로젝트를 분리합니다.** 공유하면 개발 중 테스트 알림이 운영 사용자에게 갑니다. 등록 토큰 관리는 고려 사항 5번 항목 스킬에서 정합니다.
- **설정이 없으면 빌드가 실패하게 합니다.** 기본값으로 조용히 넘어가면 운영 빌드가 개발 서버를 보게 되고, 아무도 모릅니다.
- **앱에 들어가는 값은 공개된다고 봅니다.** 앱에 포함된 설정은 추출할 수 있으므로 서버 비밀은 넣지 않습니다. 이 전제는 고려 사항 4번 항목 스킬과 같습니다.

### 3. 비밀 정보

- **서명키를 잃으면 같은 앱으로 업데이트할 수 없습니다.** 보관 위치, 백업, 접근 권한을 명시적으로 정합니다. 스토어가 제공하는 키 관리 방식을 쓸지도 함께 결정합니다.
- **키와 비밀 값을 저장소에 넣지 않습니다.** CI 비밀 저장소나 로컬 설정 파일로 주입하고 저장소에는 예시 파일만 둡니다.
- **실수로 커밋된 비밀은 이력에 남습니다.** 파일을 지우는 것으로 끝나지 않으므로, 발견하면 값 자체를 교체하는 것을 원칙으로 합니다.
- **릴리스 서명을 어디서 할지 정합니다.** CI에서만 가능하게 하면 유출 경로가 줄지만, 긴급 상황의 수동 배포 경로도 함께 준비해야 합니다.

### 4. CI 검사

- **검사 단계를 정합니다**: 포맷과 정적 분석, 컴파일, 단위 테스트, 계측 테스트, 릴리스 빌드 생성.
- **PR에서 돌릴 것과 병합 후에 돌릴 것을 나눕니다.** 전부 PR에 넣으면 느려서 우회하게 되고, 전부 뒤로 미루면 문제를 늦게 발견합니다.
- **실패를 경고로 넘기지 않습니다.** 통과 기준이 없는 검사는 장식입니다.
- **릴리스 빌드를 CI에서 실제로 만듭니다.** 축소와 난독화 설정 문제는 릴리스 빌드에서만 드러나므로, 출시 직전에 처음 만들면 그때 처음 실패합니다.
- **크래시 리포트 복원 정보를 배포 과정에서 함께 올립니다.** 난독화한 빌드를 올리면서 복원 정보를 빠뜨리면 그 버전의 크래시는 읽을 수 없고, 나중에 되살릴 수도 없습니다. 무엇을 관측할지는 고려 사항 7번 항목 스킬에서 정합니다.
- **계측 테스트는 대상을 좁힙니다.** 느리고 불안정해지기 쉬워서, 넓게 깔면 결국 아무도 결과를 보지 않습니다.
- 무엇을 테스트할지 자체는 고려 사항 7번 항목 스킬에서 정합니다.

### 5. 구버전 호환성

- **구버전 앱은 사라지지 않습니다.** 업데이트하지 않는 사용자가 항상 있으므로 서버는 계속 구버전 요청을 받습니다. 클라이언트를 고치면 되는 문제가 아닙니다.
- **API 변경 규칙을 서버와 합의합니다.** 필드 추가는 안전하고, 필드 제거·의미 변경·타입 변경은 안전하지 않습니다. 안전하지 않은 변경이 필요하면 새 경로를 만들고 구버전 경로를 유지할 기간을 정합니다.
- **응답 파싱이 관대해야 합니다.** 모르는 필드는 무시하고, 필수가 아닌 값이 없을 때 화면이 죽지 않아야 합니다. 이 규칙이 없으면 서버가 필드를 추가하는 것만으로 구버전 앱이 깨집니다.
- **로컬 저장소 스키마 변경은 이미 설치된 앱의 데이터를 넘겨받아야 합니다.** 처리 방식은 고려 사항 3번 항목 스킬에서 정합니다.
- **최소 지원 버전을 올릴 때 영향 범위를 확인합니다.** 해당 버전 미만 사용자 비율을 보고 결정하며, 올리기로 했다면 6번 결정 항목의 강제 업데이트와 함께 처리합니다.

### 6. 배포·롤백·강제 업데이트

- **운영 배포 전에 거치는 단계를 정합니다.** 내부 테스터 배포와 단계적 공개는 다른 경로입니다. 스테이징 빌드를 누가 어떻게 받는지, 운영 공개 전에 어느 단계를 반드시 거치는지 정합니다.
- **단계적 배포 비율과 각 단계의 관찰 기간을 정합니다.** 한 번에 전체 공개하면 문제를 발견했을 때 이미 모두가 받은 뒤입니다.
- **관찰 지표와 중단 기준을 미리 정합니다**: 크래시율, ANR률, 주요 요청 실패율. 지표와 임계값은 고려 사항 7번 항목 스킬에서 정한 관측 대상과 같아야 합니다. 기준 없이 "괜찮아 보인다"로 다음 단계에 넘어가지 않습니다.
- **롤백은 회수가 아닙니다.** 배포를 멈출 수는 있어도 이미 설치된 앱은 되돌아가지 않습니다. 수정 버전을 만들어 심사를 거쳐 배포하기까지의 시간을 대응 계획에 넣습니다. 이 시간 동안 무엇을 할지가 7번 결정 항목입니다.
- **버전 표기와 비교 규칙을 정합니다.** 스토어에 올리는 빌드 번호는 항상 증가해야 하며 같은 번호는 거부됩니다. 최소 지원 버전 판단도 사람이 읽는 버전 문자열이 아니라 이 빌드 번호로 비교합니다. 문자열 비교는 자릿수가 바뀌는 순간 틀립니다. 클라이언트가 서버에 자기 버전을 알리는 방법도 함께 정하며, 이것이 없으면 5번 결정 항목의 최소 지원 버전 정책을 적용할 수단이 없습니다.
- **강제 업데이트 기준을 정합니다.** 서버가 최소 지원 버전을 내려주고 클라이언트가 안내 화면을 띄우는 방식이 일반적입니다. 언제 강제하고 언제 권장만 할지 미리 정하지 않으면 매번 논쟁합니다.
- **강제 업데이트 화면은 지금 배포하는 버전에 들어 있어야 합니다.** 사고가 난 뒤에 넣으면, 정작 문제가 있는 그 버전에는 없습니다.
- **권장 업데이트와 강제 업데이트를 구분합니다.** 권장은 나중에 볼 수 있어야 하고, 강제는 진행을 막습니다.

### 7. 긴급 차단

- **배포 없이 기능을 끌 수단이 있는지부터 확인합니다.** 없다면 모든 사고가 재배포로만 해결되고, 그 사이 사용자는 계속 문제를 겪습니다. 없다는 것을 확인했다면 그 수단을 만드는 일 자체를 결정에 포함합니다.
- **끌 수 있어야 할 대상을 미리 정합니다**: 새로 출시하는 기능, 외부 서비스 연동, 비용이 큰 동작, 실험 중인 화면.
- **차단됐을 때의 화면을 정의합니다.** 기능이 아예 보이지 않을지, 안내를 보여줄지. 정의하지 않으면 빈 화면이나 동작하지 않는 버튼이 남습니다.
- **설정을 받아오지 못했을 때의 기본값을 정합니다.** 네트워크가 없거나 설정 조회가 실패해도 앱이 동작해야 하며, 안전한 쪽이 기본값이어야 합니다.
- **적용 시점을 정합니다.** 앱 실행 시에만 반영할지, 화면 진입마다 확인할지. 즉시 꺼야 하는 대상은 확인 주기를 짧게 잡습니다.
- 점검 안내 화면을 띄우는 수단도 같은 범주입니다. 서버 점검 중에 사용자가 오류만 반복해서 보게 두지 않습니다.

## 작업 흐름

1. **환경 목록과 각 환경의 대상 서버를 확정합니다.** 빌드 방식과 환경을 어떻게 조합할지도 함께 정합니다.
2. **환경마다 달라지는 설정 항목을 나열하고 주입 지점을 한 곳으로 모읍니다.** 빠진 설정에서 빌드가 실패하는지 확인합니다.
3. **비밀 정보의 위치와 접근 권한을 확인합니다.** 저장소에 들어간 값이 없는지 점검합니다.
4. **CI 단계와 통과 기준을 정합니다.** PR 단계와 병합 후 단계를 나눕니다.
5. **API 변경 규칙과 최소 지원 버전 정책을 서버와 합의합니다.** 클라이언트 혼자 정할 수 없는 항목입니다.
6. **배포 비율, 관찰 지표, 중단 기준을 정합니다.** 지표는 관측 항목과 같은 것을 씁니다.
7. **긴급 차단 수단의 유무를 확인합니다.** 없으면 지금 만드는 것을 결정에 포함합니다. 사고 후에는 만들 수 없습니다.
8. **릴리스 점검 목록을 확인합니다.** 아래 표를 실제로 실행하고, 확인하지 않은 항목을 통과로 적지 않습니다.
9. **결정할 수 없는 항목은 미결정으로 남기고, 구성 변경은 사용자 승인 후에 합니다.**
