# 코루틴과 Flow

## 목적

비동기 흐름의 구조를 정하는 작업 스킬입니다. 코루틴과 Flow를 쓸 때 반복해서 갈리는 선택을 다룹니다.

다른 스킬이 이미 정하는 것은 여기서 다시 정하지 않습니다.

| 이미 정해지는 것 | 어디서 |
| --- | --- |
| 화면 이탈 시 취소할지, 앱을 닫아도 끝내야 하는지 | 고려 사항 2번 항목 스킬 |
| 네트워크 재시도 대상과 횟수 | 고려 사항 3번 항목 스킬 |
| 중복 실행과 경쟁 상태를 화면에서 어떻게 다룰지 | 고려 사항 7번 항목 스킬 |
| 테스트에서 디스패처와 시간을 제어하는 방법 | `android-tdd` 스킬 |
| 화면에서 흐름을 생명주기에 맞춰 수집하는 방법 | `compose-development` 스킬 |

이 스킬은 **그 결정들이 코루틴 구조로 어떻게 표현되는지**를 맡습니다.

## 선행 전제: 스코프가 수명을 정합니다

코루틴은 자기가 언제 끝날지 모릅니다. 어느 스코프에서 시작했느냐가 그것을 정합니다. 여기서 두 규칙이 나옵니다.

- **스코프 없이 코루틴을 띄우지 않습니다.** 아무 데도 매달리지 않은 작업은 취소할 수도, 실패를 알 수도 없습니다.
- **부모가 취소되면 자식도 취소됩니다.** 이 연결을 끊는 구성을 쓰면 화면이 사라진 뒤에도 작업이 남습니다. 끊어야 할 이유가 있다면 그 이유를 결정에 적습니다.

## 적용 범위 판단

| 요청 | 검토할 것 |
| --- | --- |
| 비동기 흐름 설계, 코루틴 사용 감사 | 전부 |
| 화면에 보여줄 값을 흐름으로 만듦 | cold·hot 선택, 구독 정책 |
| 화면 회전이나 재진입에서 요청이 다시 나감 | 구독 정책 |
| 흐름이 멈추지 않거나 배터리를 씀 | 스코프, 구독 정책 |
| 예외가 엉뚱한 곳에서 잡히거나 앱이 죽음 | 예외 위치 |
| 테스트가 불안정함 | 디스패처 주입 |

## 스코프와 디스패처

- **작업의 수명을 먼저 정하고 스코프를 고릅니다.** 화면과 함께 사라져야 하는가, 사용자가 앱을 닫아도 끝나야 하는가. 이 판단은 고려 사항 2번 항목 스킬의 결정을 따릅니다.
- **디스패처를 주입합니다.** 코드 안에서 디스패처를 직접 고르면 테스트에서 바꿀 수 없습니다. 주입 지점을 한 곳으로 모으면 테스트와 실제 구성이 갈리지 않습니다.
- **suspend 함수는 어느 디스패처에서 불러도 안전해야 합니다.** 호출하는 쪽이 스레드를 신경 쓰게 만들지 않고, 무거운 작업은 함수 안에서 옮깁니다.
- **취소를 확인하는 지점이 있는지 봅니다.** 긴 반복 안에서 취소를 확인하지 않으면 취소해도 끝까지 돕니다.

## cold와 hot

| 구분 | 성질 | 맞는 자리 |
| --- | --- | --- |
| cold | 구독할 때마다 처음부터 다시 실행 | 요청 한 번, 데이터베이스 관찰 |
| hot | 구독과 무관하게 흐르고 여러 구독자가 공유 | 여러 화면이 같은 값을 봄, 사건 전달 |

- **구독자가 하나면 cold로 둡니다.** 공유가 필요 없는데 hot으로 바꾸면 수명 관리만 늘어납니다.
- **같은 데이터를 여러 곳이 구독하는데 cold로 두면 요청이 그 수만큼 나갑니다.** 화면이 둘인데 목록을 두 번 받는 상황이 여기서 납니다.
- **사건과 상태를 구분합니다.** 상태는 최신 값이 항상 있어야 하고, 사건은 한 번만 처리되어야 합니다. 사건을 상태로 두면 화면 재구성 때 다시 처리됩니다.

## 구독 정책

**cold를 hot으로 바꿀 때 세 가지를 정합니다.**

- **어느 스코프에서 유지할 것인가.** 화면 수명이면 화면이 사라질 때 끝나고, 더 긴 수명이면 화면 밖에서도 흐릅니다.
- **언제 시작할 것인가.** 즉시 시작하면 첫 구독자가 기다리지 않지만 아무도 안 볼 때도 돕니다. 첫 구독 때 시작하면 낭비가 없지만 첫 화면에 지연이 보입니다.
- **구독자가 없어졌을 때 얼마나 유지할 것인가.** **이 값이 화면 회전 동작을 정합니다.** 즉시 멈추면 회전할 때마다 다시 요청이 나가고, 짧게 유지하면 회전 사이를 넘겨 재요청이 없습니다. 무한히 유지하면 화면을 떠나도 계속 돕니다.

세 값을 정하지 않고 기본값을 그대로 쓰면, 회전할 때마다 요청이 나가거나 백그라운드에서 흐름이 계속 도는 것 중 하나가 됩니다. 둘 다 사용자에게는 보이지 않고 나중에 문제로 드러납니다.

## 예외와 재시도

- **예외를 잡는 계층을 정합니다.** 데이터 계층에서 앱 오류 타입으로 바꾸고 위에서는 그 타입만 다루는 방식이 기본입니다. 오류 분류는 고려 사항 3번 항목 스킬에서 정합니다.
- **흐름 안의 예외는 수집하는 쪽으로 전파됩니다.** 흐름 안에서 처리할지 수집 지점에서 처리할지 정해 두지 않으면 두 곳에서 각각 잡습니다.
- **취소는 예외로 잡지 않습니다.** 모든 예외를 한 번에 잡으면 취소까지 삼켜서 취소가 동작하지 않습니다.
- **재시도를 흐름 안에 둘지 호출하는 쪽에 둘지 정합니다.** 양쪽에 두면 재시도 횟수가 곱해집니다.

## 작업 흐름

1. **이 흐름의 수명과 구독자 수를 먼저 적습니다.** 나머지 선택이 여기서 나옵니다.
2. **스코프와 디스패처를 정합니다.** 주입 지점을 확인합니다.
3. **cold로 둘지 hot으로 바꿀지 정합니다.** 구독자가 하나면 그대로 둡니다.
4. **hot이면 스코프·시작 시점·유지 시간 세 값을 명시합니다.** 기본값을 그대로 쓰기로 했다면 그것도 결정으로 적습니다.
5. **예외와 재시도의 위치를 정합니다.** 한 곳에만 둡니다.
6. **취소가 실제로 전파되는지 확인합니다.** 화면을 떠났을 때 작업이 끝나는지 봅니다.
7. **결정을 `docs/plans/_project.md`에 남길지 판단합니다.** 디스패처 주입 방식과 구독 정책 기본값은 프로젝트 전체에 적용되므로 남깁니다.
