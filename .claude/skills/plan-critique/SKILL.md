# 계획 적대적 검토

## 목적

기능 개발 계획을 구현 전에 깨뜨려 봅니다. 목표는 계획이 괜찮다고 확인하는 것이 아니라 **어디서 깨지는지 찾는 것**입니다.

계획은 만든 직후가 가장 그럴듯해 보입니다. 만든 사람은 왜 그렇게 정했는지 알고 있어서 빠진 부분이 보이지 않습니다. 구현 중반에 발견되는 문제는 대부분 계획 단계에서 한 번도 공격받지 않은 가정입니다.

## 검토 조건

**계획 문서만 읽고 판단합니다.** 계획을 만들며 나눈 대화는 근거로 쓰지 않습니다. 대화에 "그건 이래서 그렇게 정했다"가 있으면 문서에 없는 맥락으로 계획을 변호하게 되고, 그러면 공격이 성립하지 않습니다. 나중에 이 문서만 읽고 구현할 사람과 같은 조건에서 봅니다.

계획이 참조하는 코드는 읽어도 됩니다. 계획이 현실과 맞는지 확인하려면 필요합니다.

계획이 문서로 없고 대화에만 있으면 그 내용을 대상으로 검토하되, 문서만 보는 검토보다 근거가 흐리다는 것을 보고에 밝힙니다.

**이 규칙은 격리가 아니라 규율입니다.** 같은 대화 안에서는 계획의 근거가 이미 눈앞에 있어서, 쓰지 않겠다는 결심으로만 유지됩니다. 검토 결과가 중요한 계획이라면 계획 문서만 따로 전달해 별도 세션에서 검토하는 편이 확실합니다. 같은 대화에서 검토했다면 그 사실을 보고에 적어, 읽는 사람이 이 검토의 한계를 알게 합니다.

**계획을 고치지 않습니다.** 이 스킬은 발견을 내는 데까지입니다. 무엇을 반영할지는 계획을 만든 쪽이 정합니다. 검토자가 계획을 직접 고치면 무엇이 원래 계획이고 무엇이 검토 결과인지 구분되지 않고, 고친 부분은 아무도 공격하지 않은 채로 남습니다.

**자기가 만든 계획을 검토할 때가 가장 어렵습니다.** 방금 내린 결정은 근거가 기억나기 때문에 공격 대상으로 보이지 않습니다. 발견이 적게 나왔다면 계획이 좋아서가 아니라 공격을 하지 않았을 가능성을 먼저 의심합니다. 일곱 방향 각각에 무엇을 확인했는지 남기면 건너뛴 방향이 드러납니다.

## 공격 방향

일곱 가지를 순서대로 시도합니다. 앞쪽이 더 비쌉니다. 선별이 틀렸으면 뒤쪽 결정이 아무리 정교해도 소용없습니다.

### 1. 선별 공격 — 검토하지 않은 고려 사항 중 해당하는 것이 있는가

계획에 적힌 "검토한 고려 사항" 목록과 기능 내용을 대조합니다. 여덟 항목 중 이 기능의 코드에 나타날 텐데 검토되지 않은 것을 찾습니다: 모듈 구조(`module-architecture`), 상태·생명주기(`state-lifecycle`), 데이터·네트워크·동기화(`data-layer`), 인증·보안·개인정보(`auth-session`), 알림·외부 진입(`notification-entry`), 디바이스·다국어·접근성(`adaptive-ui`), 안정성·품질·성능(`reliability`), 빌드·배포·운영(`release-ops`).

작업 스킬도 함께 대조합니다. 여덟 항목과 달리 이쪽은 결정이 아니라 탐색이 산출물이므로, 해당하는데 돌지 않았으면 계획에 빈 곳이 남습니다: 사용자 귀속 데이터 정리(`session-data-cleanup`).

자주 빠지는 것: 로그인 상태가 풀렸을 때(인증), 글자를 키웠을 때(디바이스), 앱을 닫았을 때 진행 중이던 작업(상태·생명주기), 기능을 급히 꺼야 할 때(배포·운영), 이 기능이 저장한 사용자 데이터가 로그아웃에서 지워지는지(정리).

### 2. 근거 공격 — 결정의 근거가 이 기능에 실제로 적용되는가

각 결정의 근거를 읽고, 그 근거가 **이 기능에 대한 사실**인지 **일반론**인지 가릅니다. "보통 이렇게 합니다", "권장 방식입니다"는 근거가 아니라 관성입니다. 근거가 일반론이면 다른 선택지가 검토되지 않았을 가능성이 큽니다.

근거가 사실이라면 그 사실이 맞는지 확인합니다. "재진입 시 즉시 표시가 필요함" 같은 근거는 기능 설명에서 확인할 수 있어야 합니다.

### 3. 실패 경로 공격 — 각 결정이 실패하면 어떻게 되는가

결정마다 실패를 대입합니다. 네트워크 없음, 요청 타임아웃, 응답 유실 후 재시도, 프로세스 종료 후 복귀, 권한 거부, 인증 만료, 같은 동작 두 번 실행, 대상이 이미 삭제됨.

계획이 이 중 하나라도 말하지 않는다면 그 경로는 구현자가 즉석에서 정하게 됩니다. 즉석 결정은 대체로 화면마다 다르게 나옵니다.

### 4. 순서 공격 — 의존 관계가 실제인가

두 방향으로 봅니다.

- **가짜 의존**: 앞 단계 없이도 시작할 수 있는데 뒤로 밀린 단계. 병렬로 갈 수 있으면 계획이 느려집니다.
- **숨은 의존**: 뒤 단계에서 앞 단계를 뒤집게 되는 결정. 화면을 다 만든 뒤 데이터 출처를 바꾸면 화면을 다시 만듭니다. 이게 더 비쌉니다.

서버 합의 대기 항목이 막는 단계 표시가 실제와 맞는지도 확인합니다.

### 5. 완료 조건 공격 — 조건이 확인 가능한가

각 단계의 완료 조건을 읽고, 그 문장만 보고 통과·실패를 판정할 수 있는지 봅니다. "구현 완료", "정상 동작 확인", "테스트 통과"는 조건이 아닙니다. 무엇을 어떤 상태에서 확인하면 되는지가 있어야 합니다.

### 6. 미결정 공격 — 정말 지금 못 정하는가

미결정으로 남긴 항목이 실제로 외부 정보를 기다리는 것인지, 판단을 미룬 것인지 가립니다. 지금 정할 수 있는데 미결정으로 두면 구현 중에 아무나 정하게 됩니다.

반대 방향도 봅니다. 결정으로 적혀 있지만 실제로는 서버나 제품 합의가 필요한 항목이 있으면, 그 결정은 구현 중에 뒤집힙니다.

### 7. 범위 공격 — 계획대로 만들면 기능이 동작하는가

계획을 처음부터 끝까지 따라가며 사용자 흐름을 실행해 봅니다. 진입해서 목적을 달성하고 빠져나오는 경로에 빠진 화면 상태, 빠진 진입 경로, 빠진 되돌리기가 있는지 확인합니다.

## 발견을 쓰는 방법

**모든 발견은 구체적인 상황과 함께 씁니다.** 무엇이 잘못되었는지만 쓰면 계획을 고칠 수 없습니다. 어떤 상황에서 어떤 결과가 나오는지 써야 고칠 지점이 정해집니다.

- 나쁨: "오류 처리가 부족합니다"
- 좋음: "목록 조회가 실패했을 때 화면 상태가 정해져 있지 않습니다. 비행기 모드로 진입하면 빈 목록이 뜨고, 사용자는 데이터가 없다고 판단합니다"

**심각도를 셋으로 나눕니다.**

| 등급 | 판정 기준 |
| --- | --- |
| 재설계 | 이대로 가면 이미 쓴 코드를 버리거나 모듈 경계·데이터 구조를 다시 잡아야 합니다 |
| 보완 | 빠진 것을 채우면 되고 이미 정한 구조는 그대로 갑니다 |
| 확인 | 구현하면서 정해도 결과가 거의 달라지지 않습니다 |

되돌리는 비용으로 가릅니다. "중요해 보인다"가 아니라 "나중에 고치면 무엇을 버리게 되는가"가 기준입니다.

**하지 않을 것**

- 일반론을 발견으로 쓰지 않습니다. "테스트를 더 하세요", "성능을 고려하세요"는 계획을 바꾸지 못합니다.
- 계획과 코드에서 확인할 수 없는 것을 추측으로 지적하지 않습니다.
- 문서 형식, 표현, 순서 같은 겉모습을 지적하지 않습니다. 내용만 봅니다.
- 발견 개수를 채우려고 사소한 것을 올리지 않습니다. 등급이 섞여 있으면 사용자가 무엇부터 볼지 알 수 없습니다.

**발견이 없으면 없다고 말합니다.** 다만 **무엇을 공격했는지 함께 밝힙니다.** 그래야 사용자가 이 검토가 어디까지 봤는지 압니다. 일곱 방향을 다 시도하지 않았다면 시도하지 않은 것을 적습니다.

## 보고 형식

```markdown
## 검토 결과

| 공격 방향 | 결과 |
| --- | --- |
| 선별 | 발견 2건 |
| 근거 | 발견 없음 |
| 실패 경로 | 발견 1건 |
| 순서 | 발견 없음 |
| 완료 조건 | 발견 1건 |
| 미결정 | 확인하지 않음 — 계획에 미결정 항목이 없음 |
| 범위 | 발견 없음 |

재설계 N건, 보완 N건, 확인 N건

### 재설계

**1. {한 줄 요약}**
- 상황: {언제 드러나는가}
- 결과: {무엇이 잘못되는가}
- 고칠 곳: {계획의 어느 부분}

### 보완
...

### 확인
...

## 가장 큰 위험

{하나만 고른다면 이것} — 이유
```

마지막의 **가장 큰 위험**은 반드시 하나만 고릅니다. 발견이 여러 개일 때 사용자가 먼저 볼 것을 정해 주는 자리이고, 여기서 여러 개를 나열하면 우선순위가 사라집니다.
