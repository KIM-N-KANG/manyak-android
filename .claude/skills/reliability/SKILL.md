# 안정성·품질·성능

## 목적

안드로이드 앱 개발 고려 사항 8개 항목 중 7번 **안정성·품질·성능**을 담당합니다. 아래 6개 결정 항목을 각각 명시적으로 결정하거나, 기존 구현이 이미 내린 결정을 확인하고 위반을 지적합니다.

| 결정 항목 | 결정할 내용 |
| --- | --- |
| 1. 화면 상태와 오류 구분 | 로딩·성공·비어 있음·오류를 어떻게 정의하고 구분해 보여줄지 |
| 2. 복구 경로 | 오류 발생 후 사용자가 어떻게 빠져나올지 |
| 3. 중복 실행과 경쟁 상태 | 비동기 작업이 겹칠 때 무엇을 보장할지 |
| 4. 테스트 대상 | 어떤 로직과 사용자 흐름을 테스트할지 |
| 5. 성능 | 실행 속도, 스크롤, 메모리, 배터리를 어떻게 관리할지 |
| 6. 관측 | 크래시·ANR·API 실패·동기화 실패를 어떻게 확인할지 |

**고려 사항 3번 항목 스킬과의 경계**: 3번은 네트워크 계층에서 오류를 어떻게 분류하고 재시도할지를 정합니다. 이 스킬은 그 결과를 화면에서 어떻게 보여주고 사용자가 어떻게 복구할지를 정합니다. 같은 오류를 두 번 분류하지 말고, 기술적 분류는 3번에서 가져다 씁니다.

중복 실행도 세 스킬에 걸칩니다. 요청을 서버에 두 번 보내지 않는 것과 멱등성 계약은 3번 항목, 화면을 벗어난 작업의 취소 범위는 2번 항목, 결과가 겹쳐 화면 상태가 어긋나는 문제는 이 스킬이 맡습니다.

## 두 가지 전제

- **품질은 정상 경로가 아니라 실패 경로에서 갈립니다.** 정상 경로만 확인한 화면은 아직 검증되지 않은 화면입니다.
- **측정 방법이 없는 성능 결정은 결정이 아닙니다.** "빠르게 만든다"는 목표가 아니라 바람입니다. 목표 수치와 확인 수단을 함께 정합니다.

## 적용 범위 판단

요청 규모에 맞는 항목만 검토합니다.

| 요청 | 검토할 항목 |
| --- | --- |
| 화면·기능 품질 리뷰, 릴리스 전 점검 | 1~6 전부 |
| 화면에 로딩·오류 상태 추가 | 1, 2 |
| 값이 이상하게 덮이거나 두 번 실행되는 문제 | 3 |
| 테스트를 어디까지 쓸지 판단 | 4 |
| 느리거나 끊기는 문제 진단 | 5 |
| 크래시·ANR 대응, 실패 추적 | 6 |

## 이미 결정된 항목

아래 판단 기준 중 일부는 프로젝트에서 한 번 정하면 모든 기능에 그대로 적용됩니다. 그런 항목은 `docs/plans/_project.md`를 먼저 확인합니다.

- **결정이 있으면 다시 결정하지 않습니다.** 결정을 읽고, 이 요청의 코드가 그것을 지키는지만 봅니다. 어긋나면 위반으로 보고합니다. 결정 자체를 바꿔야 하면 이유와 함께 `_project.md`를 갱신합니다.
- **결정이 없으면 여기서 정하고 그 결과를 `_project.md`에 남깁니다.** 남기지 않으면 다음 기능이 같은 결정을 처음부터 다시 하고, 기능마다 구조가 갈립니다.

이 문서를 이미 읽었다면 다시 열지 않고 그 내용을 씁니다.

| 구분 | 항목 |
| --- | --- |
| 프로젝트에서 한 번 결정 | 1 화면 상태와 오류 구분, 2의 복구 원칙, 4 테스트 대상, 5 성능 기준, 6 관측 |
| 기능마다 판단 | 2의 화면별 복구 경로, 3 중복 실행과 경쟁 상태 |

## 결정 항목별 판단 기준

### 1. 화면 상태와 오류 구분

**화면 상태는 네 가지입니다: 로딩, 성공, 비어 있음, 오류.** 네 가지를 모두 정의하지 않으면 정의되지 않은 조합이 화면에 나타납니다. 특히 비어 있음과 오류를 같이 처리하면 사용자는 데이터가 없다고 믿습니다.

- **로딩 표현을 정합니다**: 화면 전체를 막을지 실패할 수 있는 영역만 표시할지, 자리 표시자를 그릴지 회전 표시만 둘지.
- **이미 내용이 있는 상태에서 다시 불러올 때**를 따로 정합니다. 기존 내용을 유지한 채 갱신 중임만 표시할지, 비우고 로딩을 보여줄지. 비우면 사용자는 화면이 초기화된 것으로 느낍니다. 캐시를 먼저 보여줄지는 고려 사항 3번 항목 스킬의 결정과 이어집니다.
- **짧은 로딩의 깜빡임을 처리합니다.** 응답이 빠르면 로딩 표시가 번쩍이고 사라져 오히려 불안정해 보입니다. 일정 시간 이후에만 표시할지, 표시했다면 최소 시간을 유지할지 정합니다.

**오류에서 화면이 구분해야 하는 것은 원인이 아니라 사용자가 할 수 있는 행동입니다.**

| 사용자가 할 수 있는 것 | 해당 상황 | 표현 |
| --- | --- | --- |
| 다시 시도 | 연결 실패, 타임아웃, 서버 일시 오류 | 재시도 수단을 함께 제공 |
| 입력 수정 | 입력값 검증 실패 | 해당 입력 옆에 무엇이 잘못됐는지 |
| 다시 로그인 | 인증 만료·무효 | 로그인으로 유도하고 원래 대상으로 복귀 |
| 할 수 있는 것이 없음 | 권한 없음, 삭제된 대상, 지원하지 않는 버전 | 상황 설명과 다른 경로 제시 |

**표시 위치도 함께 정합니다.**

| 표시 위치 | 적합한 경우 |
| --- | --- |
| 화면 전체 | 화면을 그릴 내용 자체를 받지 못함 |
| 해당 영역 | 화면 일부만 실패, 나머지는 정상 사용 가능 |
| 입력 옆 | 입력값 문제. 잠깐 뜨는 알림은 어느 입력이 문제인지 알려주지 못함 |
| 일시적 알림 | 화면 내용은 그대로인데 부수 동작이 실패. 재시도나 되돌리기를 함께 제공 |
- **서버 문구를 그대로 쓸지 정합니다.** 그대로 쓰면 내부 용어가 노출되고, 전부 감추면 사용자가 원인을 알 수 없습니다. 어떤 오류에서 서버 문구를 신뢰할지 서버와 합의합니다.

### 2. 복구 경로

- **모든 오류 표시에 다음 행동이 있어야 합니다.** 재시도, 입력 수정, 다른 화면으로 이동 중 하나가 없으면 사용자는 앱을 닫습니다.
- **자동 복구 여부를 정합니다.** 연결이 돌아왔을 때 스스로 다시 시도할지, 사용자가 눌러야 할지. 자동으로 하려면 사용자가 화면을 보고 있을 때만 하는지, 무엇이 바뀌었는지 알릴지도 함께 정합니다.
- **재시도가 무엇을 다시 하는지 정합니다.** 화면 전체를 다시 불러올지, 실패한 요청만 다시 보낼지에 따라 사용자가 기다리는 시간이 달라집니다.
- **작성 중이던 내용을 잃지 않게 합니다.** 오류로 화면을 다시 그릴 때 입력이 사라지면 사용자는 처음부터 다시 씁니다. 보존 방법은 고려 사항 2번 항목 스킬에서 정합니다.
- **부분 실패 후 화면 상태를 정확히 맞춥니다.** 저장이 실패했는데 화면에는 저장된 것처럼 남으면 사용자는 나중에 데이터를 잃습니다.
- **막다른 화면이 없는지 확인합니다.** 뒤로 갈 수도, 다시 시도할 수도 없는 상태가 남아 있는지 봅니다.
- **반복 실패 시 안내를 바꿀지 정합니다.** 같은 문구를 세 번 보여주는 것보다 다른 경로를 제안하는 편이 낫습니다.

### 3. 중복 실행과 경쟁 상태

- **위험 지점을 먼저 나열합니다**: 버튼 연타, 요청 중 화면 전환, 자동 재시도와 사용자 재시도 중첩, 입력할 때마다 나가는 검색 요청, 새로고침과 다음 페이지 요청 동시 진행.
- **응답 순서 역전을 처리합니다.** 나중에 보낸 요청이 먼저 도착할 수 있습니다. 검색어나 필터처럼 조건이 바뀌는 요청은 최신 요청의 결과만 반영합니다. 이 처리가 없으면 이전 검색 결과가 화면에 남습니다.
- **화면 상태 갱신 지점을 한 곳으로 모읍니다.** 여러 비동기 결과가 각자 상태를 조금씩 바꾸면 어느 순간 어긋난 조합이 화면에 나타납니다.
- **취소된 작업의 결과를 반영하지 않습니다.**
- **같은 데이터를 여러 곳에서 갱신하면 마지막 것이 이깁니다.** 어느 것이 진짜인지 정하는 것은 고려 사항 3번 항목 스킬의 단일 출처 결정입니다.
- **중복 차단은 요청 계층에서 하되 사용자에게 진행 중임을 보여줍니다.** 조용히 무시하면 눌리지 않았다고 생각해 더 누릅니다.

### 4. 테스트 대상

**전부 테스트하지 않습니다. 깨졌을 때 비용이 큰 것부터 고릅니다.**

| 우선순위 | 대상 |
| --- | --- |
| 높음 | 되돌릴 수 없는 동작(결제, 삭제, 전송), 인증·세션 전환, 데이터 변환과 매핑, 오류 분기 |
| 중간 | 상태 홀더의 상태 전이, 목록 페이지네이션, 오프라인·동기화 규칙 |
| 낮음 | 단순 표시 컴포넌트, 프레임워크가 이미 보장하는 동작 |

- **테스트 종류를 목적에 맞게 씁니다.** 순수 로직은 단위 테스트, 상태 전이는 상태 홀더 테스트, 화면 흐름은 UI 테스트로 확인합니다. UI 테스트로 로직을 검증하면 느리고 자주 깨집니다.
- **실패 경로를 테스트합니다.** 정상 경로만 있는 테스트 묶음은 이 스킬의 다른 결정을 전혀 보호하지 못합니다.
- **테스트하기 어렵다면 구조 문제일 수 있습니다.** 현재 시각, 난수, 시스템 상태를 직접 참조하면 결과를 고정할 수 없습니다. 바꿔 끼울 수 있는 경계를 만듭니다.
- **가끔 실패하는 테스트를 방치하지 않습니다.** 불안정한 테스트가 몇 개 생기면 곧 전체 결과를 아무도 믿지 않습니다.
- CI에서 무엇을 언제 돌릴지는 고려 사항 8번 항목 스킬에서 정합니다.

### 5. 성능

- **목표와 측정 방법을 먼저 정합니다.** 기준이 없으면 개선 여부를 말할 수 없습니다. 최소한 다음을 구분해 정합니다: 프로세스가 없는 상태에서의 시작 시간과 이미 떠 있는 상태에서의 시작 시간, 주요 화면의 첫 내용 표시 시간, 목록 스크롤에서 놓친 프레임 비율.
- **측정은 릴리스 빌드와 저사양 기기에서 합니다.** 디버그 빌드와 고급 기기의 수치는 사용자가 겪는 것과 다릅니다.
- **시작 속도**: 앱 시작 시 실행되는 일을 나열하고, 첫 화면에 필요 없는 초기화를 뒤로 미룹니다. 라이브러리 초기화가 시작 시간의 대부분인 경우가 흔합니다.
- **스크롤 끊김**: 목록 항목에서 큰 이미지 디코딩, 무거운 계산, 동기 입출력을 하지 않습니다. 항목에 안정적인 식별자를 주어 불필요한 갱신을 줄입니다.
- **다시 그리는 범위**: 자주 바뀌는 값을 넓은 범위에서 읽으면 화면 전체가 다시 그려집니다. 상태를 읽는 위치를 실제로 바뀌는 부분까지 좁힙니다. 상태 노출 형태는 고려 사항 2번 항목 스킬에서 정합니다.
- **메모리**: 큰 이미지가 주된 원인입니다. 표시 크기에 맞춰 불러오고 화면을 벗어나면 놓아줍니다. 누수는 오래 사는 객체가 짧게 사는 객체를 붙잡을 때 생기며, 고려 사항 2번 항목 스킬의 상태 홀더 규칙과 이어집니다.
- **배터리와 데이터**: 주기 실행 빈도, 화면이 꺼진 뒤에도 도는 작업, 위치·센서 사용 시간이 원인입니다. 백그라운드 작업 결정은 고려 사항 2번 항목 스킬과 같은 자리입니다.
- **앱 크기**: 쓰지 않는 리소스와 라이브러리, 이미지 형식을 확인합니다. 설치 이탈에 직접 영향을 줍니다.
- **추측으로 고치지 않습니다.** 측정해서 원인을 찾은 뒤 고치고, 고친 뒤 다시 측정합니다.

### 6. 관측

- **무엇을 볼 수 있어야 하는지 먼저 정합니다**: 크래시, ANR, 주요 API 실패율, 전송·동기화 실패, 화면 진입 실패.
- **크래시 리포트가 해석 가능한 상태인지 확인합니다.** 난독화된 스택은 복원 정보 없이는 읽을 수 없습니다. 복원 정보 업로드를 배포 과정에 넣는 것은 고려 사항 8번 항목 스킬에서 정합니다.
- **ANR은 크래시와 다르게 잡힙니다.** 주 스레드를 막는 동기 입출력, 큰 파싱, 잠금 대기가 원인이며 리포트 도구와 스토어 통계를 함께 봅니다.
- **오류를 삼키지 않습니다.** 비어 있는 예외 처리는 문제를 없애는 게 아니라 보이지 않게 만듭니다. 화면에 표시하지 않을 오류도 기록은 남깁니다.
- **기록에 민감 정보를 넣지 않습니다.** 무엇을 남기지 않을지는 고려 사항 4번 항목 스킬에서 정합니다.
- **버전별로 구분해 볼 수 있어야 합니다.** 어느 릴리스에서 나빠졌는지 모르면 원인을 좁힐 수 없습니다.
- **확인 주기와 대응 기준을 정합니다.** 무엇이 얼마나 나빠지면 사람이 봐야 하는지 정하지 않으면 지표는 쌓이기만 합니다.
- **사용자 신고 경로를 둘지 정합니다.** 지표에 잡히지 않는 문제는 사용자만 압니다.

## 작업 흐름

1. **대상 화면과 흐름의 실패 지점을 나열합니다.** 추측하지 않고 실제 요청 지점, 예외 처리, 상태 갱신 지점을 읽습니다.
2. **오류를 사용자 행동 기준으로 분류하고 표현 위치를 정합니다.** 기술적 분류는 고려 사항 3번 항목의 결정을 가져다 씁니다.
3. **각 오류에 복구 경로를 배정합니다.** 다음 행동이 없는 오류가 하나도 없어야 합니다.
4. **중복·경쟁 위험 지점을 점검합니다.** 나열한 위험 지점마다 무엇을 보장하는지 적습니다.
5. **테스트 대상을 우선순위로 고릅니다.** 테스트하지 않기로 한 것도 이유와 함께 남깁니다.
6. **성능 목표와 측정 방법을 정합니다.** 수치와 측정 조건을 함께 적습니다.
7. **관측 대상과 확인 경로를 정합니다.**
8. **검증 시나리오를 실행합니다.** 아래 표에서 이 변경에 필요한 항목을 고릅니다.
9. **결정할 수 없는 항목은 미결정으로 남기고, 코드 변경은 사용자 승인 후에 합니다.**

### 검증 시나리오

| 시나리오 | 확인 방법 | 검증 대상 |
| --- | --- | --- |
| 오류 종류별 표현 | 네트워크 차단, 잘못된 입력, 만료된 인증, 없는 대상으로 각각 진입 | 1번 결정 항목 |
| 복구 확인 | 오류 상태에서 조건을 정상으로 되돌리고 재시도 | 2번 결정 항목 |

| 연타와 빠른 전환 | 버튼 연타, 요청 중 화면을 빠르게 오감 | 3번 결정 항목 |
