# 앱 구조

## 목적

현재 요구를 강제할 가장 작은 경계를 선택합니다. 미래 가능성만으로 모듈이나 계층을 만들지 않습니다.

## 프로젝트 결정 우선

`docs/plans/_project.md`와 실제 `settings.gradle.kts`를 먼저 읽습니다. 현재 결정과 다른 구조가 필요할 때만 선택지와 전환 비용을 제시하고 프로젝트 결정을 갱신합니다.

## 모듈 경계

현재 코드를 기존 모듈에 둘 수 있으면 그대로 둡니다. 새 모듈은 다음과 같은 구체적 신호가 있을 때만 만듭니다.

- 독립적으로 빌드·배포·소유할 경계가 필요합니다.
- 두 기능이 공유하는 안정된 코드가 생겼습니다.
- 의존성을 컴파일 단위로 막아야 합니다.
- 측정된 빌드 병목을 분리할 수 있습니다.

공통 사용처가 하나뿐인 코드를 미리 `core`로 올리지 않습니다. convention plugin도 반복되는 모듈 설정이 실제로 생겼을 때 도입합니다.

## 계층과 의존성

- Domain 계층은 여러 저장소를 조합하거나 재사용되는 비즈니스 규칙이 있을 때만 둡니다.
- Repository를 그대로 호출하는 pass-through UseCase는 만들지 않습니다.
- Domain이 있다면 의존성은 `ui → domain ← data`입니다. Data가 Domain의 인터페이스를 구현하며 Domain은 Android·HTTP·DB 구현을 모릅니다.
- Domain이 없다면 UI가 기능 내부의 Repository 계약을 사용하고 구현 세부는 노출하지 않습니다.
- 모듈 간 의존은 조립 모듈에서 기능 모듈로, 기능 모듈에서 필요한 공통 모듈로만 향하게 합니다. 기능 간 직접 의존은 피합니다.

## 네비게이션

- 화면에는 이동 객체 대신 값과 콜백을 전달합니다.
- 라우트에는 복원 가능한 식별자만 넘기고 화면 데이터는 목적지에서 다시 얻습니다.
- 인증·온보딩 완료 후 제거할 화면, 외부 진입의 부모 화면, 중복 진입 처리를 실제 흐름에 맞게 정합니다.
- 창 크기에 따라 화면 구성이 달라질 때만 adaptive layout과 백스택의 관계를 함께 결정합니다.

## 결과

선택한 경계, 근거, 의존 방향, 이동 계약과 전환 비용만 보고합니다. 감사에서는 위반을 파일과 줄로 지적합니다. 구조 변경이 이미 요청 범위에 포함되어 있으면 추가 승인을 묻지 않습니다.
