# 데이터베이스 마이그레이션

## 목적

로컬 데이터베이스 스키마 변경을 안전하게 넘기는 작업 스킬입니다. 스키마를 바꿀 때마다 반복되는 확인을 대신합니다.

어떤 데이터를 로컬 DB에 둘지는 고려 사항 3번 항목 스킬에서 정합니다. 로그아웃과 계정 전환 시 어떤 테이블을 비울지는 `session-data-cleanup` 스킬이 다룹니다. 이 스킬은 **이미 기기에 있는 데이터를 새 스키마로 옮기는 일**만 맡습니다.

## 선행 전제: 사용자 기기의 데이터는 되돌릴 수 없습니다

서버 데이터는 잘못 옮겨도 원본이 남아 있지만, 기기의 로컬 DB는 그 기기에만 있습니다. 마이그레이션이 잘못되면 복구할 원본이 없습니다. 여기서 두 규칙이 나옵니다.

- **개발 중에는 거의 드러나지 않습니다.** 개발자는 앱을 지웠다 깔기 때문에 항상 새 스키마로 시작합니다. 사고는 이전 버전을 쓰던 사용자가 업데이트할 때 처음 납니다.
- **되돌릴 수 없는 변경은 배포되면 끝입니다.** 스토어에 올라간 버전은 회수할 수 없고, 이미 데이터를 잃은 사용자는 되돌아오지 않습니다.

## 적용 범위 판단

| 요청 | 하는 일 |
| --- | --- |
| 엔티티·테이블 추가·수정 | 변경 유형 판단 → 마이그레이션 작성 → 테스트 |
| DB 버전 올리기 | 지원 범위 확인, 누락된 경로 점검 |
| 업데이트 후 데이터가 사라진다는 문제 | 마이그레이션 경로와 파괴적 대체 여부 확인 |
| 마이그레이션 테스트 정비 | 지원 버전 전부의 경로 확인 |
| DB 도입 | 스키마 내보내기 설정과 버전 정책부터 |

## 준비

- **스키마 파일을 내보내 저장소에 커밋합니다.** 내보내지 않으면 무엇이 바뀌었는지 코드 리뷰에서 볼 수 없고, 마이그레이션 테스트도 쓸 수 없습니다. DB를 도입하는 시점에 켭니다.
- **버전 변경과 스키마 파일 변경은 함께 올라옵니다.** 한쪽만 있는 커밋은 그 자체로 문제입니다.
- **어느 앱 버전까지 올라올 수 있는지 정합니다.** 이 범위가 마이그레이션 경로의 개수를 정합니다. 범위를 정하지 않으면 아주 오래된 버전까지 무한히 지원하게 됩니다.

## 변경 유형별 영향

| 변경 | 기존 데이터에 미치는 영향 |
| --- | --- |
| 테이블 추가 | 없음. 가장 안전합니다 |
| 널 허용 컬럼 추가 | 없음. 기존 행은 비어 있게 됩니다 |
| 널 불가 컬럼 추가 | **기본값이 없으면 실패합니다.** 기존 행에 넣을 값을 정해야 합니다 |
| 컬럼 삭제·이름 변경 | 테이블을 다시 만들고 값을 옮겨야 합니다. 옮기지 않으면 그 값은 사라집니다 |
| 타입 변경 | 변환 규칙이 필요합니다. 변환할 수 없는 값이 있으면 어떻게 할지 정합니다 |
| 기본값 변경 | 기존 행에는 적용되지 않습니다. 소급 적용할지 정합니다 |
| 인덱스 추가·삭제 | 데이터는 그대로지만 큰 테이블에서는 시간이 걸립니다 |
| 외래 키 추가 | **기존 데이터가 제약을 어기면 실패합니다.** 어기는 행을 어떻게 할지 먼저 정합니다 |

- **널 불가와 외래 키가 사고의 대부분입니다.** 개발 기기의 빈 테이블에서는 통과하고 실제 데이터가 있는 기기에서 실패합니다.
- **긴 마이그레이션은 앱 시작을 막습니다.** 큰 테이블을 다시 만드는 작업이 시작 경로에 있으면 사용자는 멈춘 화면을 봅니다.

## 파괴적 대체

- **운영 빌드에서 데이터를 지우고 다시 만드는 방식을 켜지 않습니다.** 켜 두면 마이그레이션을 빠뜨렸을 때 오류 없이 사용자 데이터가 사라지고, 아무도 알아채지 못합니다.
- 캐시성 데이터만 담은 DB라면 파괴적 대체가 맞을 수 있습니다. **그 판단을 명시적으로 적습니다.** 적지 않으면 다음 사람이 판단할 수 없습니다.
- 개발 빌드에서만 켜는 구성이라면, **운영 빌드에서 꺼져 있는지 확인하는 방법**까지 정합니다.

## 실패 처리

- **마이그레이션이 실패하면 앱이 시작되지 않습니다.** 그대로 두면 사용자는 앱을 지웠다 까는 것 외에 방법이 없습니다.
- 실패했을 때 무엇을 할지 정합니다: 데이터를 버리고 새로 시작할지, 사용자에게 알리고 선택하게 할지, 서버에서 다시 받을 수 있는지.
- **실패를 기록으로 남깁니다.** 남기지 않으면 얼마나 많은 사용자가 겪었는지 알 수 없습니다. 기록 경로는 고려 사항 7번 항목 스킬에서 정합니다.

## 작업 흐름

1. **현재 스키마와 지원 버전 범위를 확인합니다.** 스키마 파일이 없으면 그것부터 켭니다.
2. **변경 유형을 위 표에서 찾습니다.** 여러 변경이 섞이면 각각 확인합니다.
3. **기존 데이터에 미치는 영향을 적습니다.** 널 불가 컬럼의 기본값, 외래 키를 어기는 행, 변환할 수 없는 값을 명시합니다.
4. **마이그레이션을 작성합니다.** 지원 범위의 모든 이전 버전에서 올라오는 경로를 만듭니다.
5. **마이그레이션 테스트를 씁니다.** 이전 버전 스키마로 데이터를 넣고 올린 뒤, 값이 살아 있는지 확인합니다. 테스트를 먼저 쓸 경우 `android-tdd` 스킬을 씁니다.
6. **파괴적 대체가 운영 빌드에서 꺼져 있는지 확인합니다.**
7. **실패 경로를 정합니다.**
8. **실행해 확인합니다.** 명령 선택은 `android-change-verification` 스킬을 씁니다.
