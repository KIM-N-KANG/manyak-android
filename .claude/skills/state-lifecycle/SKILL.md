# 상태와 생명주기

## 핵심 질문

상태를 잃었을 때 사용자가 무엇을 다시 해야 하는지 먼저 판단하고 필요한 수명만 부여합니다.

| 상태 성격 | 기본 위치 |
| --- | --- |
| 복원이 필요 없는 로컬 표현 | `remember` |
| 재생성 뒤 복원할 로컬 UI 상태 | `rememberSaveable` |
| 화면 데이터·비동기 상태 | ViewModel |
| ViewModel에서 프로세스 복원이 필요한 작은 값 | `SavedStateHandle` |
| 명시적 앱 재실행 이후에도 필요한 값 | DataStore·DB·파일 등 영속 저장소 |

`rememberSaveable`과 `SavedStateHandle`은 일반 영속 저장소가 아닙니다. 복원 가능한 작은 식별자·입력에만 사용합니다. 서버에서 다시 받을 수 있는 큰 데이터는 saved state에 넣지 않고, 화면 전용 펼침·대화상자 상태를 무조건 ViewModel로 올리지 않습니다.

## 복원 결정

- 사용자 입력과 진행 단계처럼 재작업 비용이 큰 값만 복원합니다.
- 라우트는 복원에 필요한 식별자를 가져야 하며 메모리 객체에 의존하지 않습니다.
- 사용자가 직접 완료하거나 취소한 흐름이 다음 실행에서 되살아나지 않게 초기화 시점을 정합니다.
- 구성 변경과 프로세스 종료를 같은 검증으로 취급하지 않습니다.

## 비동기 작업

- 화면 표시를 위한 읽기는 화면 수명에 맞춰 취소합니다.
- 서버에 이미 도달할 수 있는 쓰기는 취소만으로 되돌릴 수 없으므로 멱등성과 결과 재조회 경로를 함께 정합니다.
- 사용자가 확정한 쓰기라고 해서 모두 WorkManager로 옮기지 않습니다.
- WorkManager는 앱 종료 후에도 완료해야 하고 지연 실행이 허용되며 재시도·실행 조건이 필요한 작업에 사용합니다. 결제나 즉시 결과가 필요한 요청은 별도 계약을 따릅니다.

## 작업 방식

변경된 상태와 작업만 목록화해 수명, 복원, 취소 범위를 결정합니다. 여러 기능이 따라야 하는 공통 기술 결정으로 채택한 경우에만 `docs/plans/_project.md`를 갱신합니다.

검증은 실행하지 않고 필요한 경우 다음 위험 태그만 `android-change-verification`에 전달합니다.

- `state-restore` — 구성 변경 또는 프로세스 복원 동작이 바뀜
- `durable-work` — 앱 종료 뒤 지속되는 작업이 바뀜
